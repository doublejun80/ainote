# 프론트 엔드와 백엔드

프론트엔드와 백엔드는 개발 입문자가 가장 자주 듣는 구분입니다. 그런데 이 말을 너무 단순하게 이해하면 나중에 금방 막히게 됩니다. 프론트엔드는 그저 예쁘게 꾸미는 부분이고, 백엔드는 그 밖의 어려운 것 전부라고 생각하는 경우가 많은데, 실제로는 그렇게 단순하지 않습니다.

가장 쉬운 설명은 이렇습니다. 프론트엔드는 사용자가 직접 보고 만지는 쪽입니다. 화면, 버튼, 입력창, 메뉴, 그래프, 애니메이션, 사용 흐름 같은 것이 여기에 포함됩니다. 백엔드는 눈에 잘 보이지 않지만 서비스가 제대로 돌아가도록 뒤에서 처리하는 쪽입니다. 데이터 저장, 로그인 확인, 권한 검사, 주문 처리, 외부 시스템과 연동하는 일 등이 여기에 들어갑니다.

## 프론트엔드는 무엇을 맡나

프론트엔드의 핵심 역할은 사용자가 서비스를 이해하고 조작할 수 있게 만드는 것입니다. 화면을 보기 좋게 만드는 것만이 아니라, 어떤 순서로 보여 줄지, 실수했을 때 어떻게 안내할지, 정보가 너무 많을 때 어떻게 정리할지도 프론트엔드의 일입니다.

예를 들어 회원가입 화면을 생각해 보면, 입력칸을 배치하고, 비밀번호 조건을 보여 주고, 잘못 입력했을 때 경고를 띄우고, 가입 완료 후 다음 화면으로 넘어가게 만드는 일까지 모두 프론트엔드에 속합니다. 즉, 프론트엔드는 디자인과 개발이 만나는 지점이자 사용자 경험을 책임지는 영역입니다.

## 백엔드는 무엇을 맡나

백엔드는 사용자가 직접 보지 않는 영역에서 서비스의 규칙과 데이터를 처리합니다. 회원가입 예시를 이어 가면, 백엔드는 이메일이 이미 가입된 것인지 확인하고, 비밀번호를 안전하게 저장하고, 가입 정보를 데이터베이스에 기록하고, 필요한 경우 인증 메일을 보내는 일을 담당합니다.

또한 백엔드는 서비스의 중심 규칙을 지키는 역할을 합니다. 주문 취소가 가능한 시간인지, 할인 쿠폰을 중복 사용하면 안 되는지, 관리자만 볼 수 있는 데이터인지 같은 판단은 보통 백엔드에서 이뤄집니다. 이유는 간단합니다. 사용자의 기기 안에서만 처리하면 조작되기 쉽기 때문입니다.

## 둘은 어떻게 연결되나

프론트엔드와 백엔드는 보통 약속된 형식으로 대화합니다. 이 연결 지점을 API라고 부릅니다. API는 프로그램끼리 대화하는 약속이라고 이해하면 됩니다. 프론트엔드가 "이 사용자 정보를 주세요"라고 요청하면, 백엔드는 약속된 형식으로 응답합니다.

여기서 중요한 것은 둘이 완전히 따로 노는 존재가 아니라는 점입니다. 프론트엔드가 어떤 데이터를 필요로 하는지, 백엔드가 어떤 형식으로 줄 수 있는지 서로 맞아야 서비스가 부드럽게 동작합니다. 그래서 실무에서는 화면 개발자와 서버 개발자가 계속 소통하게 됩니다.

## 왜 초보자가 이 구분을 꼭 알아야 하나

이 구분을 알면 문제가 생겼을 때 어디를 봐야 할지 감이 생깁니다. 버튼이 안 눌리는 문제인지, 눌렀는데 서버가 응답을 안 하는 문제인지, 응답은 왔는데 화면에 표시가 안 되는 문제인지 나누어 생각할 수 있기 때문입니다.

또한 앞으로 배우게 될 많은 주제가 어느 편에 더 가까운지 파악하기 쉬워집니다. 데이터베이스, 인증, 서버 배포는 보통 백엔드와 더 가깝고, 화면 상태 관리나 사용자 상호작용은 프론트엔드와 더 가깝습니다. 물론 둘이 완전히 분리되는 것은 아니지만, 큰 분류를 알고 있으면 학습 지도가 훨씬 선명해집니다.

## 자주 하는 오해

프론트엔드는 쉬운 쪽이고 백엔드는 어려운 쪽이라고 생각하는 경우가 많습니다. 하지만 실제로는 종류가 다른 어려움일 뿐입니다. 프론트엔드는 브라우저 차이, 복잡한 화면 상태, 접근성, 사용자 경험 문제를 다룹니다. 백엔드는 보안, 데이터 일관성, 성능, 장애 대응을 다룹니다. 둘 다 만만하지 않습니다.

또한 프론트엔드는 디자인이고 백엔드는 개발이라고 생각하는 것도 오해입니다. 프론트엔드 역시 분명한 개발 영역이며, 규모가 커질수록 구조와 성능, 테스트가 매우 중요해집니다.

## 핵심만 다시 정리하면

프론트엔드는 사용자가 직접 만나는 화면과 상호작용을 담당하고, 백엔드는 데이터와 규칙과 보이지 않는 처리 과정을 담당합니다. 둘은 API 같은 약속을 통해 연결되며, 어느 한쪽만 잘해서는 좋은 서비스가 되기 어렵습니다.

## 현업 장면으로 바꾸면 이렇게 보입니다

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 사용자 경험과 개발 비용을 함께 비교할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

결국 이 개념을 이해한다는 것은 화면 개발과 서버 개발을 따로 배우는 이유가 보입니다

## 여기서 많이 생기는 오해

이 개념이 갑자기 어려워지는 순간은 보통 웹, 웹앱, 네이티브 앱, 프론트엔드, 백엔드를 모두 비슷한 수준의 말로 받아들이는 점입니다.

어떤 말은 제품 형태를 가리키고, 어떤 말은 역할 분리를 가리키며, 어떤 말은 실행 환경을 말한다는 점을 먼저 구분해야 합니다. 그러면 비슷한 용어를 만나도 같은 상자에 모두 넣어 버리는 실수를 줄일 수 있습니다.

## 읽고 끝내지 않으려면 이렇게 해 보세요

이 개념을 내 것으로 만드는 가장 빠른 방법은 작은 실험입니다. 거창한 프로젝트가 아니라도 괜찮습니다.

1. 자주 쓰는 서비스 세 개를 떠올리고 이 주제 관점에서 각각 어떤 형태인지 분류해 봅니다.

2. 화면에서 일어나는 일과 서버에서 일어나는 일을 두 칸으로 나눠 적어 보면 경계가 훨씬 분명해집니다.

3. 내가 만들고 싶은 기능 하나를 정해 두고 브라우저, 모바일 앱, 서버 중 어디부터 필요할지 순서를 적어 봅니다.

## 이 절을 단독 지식으로 두지 않는 방법

이 개념을 이해해 두면 뒤쪽 장을 읽을 때 새 용어가 나와도 덜 위압적으로 느껴집니다. 실제로 3장의 도구 선택, 4장의 API 개념, 8장의 실제 통신 흐름에서 같은 기준이 다시 필요합니다.

결국 이 절의 목적은 지식을 하나 더 추가하는 것이 아니라, 다음에 나올 개념의 자리를 미리 만들어 두는 데 있습니다.
