# CBD 방법론은 무엇인가요?

CBD는 Component-Based Development, 우리말로 하면 컴포넌트 기반 개발입니다. 이름 그대로 소프트웨어를 큰 덩어리 하나로 만들기보다, 재사용 가능한 부품 단위로 나누어 조립하듯 개발하자는 생각입니다. 초보자에게는 낯선 약어일 수 있지만, 사실 오늘날 프론트엔드의 컴포넌트 구조나 백엔드의 모듈화 사고와도 어느 정도 맞닿아 있습니다.

이 방법이 주목받은 이유는 모든 기능을 처음부터 다시 만들면 비용이 너무 크기 때문입니다. 로그인, 결제, 화면 입력 검증, 알림 전송 같은 기능은 여러 서비스에서 반복해서 나타납니다. 그렇다면 잘 만들어 둔 부품을 다시 사용할 수 있도록 설계하는 편이 더 효율적입니다. CBD는 이런 재사용을 조직적으로 강화하려는 접근입니다.

## 컴포넌트 기반 개발은 무엇을 강조하나요

핵심은 분리와 결합입니다. 각 컴포넌트는 자기 역할이 분명해야 하고, 외부와는 약속된 방식으로만 연결되어야 합니다. 그래야 어떤 부품을 바꿔도 전체가 한꺼번에 무너지지 않습니다. 예를 들어 결제 모듈, 사용자 인증 모듈, 검색 모듈이 명확하게 나뉘어 있다면 팀별로 나누어 개발하기도 쉬워지고, 특정 부분만 교체하기도 쉬워집니다.

이 사고방식은 단지 코드 재사용만을 뜻하지 않습니다. 테스트, 배포, 유지보수의 범위를 줄이는 효과도 있습니다. 문제가 생겼을 때 어느 부품에서 비롯됐는지 찾기 쉽고, 잘 만든 부품은 여러 제품에서 반복 활용할 수 있습니다.

## 그렇다면 라이브러리나 프레임워크와는 어떻게 다를까요

컴포넌트 기반 개발을 설명하다 보면 라이브러리, 모듈, 프레임워크와 자꾸 섞입니다. 라이브러리는 필요한 기능을 담은 도구 상자이고, 프레임워크는 큰 구조와 규칙을 제공하는 틀입니다. 컴포넌트는 그 안에서 재사용 가능한 부품 단위를 말하는 경우가 많습니다. CBD는 바로 그런 부품 단위 설계를 개발 방식의 중심에 두는 것입니다.

즉, CBD는 특정 제품 이름이 아니라 처음부터 재사용 가능한 부품으로 생각하며 설계하자는 방법론적 태도라고 볼 수 있습니다. 그래서 웹 화면에서는 버튼과 카드와 폼을 컴포넌트로 쪼개고, 서버에서는 인증과 주문과 알림을 모듈 또는 서비스 단위로 나누는 식의 실천과 이어집니다.

## 지금도 의미가 있을까요

물론입니다. 이름 자체를 자주 듣지 못하더라도, 현대 개발은 대부분 재사용과 모듈화를 중요하게 생각합니다. 디자인 시스템, UI 컴포넌트 라이브러리, 패키지화된 기능 모듈, 서비스 분리 같은 흐름은 모두 같은 문제의식을 공유합니다. 기능을 부품화해 이해하기 쉽게 만들고, 바꾸기 쉽게 만들고, 재사용하기 쉽게 만들자는 것입니다.

초보자는 CBD를 오래된 시험 용어로 여기지 말고, 왜 프로젝트를 잘게 나누려 하는가를 설명하는 개념으로 받아들이면 좋습니다. 그 순간 이 방법론은 현재에도 충분히 살아 있는 실용 개념이 됩니다.

## 핵심만 다시 정리하면

CBD는 소프트웨어를 재사용 가능한 컴포넌트 단위로 나누어 개발하자는 접근입니다. 핵심은 역할 분리, 명확한 연결 규칙, 재사용성, 유지보수성에 있습니다. 오늘날 이름은 덜 자주 들려도, 모듈화와 컴포넌트화라는 형태로 여전히 널리 살아 있는 사고방식입니다.

## 실제로 만들 때는 이런 선택으로 이어집니다

이 개념은 정의 하나로 끝나는 주제가 아니라, 실제 선택의 기준이 되는 개념입니다. 특히 테스트와 배포 자동화를 언제 도입할지 정할 때 이 절의 내용이 곧바로 판단 기준이 됩니다.

이 관점을 잡아 두면 애자일, DevOps, CI/CD 같은 용어가 추상 구호가 아니라 현실 도구로 보입니다

## 초보자가 자주 섞어 보는 경계

초보자가 이 개념을 어렵게 느끼는 이유는 대개 방법론 이름을 정답처럼 외우거나, 특정 도구를 쓰면 곧바로 좋은 개발 방식이 완성된다고 믿는 점입니다.

용어보다도 팀이 문제를 어떻게 쪼개고, 검토하고, 배포하고, 회고하는지 흐름을 먼저 보는 편이 중요합니다. 정의를 통째로 외우기보다 경계를 먼저 세우는 편이 훨씬 오래 갑니다.

## 작게 실험해 보면 이해가 단단해집니다

이 개념은 실제 장면에 붙여 보는 순간 기억이 오래갑니다. 아래처럼 가볍게 확인해 보면 충분합니다.

1. 작은 기능 하나를 골라 이 주제 관점에서 요구 정리, 구현, 테스트, 배포 확인 순서를 적어 봅니다.

2. 내가 자주 실수하는 지점을 떠올리고 그 실수를 줄이려면 어떤 체크리스트가 필요할지 써 봅니다.

3. 혼자 하는 프로젝트라도 작업 전 메모와 작업 후 회고를 남겨 보면 방법론 용어가 훨씬 현실적으로 다가옵니다.
