# 소프트웨어 아키텍처라는 것은 무엇일까요?

소프트웨어 아키텍처는 프로그램을 이루는 큰 구조와 그 구조가 따르는 규칙을 뜻합니다. 벽돌 하나하나를 어떻게 놓을지가 아니라, 방을 어떻게 나누고 배관과 전기를 어떻게 연결할지 정하는 일에 더 가깝습니다. 그래서 아키텍처는 화면 하나의 버튼보다, 시스템 전체가 어떤 부품으로 나뉘고 어떻게 대화하는지를 다룹니다.

초보자는 아키텍처를 너무 거대한 회사 이야기로 느낄 수 있습니다. 하지만 작은 프로젝트에도 구조는 있습니다. 화면 코드와 데이터 처리 코드를 섞을지 나눌지, 인증을 어디서 처리할지, 외부 시스템과 연결하는 코드를 어떻게 격리할지 같은 선택이 모두 아키텍처의 시작입니다. 규모가 작을 때는 잘 안 드러나지만, 기능이 늘수록 구조의 품질 차이가 크게 드러납니다.

## 왜 아키텍처가 중요한가요

같은 기능을 만들더라도 구조가 다르면 나중의 수정 비용이 달라집니다. 예를 들어 사용자 권한 검사 코드가 곳곳에 흩어져 있으면 정책이 바뀔 때 모든 화면과 API를 뒤져야 합니다. 반대로 적절한 계층과 공통 규칙으로 모아 두면 수정 범위가 훨씬 줄어듭니다. 즉, 아키텍처는 지금 만드는 기능보다 앞으로 얼마나 덜 고통스러울 것인가와 깊게 연결됩니다.

또한 아키텍처는 성능, 보안, 확장성, 운영 편의성 같은 품질 속성과도 연결됩니다. 품질 속성이라는 말이 어렵다면 기능 말고도 시스템이 갖춰야 하는 성질이라고 이해하면 됩니다. 빠른 응답, 장애 격리, 변경 용이성, 팀 협업 편의성 같은 것들이 여기에 속합니다.

## 아키텍처는 어떻게 생각하면 덜 어렵나요

처음에는 거창한 다이어그램부터 그릴 필요가 없습니다. 대신 세 가지 질문을 던지면 도움이 됩니다. 첫째, 시스템은 어떤 역할 덩어리로 나눌 수 있는가. 둘째, 그 덩어리들은 어떤 규칙으로 통신하는가. 셋째, 어떤 변경이 자주 일어날 것 같은가입니다. 이 질문에 답하는 과정이 아키텍처 설계의 핵심입니다.

예를 들어 쇼핑몰을 만든다면 화면, 주문 처리, 결제 연동, 재고 관리, 알림 발송을 한 파일에 섞을지 나눌지 결정해야 합니다. 만약 결제사가 자주 바뀔 수 있다면 결제 관련 코드를 다른 기능과 느슨하게 연결하는 편이 좋습니다. 이런 선택이 바로 아키텍처입니다.

## 초보자가 꼭 기억해야 할 점

아키텍처는 고급 개발자만 아는 그림이 아닙니다. 기능을 구현하기 전에 구조와 규칙을 조금이라도 고민하는 습관이 곧 아키텍처 감각입니다. 물론 큰 시스템일수록 더 깊은 지식이 필요하지만, 출발점은 늘 같은 질문입니다. 무엇을 어디에 둘 것인가, 왜 그렇게 나눌 것인가, 나중에 무엇이 바뀔 가능성이 큰가입니다.

이 감각을 잡아 두면 9장에서 다룰 시스템 아키텍처와 MSA 이야기도 한층 자연스럽게 이어집니다. 즉, 소프트웨어 아키텍처는 특정 유행이 아니라, 복잡해지는 코드를 오래 버티게 만드는 기본 사고방식입니다.

## 작은 프로젝트에서도 구조를 보는 습관

작은 프로젝트에서도 구조를 보는 습관은 충분히 시작할 수 있습니다. 예를 들어 외부 API 호출 코드를 화면 로직과 분리하고, 설정 값은 한곳에서 읽고, 인증 처리는 공통 계층으로 모아 두는 것만으로도 나중에 코드가 훨씬 덜 꼬입니다. 큰 다이어그램이 없어도 바뀔 가능성이 큰 부분을 분리한다는 원칙 하나만 붙잡으면 아키텍처 감각은 자랍니다. 구조는 규모가 커진 뒤에 붙이는 장식이 아니라, 작을 때부터 쌓는 습관입니다.

정리하면, 소프트웨어 아키텍처는 시스템의 큰 구조와 연결 규칙을 설계하는 일입니다. 목표는 현재 기능 구현뿐 아니라 앞으로의 변경, 성능, 보안, 확장성까지 함께 견디게 만드는 데 있습니다. 초보자도 작은 프로젝트에서부터 역할 분리와 연결 규칙을 의식하면 아키텍처 감각을 충분히 키울 수 있습니다.
