# 부록

본문을 처음부터 끝까지 읽는 것도 좋지만, 이 책은 사전처럼 다시 찾아볼 때 더 큰 힘을 발휘하도록 설계했습니다. 본문은 큰 흐름을 이해하도록 돕고, 부록은 그 흐름이 흐려졌을 때 다시 방향을 잡게 해 주는 역할을 합니다. 즉, 부록은 남는 자투리 공간이 아니라, 초보자가 실제로 가장 자주 열어 보게 되는 구조 보강판에 가깝습니다.

개발 공부를 하다 보면 두 가지 순간이 반복됩니다. 하나는 "아, 이제 조금 보이는 것 같다"는 순간이고, 다른 하나는 "갑자기 모르는 말이 한꺼번에 밀려온다"는 순간입니다. 대부분의 초보자는 두 번째 순간에서 자신이 뒤처졌다고 느낍니다. 하지만 실제로는 그 지점이 지식이 엉키는 자리일 뿐입니다. 부록은 바로 그 엉킨 실을 다시 풀기 위해 존재합니다.

## 부록을 어떻게 쓰면 좋은가

부록은 처음부터 순서대로 읽어도 되지만, 더 좋은 방법은 본문을 읽다가 막힐 때 바로 연결해 보는 것입니다. 예를 들어 네트워크 장을 읽다가 세션, 쿠키, JWT가 섞여 보이면 용어집에서 정의를 다시 확인하고, 학습 가이드에서 "어떤 순서로 다시 읽으면 좋은지"를 찾는 식입니다. 아키텍처 장에서 갑자기 난도가 높아졌다면 부록에서 "큰 구조를 읽을 때 먼저 봐야 하는 기준"을 다시 잡아 주는 식으로 활용하면 됩니다.

이 책은 초보자를 대상으로 하지만, 초보자를 가볍게 보지는 않습니다. 그래서 부록도 단순한 요약표에 머물지 않습니다. 무엇을 다시 읽어야 하는지, 어디서 자주 헷갈리는지, 어떤 순서로 손을 움직여 보면 이해가 빨라지는지까지 함께 정리했습니다. 머릿속이 흐려질 때마다 "정의"만 다시 보는 것이 아니라 "왜 이 개념이 중요했는지"까지 회복할 수 있도록 만드는 것이 목적입니다.

## 추천 읽기 경로

### 1. 완전 초보 경로

개발 경험이 거의 없고 용어가 낯설다면 다음 순서가 가장 편합니다.

1. 1장에서 개발이라는 일이 무엇인지 감을 잡습니다.
2. 2장에서 소프트웨어 종류와 화면 쪽, 서버 쪽 역할을 구분합니다.
3. 3장에서 언어와 프레임워크를 도구 상자처럼 바라보는 법을 익힙니다.
4. 4장에서 API, 비동기, 자료 구조 같은 기본 용어의 뼈대를 세웁니다.
5. 그다음 8장, 7장, 6장 순서로 통신, 데이터, 실행 환경을 읽으면 본문 난도가 훨씬 안정됩니다.

이 경로의 핵심은 한 번에 깊게 파지 않는 것입니다. 먼저 "어디에 어떤 주제가 놓여 있는지"를 지도처럼 잡고, 두 번째 독서에서 자세한 내용을 채우는 편이 훨씬 오래 갑니다.

### 2. 웹 서비스를 만들고 싶은 사람의 경로

웹 서비스를 만들고 싶은 사람은 2장, 3장, 4장, 8장, 7장, 5장 순서가 특히 좋습니다. 먼저 웹과 앱의 구분을 이해하고, 어떤 언어와 프레임워크를 써야 하는지 감을 잡은 뒤, API와 비동기, 서버 통신, 데이터베이스, 개발 방법론으로 이어 가면 실제 서비스가 어떤 층으로 이루어지는지 자연스럽게 보입니다.

이 경로를 따를 때는 "예쁘게 보이는 화면을 만드는 법"보다 "요청이 어디서 출발해 어디서 끝나는가"를 추적하는 태도가 중요합니다. 화면은 눈에 잘 보이지만, 서비스가 실제로 움직이는 핵심은 데이터 흐름과 서버 쪽 구조에 있기 때문입니다.

### 3. 백엔드와 인프라 쪽이 궁금한 사람의 경로

백엔드, 서버, 인프라에 더 끌린다면 2장, 4장, 7장, 8장, 6장, 9장, 10장 순서가 좋습니다. 이 순서는 요청과 데이터, 운영체제, 구조 설계, 클라우드까지 이어지기 때문에 서버 개발이 단순히 코드만 쓰는 일이 아니라는 점을 분명하게 보여 줍니다.

이 경로에서 중요한 질문은 "서버는 왜 필요한가", "데이터는 왜 그냥 파일에 저장하지 않는가", "트래픽이 늘면 무엇이 먼저 버티지 못하는가"입니다. 이 질문을 붙들고 읽으면 뒤쪽 장에서 나오는 로드밸런서, 캐시, 컨테이너, 서버리스도 훨씬 덜 위압적으로 느껴집니다.

### 4. 전체를 빠르게 복습하고 싶은 사람의 경로

이미 한 번 읽었거나, 면접이나 개괄 정리가 목적이라면 각 장의 `index.md`만 먼저 훑고, 막히는 개념만 본문으로 들어가는 방식이 좋습니다. 이때 부록의 용어집을 옆에 열어 두면 속도가 빨라집니다. 즉, 처음 독서는 흐름 중심, 두 번째 독서는 연결 중심, 세 번째 독서는 약점 보완 중심으로 접근하면 됩니다.

## 메모를 남기는 방법

개발 책은 읽는 순간보다 덮은 뒤가 더 중요합니다. 읽을 때 이해한 것 같다가도, 다음 날 다시 보면 용어가 흐릿해지는 경험을 자주 하게 됩니다. 그래서 한 절을 읽고 나면 세 줄 정도만 남겨 두는 습관이 좋습니다.

- 이 절이 답하려는 질문은 무엇이었는가
- 여기서 새로 분명해진 용어는 무엇인가
- 아직도 내가 잘 모르는 것은 무엇인가

이 세 줄만 남겨도 다시 펼쳤을 때 복구 속도가 크게 달라집니다. 특히 "아직 잘 모르는 것"을 적는 습관은 중요합니다. 초보자는 모르는 것을 감추려고 하기 쉬운데, 실제 공부는 모르는 부분의 윤곽을 잡는 순간부터 빨라집니다.

## AI와 함께 이 책을 읽는 법

AI 도구는 초보자의 속도를 올려 줄 수 있습니다. 낯선 용어를 바로 물어볼 수 있고, 예시를 더 요청할 수도 있으며, 코드 조각도 빠르게 확인할 수 있습니다. 하지만 AI가 답했다고 해서 이해가 생기는 것은 아닙니다. 특히 비슷한 말의 경계가 중요한 주제에서는 AI가 그럴듯하지만 흐릿한 답을 줄 때가 많습니다.

그래서 AI와 함께 읽을 때는 질문 방식이 중요합니다. "설명해 줘"만 반복하기보다 아래처럼 물어보는 편이 훨씬 좋습니다.

- 이 개념을 초보자가 어디서 가장 많이 헷갈리는지 알려 주세요.
- 이 용어가 사람이 하는 일인지, 코드 구조인지, 실행 환경인지 분류해 주세요.
- 이 개념이 실제 서비스에서 언제 문제로 드러나는지 예를 들어 주세요.
- 비슷한 용어 두 개를 표로 비교하지 말고, 같은 상황에서 어떻게 다르게 보이는지 설명해 주세요.

즉, AI는 정답 기계가 아니라 질문 정리 도구로 쓰는 편이 훨씬 효과적입니다.

## 막힐 때 다시 잡는 기준

책을 읽다가 갑자기 난도가 튀는 느낌이 들면 보통 세 가지 중 하나입니다. 첫째, 용어 정의가 흐릿한 상태로 다음 절로 넘어갔을 때입니다. 둘째, 역할 구분이 안 된 상태에서 여러 층의 개념이 섞였을 때입니다. 셋째, 실제 장면 없이 정의만 읽어서 개념이 몸에 붙지 않았을 때입니다.

이때는 억지로 더 읽기보다 다음 순서로 다시 잡는 것이 좋습니다.

1. 먼저 이 절의 질문이 무엇인지 한 줄로 말해 봅니다.
2. 다음으로 이 개념이 화면, 서버, 데이터, 운영체제, 네트워크, 인프라 중 어디에 가까운지 분류합니다.
3. 마지막으로 실제 서비스 한 장면을 붙여 봅니다. 예를 들어 로그인, 장바구니, 알림, 업로드 같은 익숙한 기능에 얹어 보는 것입니다.

이 세 단계만 해도 막연한 공포가 많이 줄어듭니다. 대부분의 혼란은 지식 부족 자체보다 범주 혼합에서 생기기 때문입니다.

## 부록 구성 안내

이 부록은 크게 두 부분으로 보면 됩니다. 하나는 `핵심 용어집`입니다. 이곳에서는 본문 곳곳에서 반복해서 나오는 용어를 짧고 단단하게 다시 잡아 줍니다. 다른 하나는 `참고 자료와 검증 원칙`입니다. 이름은 다소 딱딱하지만, 실제 내용은 훨씬 실용적입니다. 공식 문서를 겁내지 않고 읽는 법, AI 답변을 확인하는 기준, 공부가 막힐 때 다시 움직이는 방법, 작은 프로젝트로 연결하는 방식까지 한꺼번에 정리했습니다.

이 책은 한 번 읽고 끝나는 종류의 책이 아닙니다. 개발 자체가 층이 많은 작업이기 때문에, 같은 주제를 다른 시점에서 다시 읽을수록 이해가 깊어집니다. 그래서 부록도 마지막에만 있는 부가물이 아니라, 중간중간 계속 돌아오도록 설계된 재정비 구역이라고 생각하면 가장 잘 맞습니다.
