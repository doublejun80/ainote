# 프론트엔드 개발 언어는 무엇인가요?

프론트엔드 개발을 말할 때 가장 먼저 알아야 할 것은, 엄밀히 말해 한 가지 언어만 있는 것이 아니라는 점입니다. 보통은 HTML, CSS, JavaScript 세 가지를 기본 축으로 이야기합니다. 여기에 TypeScript가 자주 함께 등장합니다.

HTML은 화면의 구조를 잡는 언어입니다. 제목, 문단, 버튼, 입력창, 표, 이미지 같은 요소가 화면에 어떤 의미로 배치되는지를 표현합니다. CSS는 그 구조를 어떻게 보이게 할지 결정합니다. 색, 글꼴, 간격, 배치, 반응형 디자인이 여기에 들어갑니다. JavaScript는 화면에 동작을 부여합니다. 버튼을 눌렀을 때 무슨 일이 일어나야 하는지, 서버에서 데이터를 받아오면 어떻게 보여 줄지, 입력이 바뀌면 화면을 어떻게 갱신할지를 처리합니다.

## 왜 세 가지가 함께 등장하나

초보자는 종종 "프론트엔드 언어는 자바스크립트인가요?"라고 묻습니다. 어느 정도는 맞지만, 정확히는 HTML과 CSS와 JavaScript가 함께 프론트엔드의 기본 뼈대를 이룹니다. 구조, 모양, 동작이 서로 다른 역할을 맡고 있기 때문입니다.

이 구분을 알면 프론트엔드에서 생기는 문제를 보는 눈도 달라집니다. 버튼이 아예 안 보이면 HTML이나 CSS 문제일 수 있고, 눌렀는데 동작이 안 되면 JavaScript 문제일 수 있습니다. 반응형 레이아웃이 깨지면 CSS 쪽을 먼저 의심할 수 있습니다.

## TypeScript는 또 무엇인가

TypeScript는 JavaScript를 더 안전하고 구조적으로 다루기 쉽게 만든 확장 언어라고 생각하면 됩니다. 자바스크립트는 매우 유연해서 빠르게 시작하기 좋지만, 규모가 커지면 데이터의 형태가 헷갈리거나 실수를 늦게 발견하는 문제가 생길 수 있습니다. TypeScript는 변수와 함수의 데이터 형태를 더 분명하게 적게 해 이런 문제를 줄이는 데 도움을 줍니다.

그래서 실무 프론트엔드 프로젝트에서는 TypeScript를 함께 쓰는 경우가 많습니다. 초보자는 처음부터 모든 타입 개념을 깊게 알 필요는 없지만, 자바스크립트 위에 안정성을 더하는 도구라는 정도는 알아두면 좋습니다.

## 프론트엔드 개발은 화면만 예쁘게 만드는 일인가

아닙니다. 프론트엔드 개발은 화면을 그리는 것 이상입니다. 사용자의 행동에 반응하고, 상태를 기억하고, 서버와 데이터를 주고받고, 오류를 친절하게 안내해야 합니다. 그래서 언어를 배운다는 것은 문법만 외우는 것이 아니라, 구조와 상태와 이벤트를 함께 이해하는 일입니다.

## 핵심만 다시 정리하면

프론트엔드의 기본 언어는 HTML, CSS, JavaScript입니다. HTML은 구조, CSS는 모양, JavaScript는 동작을 담당합니다. TypeScript는 그 위에 안정성과 구조화를 더하는 도구라고 이해하면 됩니다.

## 현업 장면으로 바꾸면 이렇게 보입니다

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 프론트엔드, 모바일, 서버 중 어디에 집중할지 정할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

결국 이 개념을 이해한다는 것은 도구 선택이 취향이 아니라 맥락 문제라는 점이 드러납니다

## 여기서 많이 생기는 오해

이 개념이 갑자기 어려워지는 순간은 보통 가장 좋은 언어 하나만 찾으면 끝난다고 생각하거나, 프레임워크 이름을 언어처럼 받아들이는 점입니다.

문법, 실행 환경, 생태계, 팀 숙련도는 서로 다른 축이라는 사실을 나눠 봐야 합니다. 그러면 비슷한 용어를 만나도 같은 상자에 모두 넣어 버리는 실수를 줄일 수 있습니다.

## 읽고 끝내지 않으려면 이렇게 해 보세요

이 개념을 내 것으로 만드는 가장 빠른 방법은 작은 실험입니다. 거창한 프로젝트가 아니라도 괜찮습니다.

1. 같은 기능을 만들 때 이 개념이 무엇을 더 쉽게 해 주는지 한 줄씩 비교해 봅니다.

2. 공식 소개 문서에서 이 개념이 주로 어떤 문제를 해결하는지 찾아 적어 봅니다.

3. 내가 만들고 싶은 서비스 기준으로 이 개념이 왜 필요한지 또는 왜 아직 과한지 판단해 봅니다.

## 이 절을 단독 지식으로 두지 않는 방법

이 개념을 이해해 두면 뒤쪽 장을 읽을 때 새 용어가 나와도 덜 위압적으로 느껴집니다. 실제로 4장의 핵심 개발 개념, 5장의 팀 개발 흐름, 10장의 현대 인프라 선택에서 같은 기준이 다시 필요합니다.

결국 이 절의 목적은 지식을 하나 더 추가하는 것이 아니라, 다음에 나올 개념의 자리를 미리 만들어 두는 데 있습니다.
