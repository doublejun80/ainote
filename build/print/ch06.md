# 6장. 컴퓨터 구조와 운영체제의 이해

개발을 조금 하다 보면 갑자기 이상한 일이 생깁니다. 분명 코드는 맞는 것 같은데 프로그램이 느려지고, 메모리가 부족하다는 오류가 나고, 동시에 여러 작업을 돌리자 꼬이기 시작합니다. 이때 초보자는 종종 언어 문법만 더 파고들려고 합니다. 하지만 문제의 일부는 코드 위가 아니라 코드 아래, 즉 컴퓨터 구조와 운영체제에서 올라옵니다.

6장은 바로 그 아래층을 이해하는 장입니다. 컴퓨터가 어떤 부품으로 이루어져 있는지, 운영체제가 왜 필요한지, 프로그램이 어떻게 실행 단위로 바뀌는지, 메모리는 왜 여러 단계로 나뉘는지 설명합니다. 이 장을 읽는 목적은 운영체제 시험을 치르기 위해서가 아니라, 실제 개발에서 느린 이유와 충돌하는 이유를 해석할 수 있게 되는 데 있습니다.

운영체제와 컴퓨터 구조는 추상적으로 보이지만, 사실 개발자의 매일과 연결됩니다. 앱이 갑자기 종료되는 문제, 서버가 동시에 많은 요청을 처리하는 방식, 멀티스레드 버그, 캐시 적중률, 메모리 부족, 파일 시스템, 프로세스 격리 같은 개념은 모두 이 장의 내용과 이어집니다. 즉, 이 장은 저수준 지식을 자랑하기 위한 장이 아니라, 프로그램의 현실적인 움직임을 이해하기 위한 기반입니다.

## 이 장에서 중요한 태도

처음부터 모든 하드웨어 용어를 완벽하게 외우려 하지 않아도 됩니다. 대신 내가 작성한 코드가 결국 CPU, 메모리, 저장장치, 운영체제를 거쳐 실행된다는 흐름만 선명하게 잡으면 됩니다. 그 흐름이 잡히면 디버깅과 성능 문제를 보는 시야가 한층 넓어집니다.

## 컴퓨터 운영체제의 역사

운영체제의 역사를 배우는 이유는 오래된 연도를 외우기 위해서가 아닙니다. 지금 우리가 당연하게 여기는 파일 저장, 여러 프로그램 동시 실행, 사용자 계정, 앱 설치, 네트워크 연결 같은 기능이 왜 운영체제의 기본 역할이 되었는지 이해하기 위해서입니다. 역사를 보면 운영체제가 어떤 문제를 해결해 왔는지가 보입니다.

초기의 컴퓨터는 지금처럼 개인이 자유롭게 여러 프로그램을 띄우는 기계가 아니었습니다. 한 번에 하나의 작업을 길게 수행하는 배치 처리 방식이 중심이었습니다. 사용자는 작업을 예약하고 기다렸고, 컴퓨터는 그 작업을 차례로 실행했습니다. 이 시기에는 효율적으로 작업을 순서대로 돌리는 것이 중요했습니다.

### 여러 사용자가 함께 쓰기 시작하며 바뀐 점

컴퓨터가 더 널리 쓰이면서 여러 사람이 한 기계를 나누어 쓰는 문제가 중요해졌습니다. 이때 등장한 것이 시분할 개념입니다. 운영체제가 짧은 시간 조각을 나눠 여러 작업에 번갈아 CPU를 배정하면서, 각 사용자는 마치 자신만 컴퓨터를 쓰는 것처럼 느끼게 되었습니다. 오늘날 멀티태스킹의 감각은 여기서 이어집니다.

이후 개인용 컴퓨터 시대가 오면서 운영체제는 전문가용 제어 소프트웨어를 넘어 일반 사용자의 작업 환경이 되었습니다. 파일 탐색기, 그래픽 인터페이스, 마우스, 윈도우 개념이 중요해졌고, 사용 편의성과 장치 지원 범위도 커졌습니다. 즉, 운영체제는 단지 계산 자원을 분배하는 시스템에서 사람과 컴퓨터를 연결하는 작업 공간으로 확장되었습니다.

### 인터넷과 모바일 시대에는 무엇이 달라졌나요

인터넷이 보편화되면서 운영체제는 네트워크를 전제로 움직이게 되었습니다. 보안, 사용자 권한, 네트워크 스택, 원격 업데이트, 브라우저 환경이 중요해졌습니다. 모바일 시대에는 배터리 관리, 터치 인터페이스, 앱 권한 통제, 앱 샌드박스가 중요한 기준이 되었습니다. 최근에는 클라우드와 컨테이너 환경이 커지면서, 운영체제가 직접 드러나지 않더라도 격리와 자원 관리 기능이 더 중요해졌습니다.

즉, 운영체제의 역사는 컴퓨터가 어떤 문제를 중심으로 발전해 왔는지를 보여 줍니다. 한 기계에서 한 작업만 처리하던 시대에서, 수많은 사용자와 장치와 네트워크와 서비스를 동시에 다루는 시대로 오면서 운영체제의 책임도 점점 넓어졌습니다.

### 초보자가 여기서 얻어야 할 감각

운영체제는 처음부터 지금처럼 완성된 것이 아니었습니다. 사용자가 늘고, 장치가 다양해지고, 보안 요구가 커지고, 서비스 형태가 복잡해질 때마다 새로운 역할이 더해졌습니다. 그래서 오늘날 운영체제를 이해한다는 것은 단지 운영체제 프로그램 하나를 아는 것이 아니라, 현대 컴퓨팅 환경이 요구하는 조정자 역할을 이해하는 것과 같습니다.

이 관점을 잡아 두면 앞으로 배울 커널, 프로세스, 메모리, 스레드 같은 개념도 따로 떠다니지 않습니다. 모두 운영체제가 역사적으로 맡게 된 책임의 일부로 연결됩니다.

### 핵심만 다시 정리하면

운영체제의 역사는 컴퓨터가 해결해야 할 문제가 어떻게 확장되었는지를 보여 줍니다. 배치 처리에서 시분할, 개인용 컴퓨터, 인터넷, 모바일, 클라우드 시대로 오면서 운영체제는 자원 관리뿐 아니라 사용자 환경, 보안, 네트워크, 격리까지 책임지게 되었습니다. 역사를 이해하면 운영체제의 현재 역할도 훨씬 자연스럽게 보입니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 컴퓨터 구조, 운영체제, 메모리와 동시성와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 프로그램이 왜 느려지는지, 어디서 병목이 생기는지 추적할 때 이 개념이 다시 등장합니다.

그래서 이 절의 설명은 곧 디버깅할 때 코드만 보는 습관에서 한 단계 더 내려갈 수 있습니다

### 읽다가 흔들리는 지점

이 주제에서 가장 흔한 오해는 운영체제와 하드웨어 이야기를 언어 문법과 별개인 어려운 이론으로만 보는 점입니다.

코드가 결국 CPU, 메모리, 저장장치, 운영체제를 지나 실행된다는 흐름을 붙잡으면 개별 용어가 훨씬 쉬워집니다. 이 기준만 있어도 뒤 장에서 같은 말을 다시 만나도 훨씬 덜 흔들립니다.

### 손으로 확인해 보면 더 빨리 남습니다

이 개념은 읽는 것만으로는 쉽게 손에 잡히지 않습니다. 아주 작은 확인만 해도 본문이 훨씬 입체적으로 보입니다.

1. 작업 관리자나 리소스 모니터를 열고 이 주제와 관련된 정보가 어디에서 보이는지 찾아봅니다.

2. 프로그램 하나를 실행하고 메모리 사용량, 프로세스 수, CPU 사용량이 어떻게 바뀌는지 관찰해 봅니다.

3. 느려짐이나 멈춤이 생겼을 때 코드 문제인지 실행 환경 문제인지 구분하는 질문을 세 개 적어 봅니다.

### 책 전체 흐름 속에서의 자리

이 개념은 여기서 끝나는 개념이 아닙니다. 이 절에서 잡은 감각은 7장의 데이터 처리 성능, 8장의 네트워크 처리, 10장의 컨테이너와 인프라 운영로 이어집니다.

따라서 다음 절을 읽을 때는 "이 개념이 지금 설명하는 층은 어디인가"를 계속 추적해 보세요. 그 습관이 전체 책을 훨씬 쉽게 만듭니다.

## 컴퓨터는 어떤 구성 요소로 되어 있나요?

컴퓨터를 이해하는 가장 쉬운 방법은 하나의 똑똑한 상자로 보는 대신 역할이 다른 부품들의 협업으로 보는 것입니다. 우리가 작성한 프로그램은 결국 여러 하드웨어 요소를 거치며 실행됩니다. 그래서 CPU, 메모리, 저장장치, 입력 장치, 출력 장치, 네트워크 장치가 각각 무슨 일을 하는지 알면 프로그램이 느려지거나 멈추는 이유를 훨씬 현실적으로 이해할 수 있습니다.

가장 중심에는 CPU가 있습니다. CPU는 명령을 읽고 계산하고 제어하는 부품입니다. 흔히 컴퓨터의 두뇌라고 부르지만, CPU 혼자 모든 것을 해결하는 것은 아닙니다. 계산은 빠르지만 저장 공간은 거의 없고, 필요한 데이터를 메모리와 저장장치에서 계속 받아와야 합니다.

### 메모리와 저장장치는 무엇이 다를까요

메모리는 지금 실행 중인 프로그램이 바로 사용해야 하는 데이터를 잠시 올려 두는 작업대입니다. 빠르지만 비싸고 용량이 한정되어 있습니다. 전원이 꺼지면 일반적으로 내용도 사라집니다. 반면 저장장치는 파일과 프로그램을 오래 보관하는 창고에 가깝습니다. SSD나 HDD가 대표적이며, 메모리보다 느리지만 훨씬 많은 데이터를 저장할 수 있습니다.

이 차이를 이해하면 왜 프로그램 실행 전에 디스크에 있던 파일이 메모리로 올라오는지 자연스럽게 보입니다. 저장장치는 오래 보관하는 곳, 메모리는 지금 당장 일하는 곳이라는 감각이 중요합니다.

### 나머지 부품들은 어떤 역할을 하나요

입력 장치는 키보드, 마우스, 카메라, 센서처럼 컴퓨터에 정보를 넣는 통로입니다. 출력 장치는 모니터, 스피커, 프린터처럼 결과를 보여 주는 통로입니다. 네트워크 장치는 다른 컴퓨터와 데이터를 주고받는 길을 담당합니다. 또한 각 부품을 서로 연결하고 데이터가 오갈 수 있게 해 주는 통로 개념으로 버스를 이해하면 좋습니다. 이름이 생소해도 본질은 부품 간 이동 경로입니다.

최근에는 GPU도 중요한 역할을 맡습니다. 원래는 그래픽 처리에 강한 장치였지만, 대량의 병렬 계산에 유리해 머신러닝과 영상 처리에서도 널리 쓰입니다. 즉, 현대 컴퓨터는 CPU 하나가 전부 하는 구조가 아니라, 역할별로 특화된 장치들이 함께 일하는 구조입니다.

### 초보자는 어떤 그림을 떠올리면 좋을까요

한 문장으로 정리하면 이렇습니다. CPU는 계산하고, 메모리는 지금 필요한 것을 가까이 두고, 저장장치는 오래 보관하고, 입출력 장치는 바깥세상과 연결하고, 운영체제는 이 모든 자원을 조정합니다. 이 그림만 머릿속에 있어도 이후에 나올 메모리 부족, I/O 지연, 프로세스 스케줄링, 캐시 같은 개념을 붙잡기가 훨씬 쉬워집니다.

즉, 컴퓨터는 하나의 마법 상자가 아니라 역할을 나눈 시스템입니다. 개발자는 이 분업 구조를 이해할수록 코드가 실제로 어디서 비용을 쓰는지 더 잘 판단할 수 있습니다.

### 핵심만 다시 정리하면

컴퓨터는 CPU, 메모리, 저장장치, 입출력 장치, 네트워크 장치 같은 서로 다른 역할의 부품으로 구성됩니다. CPU가 계산을 맡더라도 메모리와 저장장치, I/O 없이는 아무 일도 할 수 없습니다. 개발자가 이 구조를 이해하면 프로그램의 실행 흐름과 성능 문제를 훨씬 더 현실적으로 해석할 수 있습니다.

### 실제로 만들 때는 이런 선택으로 이어집니다

이 개념은 정의 하나로 끝나는 주제가 아니라, 실제 선택의 기준이 되는 개념입니다. 특히 프로세스와 스레드 중 어떤 실행 단위를 이해해야 하는지 정리할 때 이 절의 내용이 곧바로 판단 기준이 됩니다.

이 관점을 잡아 두면 멀티스레드와 메모리 이야기가 갑자기 튀어나와도 맥락을 놓치지 않습니다

### 초보자가 자주 섞어 보는 경계

초보자가 이 개념을 어렵게 느끼는 이유는 대개 운영체제와 하드웨어 이야기를 언어 문법과 별개인 어려운 이론으로만 보는 점입니다.

코드가 결국 CPU, 메모리, 저장장치, 운영체제를 지나 실행된다는 흐름을 붙잡으면 개별 용어가 훨씬 쉬워집니다. 정의를 통째로 외우기보다 경계를 먼저 세우는 편이 훨씬 오래 갑니다.

## 왜 모든 데이터를 메모리에 올리지 못하나요?

초보자는 저장장치도 있고 메모리도 있는데, 왜 필요한 걸 전부 메모리에 올려 두지 않느냐고 묻곤 합니다. 가장 직접적인 이유는 메모리가 빠르지만 비싸고, 용량이 제한되어 있기 때문입니다. 저장장치에 수백 기가바이트, 수테라바이트를 쉽게 넣을 수 있다고 해서, 그 모든 데이터를 같은 규모의 메모리로 항상 들고 있을 수는 없습니다.

또 하나의 이유는 지금 당장 쓰지 않는 데이터까지 모두 올려 둘 필요가 없기 때문입니다. 프로그램은 한 번에 전체 데이터를 다 쓰지 않고, 현재 작업에 필요한 일부만 집중적으로 사용합니다. 이를 일하는 범위라고 이해하면 편합니다. 즉, 메모리는 전체 창고가 아니라 지금 손에 들고 작업하는 책상입니다.

### 메모리에 다 올리면 오히려 어떤 문제가 생길까요

메모리를 많이 쓰는 프로그램이 동시에 여러 개 실행되면 서로 자리를 차지하게 됩니다. 운영체제는 모든 프로그램이 공정하게 자원을 쓰도록 관리해야 하므로, 무조건 전부 메모리에 올리는 전략은 현실적이지 않습니다. 또한 메모리는 전원이 꺼지면 내용이 사라지는 특성이 있으므로, 영구 보관 용도로도 적합하지 않습니다.

대용량 데이터를 다루는 서비스에서는 더 분명합니다. 예를 들어 쇼핑몰의 주문 기록 전체, 동영상 파일 전체, 수많은 로그 파일을 매번 메모리에 다 올려 두는 것은 비효율적입니다. 필요한 부분만 읽고, 자주 쓰는 것만 메모리에 남기고, 나머지는 저장장치에 두는 편이 훨씬 현실적입니다.

### 그래서 운영체제는 어떻게 해결하나요

운영체제와 프로그램은 필요한 데이터만 점진적으로 메모리에 올리는 방향으로 움직입니다. 파일을 읽을 때도 전체를 통째로 다루기보다 일부씩 읽을 수 있고, 데이터베이스도 필요한 결과만 가져오려 합니다. 자주 쓰는 데이터는 캐시에 남겨 두고, 한동안 안 쓰는 데이터는 뒤로 미룹니다.

이 감각은 웹 개발이나 앱 개발에서도 중요합니다. 화면에 한 번에 다 보여 주지 않아도 되는 목록을 페이지 단위로 나누거나, 이미지도 필요한 시점에만 불러오는 이유가 여기에 있습니다. 즉, 메모리 한계는 운영체제만의 문제가 아니라 애플리케이션 설계에도 영향을 줍니다.

### 초보자가 꼭 기억할 점

메모리 부족은 단순히 컴퓨터가 약해서 생기는 문제가 아닙니다. 빠르고 비싼 자원을 제한된 환경에서 여러 프로그램이 나눠 쓰는 구조 때문에 생깁니다. 그래서 좋은 프로그램은 필요한 만큼만 메모리를 쓰고, 쓰지 않는 것은 놓아주며, 큰 데이터를 한꺼번에 다루지 않도록 설계합니다.

이 관점을 이해하면 나중에 캐시, 가상 메모리, 페이징, 스트리밍, 페이지네이션 같은 개념도 모두 같은 축 위에 놓이게 됩니다. 결국 핵심은 모든 것을 가까이에 둘 수 없기 때문에, 무엇을 언제 가까이에 둘지 결정해야 한다는 것입니다.

### 핵심만 다시 정리하면

모든 데이터를 메모리에 올리지 못하는 이유는 메모리가 빠르지만 비싸고 제한된 자원이기 때문입니다. 또한 프로그램은 전체 데이터가 아니라 지금 필요한 일부만 주로 사용합니다. 따라서 운영체제와 애플리케이션은 필요한 것만 메모리에 두고 나머지는 저장장치에 두는 방향으로 설계됩니다.

## 메모리는 왜 캐시 메모리, 메인 메모리, 가상 메모리 나뉘어 사용되나요?

메모리가 여러 단계로 나뉘는 이유는 한 가지 자원으로 속도와 용량과 가격을 모두 만족시키기 어렵기 때문입니다. 가장 빠른 메모리는 비싸고 용량이 작고, 용량이 큰 저장 공간은 상대적으로 느립니다. 그래서 컴퓨터는 자주 쓰는 것은 더 가까운 곳에 두고, 덜 쓰는 것은 더 멀지만 넓은 곳에 두는 계층 구조를 사용합니다.

캐시 메모리는 CPU 바로 가까이에 있어 매우 빠르지만 아주 작습니다. 메인 메모리, 즉 우리가 흔히 말하는 RAM은 그보다 느리지만 훨씬 많은 데이터를 담을 수 있습니다. 가상 메모리는 운영체제가 메모리를 더 넓게 쓰는 것처럼 보이게 해 주는 방식으로, 필요에 따라 저장장치의 일부를 보조 공간처럼 활용합니다. 이 셋은 경쟁 관계가 아니라 서로 다른 속도와 역할을 가진 단계들입니다.

### 캐시 메모리는 왜 필요할까요

CPU는 매우 빠르게 계산하지만, 필요한 데이터를 메인 메모리에서 매번 기다리면 발이 묶일 수 있습니다. 그래서 최근에 자주 쓴 값이나 곧 다시 쓸 가능성이 높은 값을 CPU 가까이에 잠깐 두는 것이 캐시입니다. 캐시가 잘 맞으면 CPU는 훨씬 적은 대기 시간으로 작업할 수 있습니다.

초보자는 캐시를 단순히 임시 저장 정도로 생각하지만, 성능에서 매우 큰 차이를 만들 수 있습니다. 같은 계산이라도 데이터 접근 방식에 따라 캐시 효율이 달라지기 때문에, 알고리즘과 코드 구조가 실제 속도에 영향을 주는 이유 중 하나가 됩니다.

### 가상 메모리는 무엇을 해결하나요

가상 메모리는 프로그램마다 넓고 연속된 메모리를 쓰는 것처럼 보이게 해 주는 추상화입니다. 이 덕분에 각 프로그램은 다른 프로그램의 메모리를 직접 건드리지 않고, 운영체제는 필요한 부분만 실제 메모리에 올려 관리할 수 있습니다. 메모리가 부족할 때는 일부 내용을 저장장치 쪽으로 밀어내기도 합니다.

다만 가상 메모리가 있다고 해서 물리 메모리 부족이 사라지는 것은 아닙니다. 실제 RAM이 너무 부족한데 저장장치에 자꾸 밀어내며 버티기 시작하면 성능이 크게 떨어질 수 있습니다. 즉, 가상 메모리는 마법처럼 메모리를 무한히 만들어 주는 것이 아니라, 제한된 메모리를 더 유연하고 안전하게 쓰게 하는 장치입니다.

### 초보자는 어떤 그림으로 기억하면 좋을까요

가장 빠른 책상 서랍이 캐시, 넓은 작업 책상이 메인 메모리, 창고와 작업대를 오가며 관리하는 시스템이 가상 메모리라고 떠올리면 도움이 됩니다. 자주 쓰는 것은 제일 가까이, 지금 쓰는 것은 작업대에, 당장 필요 없는 것은 멀리 두는 구조입니다.

이 구조를 이해하면 왜 대용량 프로그램에서 성능 차이가 생기는지, 왜 메모리 부족 상태에서 컴퓨터가 갑자기 느려지는지, 왜 운영체제가 메모리 사용량을 중요하게 관리하는지 자연스럽게 연결됩니다.

### 핵심만 다시 정리하면

캐시, 메인 메모리, 가상 메모리는 속도와 용량과 비용의 균형을 맞추기 위해 존재하는 메모리 계층입니다. 캐시는 매우 빠른 가까운 저장소, 메인 메모리는 실제 작업 공간, 가상 메모리는 그 공간을 더 유연하게 보이게 하는 관리 방식입니다. 컴퓨터는 이 계층 구조 덕분에 제한된 자원으로도 복잡한 프로그램을 실행할 수 있습니다.

## 여러 프로그램이 동시에 실행되는 원리는 무엇인가요?

우리는 음악을 들으면서 브라우저를 켜고, 메신저를 띄우고, 코드를 작성합니다. 겉으로 보면 모든 프로그램이 동시에 실행되는 것처럼 보입니다. 실제로는 운영체제가 CPU 시간을 아주 짧게 나누어 여러 작업에 번갈아 배정하면서 이런 착시를 만들어 냅니다. 이것이 멀티태스킹의 기본 감각입니다.

CPU 코어가 하나뿐인 환경에서는 진짜 물리적 동시 실행이 아니라 매우 빠른 교대 실행이 중심입니다. 운영체제는 어떤 작업을 잠깐 실행시키고, 다음 작업으로 바꾸고, 다시 돌아오는 과정을 매우 빠르게 반복합니다. 사용자는 그 속도가 충분히 빠르면 여러 프로그램이 동시에 도는 것처럼 느끼게 됩니다.

### 문맥 전환과 스케줄링은 무엇인가요

어떤 작업을 실행하다가 다른 작업으로 바꿀 때는 현재 상태를 저장하고, 다음 작업의 상태를 불러와야 합니다. 이를 문맥 전환이라고 부릅니다. 상태에는 어떤 명령까지 실행했는지, 어떤 값들을 쓰고 있었는지 같은 정보가 들어 있습니다. 운영체제는 이런 전환을 관리하면서 전체 시스템이 고르게 움직이도록 합니다.

스케줄링은 누구에게 CPU를 얼마나 줄지 정하는 일입니다. 대화형 프로그램은 사용자의 입력에 빨리 반응해야 하고, 백그라운드 작업은 조금 늦어도 괜찮을 수 있습니다. 운영체제는 우선순위, 대기 시간, 공정성 같은 요소를 고려해 CPU 시간을 분배합니다.

### 멀티코어 시대에는 무엇이 더해지나요

요즘 컴퓨터는 CPU 코어가 여러 개인 경우가 많아, 일부 작업은 실제로 동시에 실행될 수 있습니다. 하지만 그렇다고 해서 스케줄링 문제가 사라지는 것은 아닙니다. 어떤 코어에 어떤 작업을 보낼지, 공유 자원은 어떻게 보호할지, 동시에 실행되는 작업끼리 어떻게 간섭을 줄일지도 여전히 중요합니다.

즉, 여러 프로그램이 동시에 실행되는 느낌은 시분할과 스케줄링, 그리고 멀티코어 하드웨어가 함께 만든 결과입니다. 개발자는 이 구조를 이해할수록 왜 응답성 문제가 생기는지, 왜 백그라운드 작업이 전체 시스템을 느리게 만들 수 있는지 잘 파악하게 됩니다.

### 초보자는 무엇을 기억하면 좋을까요

핵심은 운영체제가 CPU를 빌려주는 관리자라는 점입니다. 프로그램이 많아질수록 운영체제는 누가 먼저 실행될지, 얼마나 오래 실행될지, 언제 멈추고 바꿀지를 계속 결정합니다. 그래서 프로그램을 작성할 때도 긴 작업을 한 번에 독점하지 않도록 설계하는 것이 중요합니다.

이 관점을 잡고 나면 다음 절의 운영체제 역할, 프로세스와 스레드 차이, 동시성 문제도 모두 하나의 흐름으로 이어집니다. 결국 동시에 실행된다는 말 뒤에는 언제나 운영체제의 자원 배분이 숨어 있습니다.

### 핵심만 다시 정리하면

여러 프로그램이 동시에 실행되는 것처럼 보이는 이유는 운영체제가 CPU 시간을 짧게 나누어 번갈아 배정하기 때문입니다. 이 과정에서 문맥 전환과 스케줄링이 핵심 역할을 합니다. 멀티코어 환경에서는 실제 동시 실행도 가능하지만, 여전히 운영체제의 조정이 필수입니다.

코드가 결국 CPU, 메모리, 저장장치, 운영체제를 지나 실행된다는 흐름을 붙잡으면 개별 용어가 훨씬 쉬워집니다. 이 기준만 있어도 뒤 장에서 같은 말을 다시 만나도 훨씬 덜 흔들립니다.

3. 느려짐이나 멈춤이 생겼을 때 코드 문제인지 실행 환경 문제인지 구분하는 질문을 세 개 적어 봅니다.

## 운영체제는 무슨 일을 하나요?

운영체제는 컴퓨터의 자원을 관리하고, 프로그램이 하드웨어를 직접 다루지 않아도 되게 중간에서 조정해 주는 시스템 소프트웨어입니다. 초보자는 운영체제를 윈도우나 macOS 같은 화면 환경 정도로만 생각하기 쉽지만, 실제 핵심은 보이지 않는 자원 관리에 있습니다. CPU 시간, 메모리, 파일, 장치, 네트워크, 사용자 권한을 조정하는 것이 운영체제의 본업입니다.

운영체제가 없다면 프로그램은 화면을 그리는 일부터 키보드 입력 처리, 저장장치 접근, 네트워크 장치 제어까지 모두 직접 다뤄야 합니다. 그렇게 되면 프로그램마다 하드웨어 제어 방식이 뒤엉키고, 하나의 실수가 시스템 전체를 쉽게 망가뜨릴 수 있습니다. 운영체제는 이런 혼란을 막기 위해 공통 규칙과 인터페이스를 제공합니다.

### 운영체제가 맡는 대표적인 일들

첫째는 프로세스 관리입니다. 어떤 프로그램이 실행 중인지, CPU를 누구에게 얼마나 줄지, 종료된 작업을 어떻게 정리할지를 관리합니다. 둘째는 메모리 관리입니다. 각 프로그램이 자기 공간 안에서 안전하게 메모리를 쓰도록 돕고, 부족한 자원을 효율적으로 분배합니다.

셋째는 파일 시스템 관리입니다. 파일을 어디에 저장하고, 누가 읽고 쓸 수 있는지, 디렉터리를 어떻게 구성할지 운영체제가 결정합니다. 넷째는 장치 관리입니다. 프린터, 키보드, 디스크, 네트워크 카드 같은 장치를 직접 다루는 복잡함을 운영체제가 흡수해 줍니다. 다섯째는 보안과 권한 관리입니다. 어떤 사용자가 어떤 파일과 기능에 접근할 수 있는지 통제하지 않으면 시스템은 금방 위험해집니다.

### 왜 개발자도 운영체제를 알아야 하나요

앱이나 웹 서비스 개발자라고 해서 운영체제와 무관하지 않습니다. 파일 읽기 실패, 포트 충돌, 권한 문제, 메모리 부족, 프로세스 종료, 로그 저장 위치, 스레드 동작은 모두 운영체제와 연결됩니다. 운영체제의 역할을 모르면 이런 문제를 단순한 코드 버그로만 오해하기 쉽습니다.

예를 들어 서버가 갑자기 종료되었다면, 코드 논리 문제일 수도 있지만 운영체제가 메모리 부족으로 프로세스를 강제 종료한 것일 수도 있습니다. 파일 업로드가 실패했다면 코드보다 파일 권한이나 디스크 공간 문제가 원인일 수 있습니다. 즉, 운영체제는 문제의 배경을 읽게 해 주는 기본 맥락입니다.

### 초보자는 어떤 한 문장으로 기억하면 좋을까요

운영체제는 컴퓨터 자원의 관리자이자 프로그램과 하드웨어 사이의 통역사라고 기억하면 좋습니다. 프로그램이 편하게 일할 수 있도록 자원을 나누고, 하드웨어 접근을 표준화하고, 충돌과 위험을 줄여 주는 존재입니다.

이렇게 이해하면 운영체제는 더 이상 막연한 시스템 과목이 아닙니다. 내가 만든 프로그램이 실제로 살아 움직이는 환경을 제공하는 가장 중요한 바닥층으로 보이기 시작합니다.

### 핵심만 다시 정리하면

운영체제는 CPU, 메모리, 파일, 장치, 네트워크, 권한을 관리하면서 프로그램이 하드웨어를 안전하게 사용할 수 있게 돕는 시스템입니다. 겉으로는 화면 환경처럼 보일 수 있지만, 본질은 자원 관리와 추상화에 있습니다. 개발자는 운영체제를 이해할수록 프로그램의 실행 환경을 더 정확하게 해석할 수 있습니다.

## 멀티 스레드를 활용한 동시 수행

스레드는 한 프로세스 안에서 실제 작업 흐름을 실행하는 단위입니다. 멀티 스레드는 그 하나의 프로세스 안에서 여러 작업 흐름을 동시에 또는 번갈아 수행하게 만드는 방식입니다. 초보자가 자주 헷갈리는 지점은 프로세스와 스레드가 비슷해 보인다는 점인데, 핵심은 스레드가 같은 프로세스의 자원을 공유한다는 데 있습니다.

예를 들어 채팅 프로그램을 생각해 보면, 화면을 그리는 일, 네트워크 메시지를 기다리는 일, 파일 업로드 진행률을 보여 주는 일이 한 앱 안에서 동시에 돌아가야 할 수 있습니다. 이런 작업을 모두 한 흐름에서만 처리하면 특정 작업이 오래 걸릴 때 전체가 멈춘 것처럼 느껴질 수 있습니다. 멀티 스레드는 이런 응답성 문제를 줄이는 데 도움을 줍니다.

### 왜 멀티 스레드를 쓰나요

첫째는 응답성을 높이기 위해서입니다. 사용자 화면을 담당하는 스레드와 오래 걸리는 작업을 담당하는 스레드를 나누면, 파일 업로드 중에도 화면이 덜 멈춘 것처럼 만들 수 있습니다. 둘째는 자원을 더 효율적으로 쓰기 위해서입니다. 멀티코어 환경에서는 여러 스레드가 실제로 병렬 실행되며 처리량을 높일 수 있습니다.

셋째는 같은 프로세스 안에서 데이터를 공유하기 쉽기 때문입니다. 프로세스를 여러 개 띄우는 것보다 스레드를 나누는 편이 메모리 공유가 자연스럽고 생성 비용도 적은 경우가 많습니다. 그래서 서버 프로그램이나 게임 엔진, 백그라운드 작업이 많은 앱에서 멀티 스레드가 자주 등장합니다.

### 그런데 왜 멀티 스레드가 어렵다고 하나요

이유는 공유 때문입니다. 같은 메모리를 함께 쓰면 협력도 쉬워지지만 충돌도 쉬워집니다. 한 스레드가 값을 바꾸는 동안 다른 스레드가 동시에 읽거나 바꾸면 예상하지 못한 오류가 생길 수 있습니다. 이를 경쟁 상태라고 부르며, 디버깅이 특히 어렵습니다.

또한 스레드가 서로 자원을 기다리다 멈춰 버리는 교착 상태, 순서에 따라 결과가 달라지는 문제도 생길 수 있습니다. 그래서 멀티 스레드는 빠르기만 한 기술이 아니라, 올바른 동기화 설계가 함께 필요합니다. 초보자는 멀티 스레드를 쓰면 무조건 성능이 좋아진다고 생각하기 쉽지만, 잘못 쓰면 오히려 더 느리고 불안정해질 수 있습니다.

### 초보자는 어떤 기준으로 접근하면 좋을까요

먼저 모든 프로그램이 멀티 스레드를 꼭 써야 하는 것은 아니라는 점을 기억하면 좋습니다. 독립적인 작업이 있고, 응답성을 지켜야 하며, 공유 자원 접근을 잘 통제할 수 있을 때 멀티 스레드의 이점이 커집니다. 반면 단순한 순차 작업을 괜히 여러 스레드로 쪼개면 복잡성만 증가할 수 있습니다.

결국 멀티 스레드는 동시에 많이 한다기보다, 작업을 더 잘 나누고 시스템 자원을 더 잘 활용하기 위한 도구입니다. 그 장점과 위험을 함께 이해하는 것이 중요합니다.

### 핵심만 다시 정리하면

멀티 스레드는 하나의 프로세스 안에서 여러 실행 흐름을 활용해 응답성과 처리량을 높이려는 방식입니다. 같은 메모리를 공유하므로 효율적이지만, 경쟁 상태와 교착 상태 같은 동시성 문제도 함께 생깁니다. 따라서 멀티 스레드는 성능 도구이면서 동시에 설계 책임을 요구하는 기술입니다.

### 현업 장면으로 바꾸면 이렇게 보입니다

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 메모리 부족, 충돌, 동시성 문제를 해석할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

결국 이 개념을 이해한다는 것은 운영체제가 왜 개발자의 관심사인지 납득하게 됩니다

코드가 결국 CPU, 메모리, 저장장치, 운영체제를 지나 실행된다는 흐름을 붙잡으면 개별 용어가 훨씬 쉬워집니다. 그러면 비슷한 용어를 만나도 같은 상자에 모두 넣어 버리는 실수를 줄일 수 있습니다.

3. 느려짐이나 멈춤이 생겼을 때 코드 문제인지 실행 환경 문제인지 구분하는 질문을 세 개 적어 봅니다.

## 커널(Kernel)이란 무엇인가요?

커널은 운영체제의 핵심 부분입니다. 운영체제 전체가 집이라면 커널은 그 집의 기초 공사와 전기 배선, 수도관처럼 가장 안쪽에서 자원을 직접 관리하는 층이라고 볼 수 있습니다. 프로세스 관리, 메모리 관리, 장치 제어, 파일 시스템 접근 같은 중요한 일들이 커널 중심으로 움직입니다.

초보자는 운영체제와 커널을 같은 말로 쓰기도 하지만, 엄밀히 보면 커널은 운영체제의 중심부입니다. 우리가 보는 창, 설정 화면, 파일 탐색기 같은 요소는 운영체제의 사용자 환경에 가깝고, 커널은 그 아래에서 실제 권한 있는 작업을 수행하는 부분입니다.

### 왜 커널이 따로 중요할까요

하드웨어는 함부로 접근하면 시스템 전체가 불안정해질 수 있습니다. 그래서 모든 프로그램이 직접 하드웨어를 마음대로 만지지 못하도록 막고, 중요한 접근은 커널을 거치게 합니다. 예를 들어 파일을 읽거나 네트워크 소켓을 열거나 메모리를 할당하는 일은 결국 커널이 관리하는 영역을 통과합니다.

프로그램이 이런 기능을 요청할 때는 시스템 호출이라는 통로를 사용합니다. 초보자는 시스템 호출이라는 단어를 무겁게 느낄 수 있지만, 간단히 말해 프로그램이 운영체제 핵심 기능을 정식으로 부탁하는 방식입니다. 즉, 커널은 무질서를 막는 안전한 관문입니다.

### 사용자 공간과 커널 공간은 무엇이 다른가요

현대 운영체제는 보통 프로그램이 실행되는 사용자 공간과, 커널이 동작하는 커널 공간을 구분합니다. 사용자 프로그램은 제한된 권한 안에서 실행되고, 위험한 작업이나 핵심 자원 접근은 커널 쪽에서만 처리합니다. 이 구분 덕분에 하나의 프로그램 오류가 시스템 전체를 쉽게 망가뜨리는 일을 줄일 수 있습니다.

물론 커널이 강력한 만큼, 커널 수준의 오류는 영향도 큽니다. 그래서 커널 코드는 매우 신중하게 작성되고 검증되어야 합니다. 일반 개발자가 रोज마다 커널 코드를 만질 일은 적어도, 커널이 왜 존재하는지 이해하면 파일 권한, 네트워크 소켓, 시스템 자원 접근 같은 문제를 훨씬 덜 막연하게 보게 됩니다.

### 초보자는 무엇만 기억해도 충분할까요

커널은 운영체제의 심장부이며, 하드웨어와 자원을 직접 관리하는 가장 신뢰된 층이라고 이해하면 충분합니다. 프로그램은 보통 커널의 규칙을 통해 자원을 사용하고, 이 구조 덕분에 시스템은 비교적 안전하고 질서 있게 움직입니다.

이 감각을 알면 운영체제는 단순한 배경 소프트웨어가 아니라, 내 프로그램이 기대는 가장 강한 바닥이라는 점이 선명해집니다.

### 핵심만 다시 정리하면

커널은 운영체제의 핵심 부분으로, 프로세스, 메모리, 장치, 파일 시스템 같은 핵심 자원을 직접 관리합니다. 일반 프로그램은 시스템 호출을 통해 커널에 도움을 요청하며, 사용자 공간과 커널 공간의 분리는 시스템 안정성과 보안을 높여 줍니다. 커널을 이해하면 운영체제의 실제 중심이 어디인지 분명하게 보입니다.

이 절을 제대로 소화하면 성능 문제를 말할 때 훨씬 구체적인 질문을 할 수 있게 됩니다

코드가 결국 CPU, 메모리, 저장장치, 운영체제를 지나 실행된다는 흐름을 붙잡으면 개별 용어가 훨씬 쉬워집니다. 초보자에게 필요한 것은 어려운 설명보다 분명한 경계입니다.

2. 프로그램 하나를 실행하고 메모리 사용량, 프로세스 수, CPU 사용량이 어떻게 바뀌는지 관찰해 봅니다.

3. 느려짐이나 멈춤이 생겼을 때 코드 문제인지 실행 환경 문제인지 구분하는 질문을 세 개 적어 봅니다.

## 프로그램, 프로세스, 프로세서의 차이가 뭔가요?

이 세 단어는 소리가 비슷해서 초보자를 자주 헷갈리게 합니다. 하지만 가리키는 대상은 분명히 다릅니다. 프로그램은 저장장치에 저장된 코드와 데이터 묶음이고, 프로세스는 그 프로그램이 실제로 실행 중인 상태를 뜻합니다. 프로세서는 보통 CPU, 즉 계산을 수행하는 하드웨어를 가리킵니다.

쉽게 비유하면 프로그램은 요리책의 레시피, 프로세스는 지금 실제로 요리하고 있는 장면, 프로세서는 그 요리를 수행하는 요리사라고 볼 수 있습니다. 같은 레시피가 있어도 여러 명이 동시에 요리하면 여러 실행 장면이 생길 수 있듯, 하나의 프로그램으로부터 여러 프로세스가 만들어질 수도 있습니다.

### 프로그램과 프로세스는 왜 구분해야 하나요

프로그램은 아직 실행되지 않은 정적인 존재입니다. 파일 시스템 안에 저장되어 있을 뿐이며, CPU 시간을 쓰지 않습니다. 반면 프로세스는 메모리를 할당받고, 운영체제의 관리 대상이 되며, 실제로 명령을 수행합니다. 즉, 실행 순간부터 운영체제는 프로그램이 아니라 프로세스를 다룹니다.

이 구분을 이해하면 작업 관리자에서 보이는 목록을 해석하기 쉬워집니다. 거기 보이는 것은 설치된 프로그램 목록이 아니라 현재 살아 있는 프로세스 목록입니다. 또한 같은 앱을 두 번 실행하면 같은 프로그램 파일에서 서로 다른 프로세스가 생길 수 있다는 점도 자연스럽게 이해됩니다.

### 프로세서라는 말은 무엇을 가리키나요

프로세서는 보통 명령을 처리하는 하드웨어 장치, 즉 CPU를 뜻합니다. 운영체제가 여러 프로세스를 관리하더라도 실제 계산은 결국 프로세서가 수행합니다. 멀티코어 CPU에서는 여러 코어가 함께 프로세서 역할을 나누어 수행합니다.

초보자는 프로세스와 프로세서를 비슷한 것으로 착각하기 쉽습니다. 하지만 프로세스는 소프트웨어 실행 단위이고, 프로세서는 하드웨어 계산 장치입니다. 하나는 운영체제가 관리하는 일감이고, 다른 하나는 그 일감을 처리하는 기계라고 보면 됩니다.

### 왜 이 차이를 꼭 알아야 할까요

이 세 단어를 구분해야 성능 문제와 시스템 동작을 정확히 설명할 수 있습니다. 예를 들어 프로세스가 너무 많아 메모리를 많이 쓴다고 말하는 것과, CPU 사용률이 높다고 말하는 것은 전혀 다른 문제입니다. 하나는 실행 단위의 수와 상태에 관한 이야기이고, 다른 하나는 계산 자원의 바쁨에 관한 이야기입니다.

즉, 프로그램, 프로세스, 프로세서를 나누어 생각하는 습관은 운영체제와 성능 문제를 정확하게 말하는 첫걸음입니다.

### 핵심만 다시 정리하면

프로그램은 저장된 코드, 프로세스는 실행 중인 프로그램, 프로세서는 그 일을 처리하는 CPU 하드웨어입니다. 세 단어는 비슷해 보여도 정적 파일, 실행 상태, 계산 장치라는 전혀 다른 층위를 가리킵니다. 이 차이를 이해하면 작업 관리자와 성능 문제를 훨씬 정확하게 읽을 수 있습니다.

### 읽다가 흔들리는 지점

## 프로세스와 쓰레드의 차이는 무엇인가요?

프로세스와 스레드는 모두 실행과 관련된 단위이지만, 크기와 공유 방식이 다릅니다. 프로세스는 운영체제가 관리하는 독립적인 실행 단위이고, 스레드는 그 프로세스 안에서 실제 작업 흐름을 나누는 더 작은 단위입니다. 초보자는 두 개념을 단순히 크기 차이로만 생각하기 쉽지만, 핵심은 자원을 얼마나 공유하느냐에 있습니다.

프로세스는 보통 서로 독립된 메모리 공간을 가집니다. 그래서 하나의 프로세스가 크게 잘못되어도 다른 프로세스에 바로 영향을 주지 않도록 격리하기 쉽습니다. 반면 같은 프로세스 안의 스레드들은 코드와 메모리의 많은 부분을 공유합니다. 그래서 스레드는 가볍고 협력하기 쉽지만, 서로 간섭할 위험도 큽니다.

### 언제 프로세스를 나누고, 언제 스레드를 나누나요

프로세스를 나누는 것은 격리와 안정성이 중요할 때 유리합니다. 예를 들어 브라우저가 탭을 별도 프로세스로 두거나, 서버에서 독립 서비스가 각각 자기 프로세스로 도는 이유는 문제가 퍼지는 범위를 줄이기 위해서입니다. 프로세스는 경계가 분명하기 때문에 보안과 장애 격리에 유리합니다.

반면 스레드는 같은 데이터와 상태를 함께 다루며 응답성을 높이거나 병렬 처리를 하고 싶을 때 유리합니다. 같은 프로세스 안에서 메모리를 공유하므로 협력이 빠르고 생성 비용도 비교적 적습니다. 하지만 공유가 쉬운 만큼 동기화 문제가 따라옵니다.

### 초보자가 자주 헷갈리는 포인트

스레드가 가볍다고 해서 무조건 더 좋은 선택은 아닙니다. 공유 메모리 때문에 작은 실수도 복잡한 버그로 이어질 수 있습니다. 반대로 프로세스는 무겁다고만 볼 필요도 없습니다. 안정성과 격리가 중요한 시스템에서는 오히려 더 적절한 선택일 수 있습니다.

또한 프로그램 하나가 프로세스 하나, 스레드 하나로만 이루어진다고 생각하면 안 됩니다. 현실의 앱과 서버는 여러 프로세스와 여러 스레드를 조합해 사용합니다. 즉, 둘은 경쟁 개념이 아니라 문제에 따라 다르게 쓰는 도구입니다.

### 초보자는 어떤 한 문장으로 기억하면 좋을까요

프로세스는 독립된 집, 스레드는 그 집 안에서 움직이는 사람이라고 생각하면 도움이 됩니다. 집을 나누면 안전하지만 왕래 비용이 있고, 집 안에서 여러 사람이 함께 움직이면 빠르지만 충돌 관리가 필요합니다.

이 비유만 잡혀도 나중에 멀티프로세스 구조, 멀티스레드 서버, 동시성 문제를 읽을 때 훨씬 덜 막막해집니다.

### 핵심만 다시 정리하면

프로세스는 독립성과 격리를 가진 실행 단위이고, 스레드는 그 안에서 자원을 공유하며 움직이는 더 작은 실행 흐름입니다. 프로세스는 안정성과 분리에, 스레드는 효율과 협력에 유리합니다. 어떤 쪽이 더 좋다기보다, 무엇을 우선할지에 따라 선택이 달라집니다.
