# 3장. 소프트웨어를 만드는 개발 언어 및 프레임워크

개발을 시작하면 가장 먼저 쏟아지는 정보가 언어 이름과 프레임워크 이름입니다. C, C++, Java, JavaScript, Python, React, Spring, Flutter 같은 이름이 한꺼번에 등장하면 초보자는 금방 지치기 쉽습니다. 이름은 많은데, 각각이 왜 존재하는지와 언제 쓰는지가 잘 보이지 않기 때문입니다.

이 장의 목표는 언어와 프레임워크를 모두 외우게 만드는 것이 아닙니다. 오히려 반대입니다. 각각의 도구가 어떤 문제를 해결하기 위해 등장했고, 어떤 상황에서 강점을 가지는지 보이게 만드는 것이 목적입니다. 그래야 새로운 이름을 만나도 당황하지 않고, "아, 이건 이런 계열이구나"라고 자리를 잡을 수 있습니다.

## 이 장을 읽을 때 붙잡아야 할 기준

첫째, 언어는 모두 같은 일을 하는 것이 아닙니다. 어떤 언어는 하드웨어에 가까운 제어에 강하고, 어떤 언어는 대규모 업무 시스템에 강하며, 어떤 언어는 빠른 실험과 자동화에 강합니다.

둘째, 프레임워크는 언어를 대신하는 존재가 아닙니다. 언어가 재료라면 프레임워크는 자주 쓰는 구조와 규칙을 미리 마련해 둔 작업 틀에 가깝습니다.

셋째, 좋은 선택은 유행이 아니라 목적에 따라 달라집니다. 무엇을 만들 것인지, 누가 유지보수할 것인지, 얼마나 빨리 실험해야 하는지에 따라 정답이 달라집니다.

## 이 장에서 얻어야 하는 것

이 장을 읽고 나면 적어도 다음 정도는 설명할 수 있어야 합니다. 언어 선택은 취향의 문제가 아니라 제품과 팀의 문제라는 점, C와 Java와 Python이 왜 서로 다른 자리에 있는지, React 같은 프레임워크가 왜 널리 쓰이는지, 그리고 모바일과 서버 개발에서 왜 도구 선택이 달라지는지 말입니다.

## 언제 어떤 언어를 선택하는 게 좋을까요?

개발 언어를 고를 때 초보자가 가장 많이 하는 질문은 "가장 좋은 언어가 무엇인가요?"입니다. 하지만 이 질문에는 단 하나의 정답이 없습니다. 이유는 언어가 모두 같은 목적을 위해 만들어진 도구가 아니기 때문입니다. 어떤 언어는 속도와 제어에 강하고, 어떤 언어는 생산성과 가독성에 강하며, 어떤 언어는 특정 생태계와 함께 힘을 발휘합니다.

그래서 언어를 고를 때는 "무엇이 최고인가"보다 "무엇을 만들 것인가"를 먼저 봐야 합니다. 예를 들어 브라우저 안에서 동작하는 화면을 만들고 싶다면 자바스크립트 계열을 피하기 어렵습니다. 반대로 간단한 자동화와 데이터 처리부터 시작하고 싶다면 파이썬이 더 부드러운 출발이 될 수 있습니다. 기업용 서버 시스템이라면 자바나 C# 같은 언어가 자주 선택되기도 합니다.

### 언어를 고를 때 실제로 봐야 할 기준

첫 번째 기준은 제품의 성격입니다. 웹 프론트엔드, 모바일 앱, 게임, 임베디드 장치, 데이터 분석, 서버 시스템은 요구가 서로 다릅니다. 예를 들어 하드웨어와 가까운 제어가 중요하면 C 계열이 강하고, 빠르게 프로토타입을 만들고 반복해야 하면 파이썬이나 자바스크립트 계열이 유리할 수 있습니다.

두 번째 기준은 팀의 역량입니다. 좋은 언어라도 팀이 읽고 유지할 수 없으면 좋은 선택이 아닙니다. 회사에서는 언어의 기술적 우수성만큼이나 채용 가능성, 기존 코드베이스, 라이브러리 경험, 운영 인력의 숙련도가 중요하게 작용합니다.

세 번째 기준은 생태계입니다. 생태계라는 말은 그 언어를 둘러싼 프레임워크, 라이브러리, 문서, 커뮤니티, 배포 도구, 예제의 묶음을 뜻합니다. 언어 자체는 비슷해 보여도 생태계가 풍부한지에 따라 생산성이 크게 달라집니다. 초보자에게 특히 중요한 이유는, 막혔을 때 참고할 자료가 많은 언어가 학습 난이도를 많이 낮춰 주기 때문입니다.

### 초보자는 어떻게 접근하는 것이 좋은가

처음부터 모든 분야를 고려해 완벽한 선택을 할 필요는 없습니다. 오히려 처음에는 진입 목적을 분명히 하는 것이 중요합니다. 웹 화면을 만들고 싶으면 자바스크립트와 타입스크립트, 자동화나 데이터 쪽이 궁금하면 파이썬, 앱과 기업 시스템 구조를 배우고 싶다면 자바처럼 출발점을 정하면 됩니다.

여기서 중요한 점은 첫 언어가 마지막 언어가 아니라는 것입니다. 개발자는 평생 하나의 언어만 쓰는 경우가 드뭅니다. 첫 언어의 목적은 평생 충성할 언어를 찾는 것이 아니라, 변수, 함수, 조건문, 자료구조, 디버깅 같은 핵심 사고를 익히는 데 있습니다. 한 언어에서 이 뼈대를 익히면 다른 언어로 옮겨 가는 속도는 점점 빨라집니다.

### 유행만 보고 고르면 왜 흔들리나

언어 선택에서 자주 생기는 실수는 유행만 좇는 것입니다. 인터넷에서는 늘 "요즘은 이 언어가 대세다"라는 말이 나옵니다. 물론 시장 흐름을 보는 것은 중요하지만, 유행만으로 시작하면 왜 배우는지 모른 채 툴 이름만 쫓게 되기 쉽습니다.

예를 들어 어떤 언어가 채용 공고에서 많이 보인다고 해도, 그 언어가 여러분의 현재 목표와 맞지 않을 수 있습니다. 반대로 덜 화려해 보여도 기초를 배우기 좋은 언어가 더 나은 첫 선택일 수도 있습니다. 결국 좋은 언어 선택이란 멋져 보이는 도구를 고르는 일이 아니라, 지금의 목적과 다음 단계까지 함께 고려하는 일입니다.

### 핵심만 다시 정리하면

언어 선택에는 절대적인 정답이 없습니다. 무엇을 만들지, 누가 유지할지, 관련 생태계가 어떤지에 따라 적절한 선택이 달라집니다. 초보자는 완벽한 첫 언어를 찾으려 하기보다, 자신이 만들고 싶은 것에 가장 가까운 출발점을 고르고 핵심 사고를 익히는 데 집중하는 편이 훨씬 좋습니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 언어와 프레임워크 선택, 생태계, 역할 구분와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 어떤 언어가 지금 문제에 잘 맞는지, 팀이 유지보수하기 쉬운지 따질 때 이 개념이 다시 등장합니다.

그래서 이 절의 설명은 곧 새 기술 이름을 만나도 겁먹지 않고 자리를 잡을 수 있습니다

### 읽다가 흔들리는 지점

이 주제에서 가장 흔한 오해는 가장 좋은 언어 하나만 찾으면 끝난다고 생각하거나, 프레임워크 이름을 언어처럼 받아들이는 점입니다.

문법, 실행 환경, 생태계, 팀 숙련도는 서로 다른 축이라는 사실을 나눠 봐야 합니다. 이 기준만 있어도 뒤 장에서 같은 말을 다시 만나도 훨씬 덜 흔들립니다.

### 손으로 확인해 보면 더 빨리 남습니다

이 개념은 읽는 것만으로는 쉽게 손에 잡히지 않습니다. 아주 작은 확인만 해도 본문이 훨씬 입체적으로 보입니다.

1. 같은 기능을 만들 때 이 개념이 무엇을 더 쉽게 해 주는지 한 줄씩 비교해 봅니다.

2. 공식 소개 문서에서 이 개념이 주로 어떤 문제를 해결하는지 찾아 적어 봅니다.

3. 내가 만들고 싶은 서비스 기준으로 이 개념이 왜 필요한지 또는 왜 아직 과한지 판단해 봅니다.

이 개념은 여기서 끝나는 개념이 아닙니다. 이 절에서 잡은 감각은 4장의 핵심 개발 개념, 5장의 팀 개발 흐름, 10장의 현대 인프라 선택로 이어집니다.

따라서 다음 절을 읽을 때는 "이 개념이 지금 설명하는 층은 어디인가"를 계속 추적해 보세요. 그 습관이 전체 책을 훨씬 쉽게 만듭니다.

## 전공자들이 배우는 C언어

많은 컴퓨터 관련 학과에서 여전히 C언어를 가르칩니다. 이 사실을 보면 초보자는 종종 의아해합니다. 요즘은 웹도 있고, 앱도 있고, 파이썬처럼 더 읽기 쉬운 언어도 많은데 왜 굳이 오래된 C언어를 배우는지 궁금해하는 것입니다.

이유는 C언어가 최신 유행의 생산성 도구라서가 아니라, 컴퓨터가 어떻게 움직이는지를 비교적 직접적으로 보여 주는 언어이기 때문입니다. C언어를 배우면 변수 하나를 선언하는 것, 배열을 다루는 것, 메모리를 사용하는 것, 프로그램이 실행되는 흐름이 조금 더 생생하게 드러납니다. 그래서 전공 기초를 다지는 데 자주 쓰입니다.

### C언어가 보여 주는 것

C언어의 중요한 특징 중 하나는 하드웨어와 운영체제에 상대적으로 가까운 감각을 준다는 점입니다. 예를 들어 메모리 주소, 포인터, 배열, 버퍼 같은 개념이 다른 현대 언어보다 더 직접적으로 등장합니다. 초보자에게는 처음에 어렵게 느껴질 수 있지만, 그만큼 컴퓨터 내부에서 무슨 일이 일어나는지 감을 잡는 데 도움이 됩니다.

또한 C언어는 언어 자체가 비교적 작고 단순한 편입니다. 그래서 화려한 기능이 많다기보다, 기본적인 흐름 제어와 데이터 처리 원리를 또렷하게 보여 줍니다. 이런 이유로 자료구조, 운영체제, 컴퓨터 구조 같은 과목과도 연결하기 좋습니다.

### 그렇다고 C언어가 모든 개발의 중심은 아니다

여기서 중요한 오해를 바로잡아야 합니다. 전공자가 C언어를 배운다고 해서, 실무에서 모든 것을 C로 만든다는 뜻은 아닙니다. 실제 현장에서는 웹, 앱, 서버, 데이터 분야에 따라 자바, 자바스크립트, 파이썬, 고, 러스트 같은 다양한 언어가 사용됩니다.

C언어는 모든 상황에서 가장 편한 언어라기보다, 기초 원리를 선명하게 보여 주는 언어에 가깝습니다. 운영체제, 임베디드 시스템, 성능이 중요한 라이브러리처럼 C가 여전히 강한 분야도 분명히 있지만, 많은 제품 개발에서는 더 높은 생산성을 주는 다른 언어가 선택됩니다.

### 초보자가 C언어에서 얻을 수 있는 것

비전공자라도 C언어를 조금 접해 보면 얻는 것이 있습니다. 프로그램이 왜 메모리를 신경 써야 하는지, 자료형이 왜 중요한지, 성능과 제어가 무엇을 뜻하는지 더 분명하게 느끼게 됩니다. 특히 포인터와 배열, 함수 호출, 메모리 관리 같은 개념은 처음에는 어렵지만, 한 번 감을 잡으면 다른 언어를 볼 때도 눈이 달라집니다.

다만 처음부터 C언어만 고집해야 한다는 뜻은 아닙니다. 웹 서비스를 जल्दी 만들어 보고 싶거나 자동화부터 시작하고 싶다면, 다른 언어를 먼저 배우고 나중에 C를 접해도 됩니다. 중요한 것은 C언어를 신화처럼 보는 것이 아니라, 어떤 종류의 이해를 주는 언어인지 아는 것입니다.

### 왜 여전히 의미가 있는가

C언어는 오래되었지만 아직 끝나지 않은 언어입니다. 운영체제의 핵심 부분, 여러 라이브러리, 임베디드 소프트웨어, 성능이 중요한 영역에서는 여전히 큰 영향을 미칩니다. 그리고 무엇보다, 소프트웨어가 기계 위에서 어떻게 실행되는지를 배우는 데 여전히 교육적 가치가 큽니다.

### 핵심만 다시 정리하면

C언어는 모든 제품을 만들기 위한 가장 편한 언어라서 배우는 것이 아닙니다. 컴퓨터의 동작 원리와 메모리 감각을 더 직접적으로 보여 주기 때문에 전공 기초로 자주 사용됩니다. 실무 언어 선택과는 별개로, 기초를 다지는 데 의미가 큰 언어라고 이해하면 됩니다.

### 실제로 만들 때는 이런 선택으로 이어집니다

이 개념은 정의 하나로 끝나는 주제가 아니라, 실제 선택의 기준이 되는 개념입니다. 특히 프레임워크 도입으로 얻는 속도와 잃는 자유를 비교할 때 이 절의 내용이 곧바로 판단 기준이 됩니다.

이 관점을 잡아 두면 같은 기능을 왜 서로 다른 언어로 구현하는지 이해하게 됩니다

## C언어와 C++의 차이는 무엇인가요?

이 두 언어는 이름이 비슷해서 초보자가 같은 언어의 버전 차이 정도로 생각하기 쉽습니다. 실제로 역사적으로 C에서 출발해 C++가 발전한 것은 맞습니다. 하지만 지금의 관점에서 보면 두 언어는 성격이 꽤 다릅니다. 단순히 기능이 조금 더 붙은 수준이라고 보기에는 사고방식과 활용 분야가 많이 벌어져 있습니다.

C언어는 상대적으로 단순한 구조와 직접적인 제어를 중시합니다. 반면 C++는 C의 기반 위에 더 복잡한 추상화 도구를 추가해, 큰 프로그램을 구조적으로 다룰 수 있게 확장된 언어입니다. 그래서 같은 계열이라고는 해도 사용하는 느낌은 제법 다릅니다.

### C는 더 직접적이고, C++는 더 많은 도구를 준다

C언어는 메모리와 자료 구조를 비교적 직접적으로 다루게 합니다. 언어가 단순한 만큼, 프로그래머가 스스로 책임져야 할 부분도 많습니다. 이것이 어렵지만 동시에 교육적으로 선명한 이유이기도 합니다.

C++는 여기에 클래스, 상속, 다형성 같은 객체지향 기능뿐 아니라 템플릿, 표준 라이브러리, 자동 자원 관리에 도움이 되는 여러 기능을 추가했습니다. 쉽게 말해 C보다 더 큰 프로그램을 더 구조적으로 다룰 수 있도록 많은 장치를 제공하는 언어입니다.

### 왜 C++는 어려워 보이나

초보자가 C++를 어렵게 느끼는 이유는 두 세계가 동시에 들어 있기 때문입니다. C 스타일의 직접 제어도 어느 정도 남아 있고, 그 위에 고수준 추상화 기능도 많습니다. 그래서 문법 표면만 봐도 선택지가 많고, 같은 일을 하는 방식이 여러 개처럼 보일 수 있습니다.

하지만 이런 복잡성은 이유 없이 생긴 것이 아닙니다. 게임 엔진, 고성능 애플리케이션, 그래픽스, 시스템 소프트웨어처럼 성능도 중요하고 규모도 큰 프로그램을 만들다 보면, 세밀한 제어와 큰 구조화가 동시에 필요해집니다. C++는 이런 요구를 오래 다뤄 온 언어입니다.

### 실무에서는 어떻게 다르게 쓰이나

C는 운영체제의 일부, 임베디드 소프트웨어, 라이브러리, 장치 제어처럼 단순하고 직접적인 제어가 중요한 영역에서 많이 보입니다. C++는 게임 개발, 렌더링 엔진, 대규모 데스크톱 애플리케이션, 성능이 중요한 복잡한 시스템에서 자주 등장합니다.

물론 경계가 완전히 고정된 것은 아닙니다. 어떤 프로젝트는 C로도 큰 시스템을 만들고, 어떤 프로젝트는 C++를 비교적 단순한 방식으로 쓰기도 합니다. 하지만 초보자가 큰 차이를 잡을 때는 "C는 더 직접적이고 작다, C++는 더 많은 추상화와 구조화를 제공한다" 정도로 이해하는 것이 좋습니다.

### 어떤 점을 헷갈리기 쉬운가

가장 흔한 오해는 C++가 C를 완전히 대체하는 상위 버전이라는 생각입니다. 실제로는 상위·하위 관계보다는 목적과 스타일의 차이로 보는 편이 더 정확합니다. 또 어떤 사람은 C++가 무조건 객체지향 언어라고만 이해하지만, 실제 C++는 객체지향뿐 아니라 절차적 스타일, 일반화 프로그래밍 스타일도 함께 사용하는 언어입니다.

### 핵심만 다시 정리하면

C와 C++는 뿌리는 가깝지만 지금은 꽤 다른 성격을 가진 언어입니다. C는 더 직접적이고 단순한 제어에 강하고, C++는 더 큰 규모의 구조화와 추상화를 제공하면서도 성능을 중시하는 언어입니다. 이름이 비슷하다고 같은 용도로만 보면 곤란합니다.

## 자바(Java)는 어떤 언어인가요?

자바는 오랫동안 기업용 시스템과 서버 개발에서 강한 위치를 차지해 온 언어입니다. 초보자에게는 문법이 다소 장황해 보일 수 있지만, 그만큼 구조를 명확하게 드러내는 편이어서 큰 프로그램을 다루는 훈련에 자주 쓰입니다. 국내외에서 교육용으로도 많이 사용되고, 실무에서도 여전히 넓은 영역을 차지하고 있습니다.

자바를 이해할 때 중요한 키워드는 두 가지입니다. 하나는 "안정적인 대규모 개발"이고, 다른 하나는 "플랫폼 독립성"입니다. 자바는 실행 환경인 JVM 위에서 동작하는 구조를 통해, 운영체제 차이를 어느 정도 감추고 비교적 일관된 실행 환경을 제공해 왔습니다.

### 자바가 왜 오래 사랑받았나

자바가 널리 쓰인 이유는 단지 오래되었기 때문이 아닙니다. 대규모 팀 개발에 맞는 구조화, 풍부한 라이브러리, 성숙한 생태계, 강한 도구 지원이 오랫동안 쌓여 왔기 때문입니다. 금융, 공공, 전자상거래, 기업용 업무 시스템처럼 안정성과 유지보수가 중요한 분야에서 특히 강했습니다.

또한 자바는 언어 차원에서 타입을 비교적 엄격하게 다루는 편입니다. 타입은 데이터의 종류를 뜻합니다. 숫자인지, 문자열인지, 어떤 클래스의 객체인지 분명하게 선언하게 하는 방식은 처음에는 번거롭게 느껴질 수 있지만, 규모가 커질수록 실수를 줄이고 협업을 돕는 장점이 있습니다.

### 자바를 배우면 어떤 감각이 생기나

자바를 배우면 클래스, 객체, 패키지, 인터페이스, 예외 처리 같은 개념이 자주 등장합니다. 그래서 자연스럽게 큰 프로그램을 파일과 역할 단위로 나누는 감각을 익히게 됩니다. 이 점 때문에 객체지향 개념을 설명할 때 자바가 자주 등장합니다.

또한 서버 애플리케이션을 만드는 프레임워크 생태계가 잘 발달해 있어서, 웹 서비스가 실제로 어떤 층으로 나뉘는지 배우기에도 좋습니다. 예를 들어 요청을 받는 부분, 비즈니스 규칙을 처리하는 부분, 데이터를 저장하는 부분이 나뉘어 있는 구조를 자바 프로젝트에서 자주 볼 수 있습니다.

### 그렇다면 자바는 무조건 무겁고 느린가

자바를 두고 무겁다고 느끼는 사람도 많습니다. 프로젝트 구조가 크고, 처음 Hello World를 쓰는 데도 선언해야 할 것이 많기 때문입니다. 하지만 이런 인상만으로 자바를 낡은 언어라고 보기는 어렵습니다. 실제로는 긴 시간 동안 성능과 생산성 모두 많이 개선되어 왔고, 대형 서비스에서 여전히 널리 사용됩니다.

초보자에게 중요한 것은 자바를 무조건 최고라고 보는 것도, 반대로 구식이라고 치부하는 것도 아니라는 점입니다. 자바는 "복잡한 시스템을 비교적 정돈된 방식으로 다루는 데 강한 언어"라는 자리를 이해하면 됩니다.

자바는 대규모 서비스와 팀 개발에 강한 언어입니다. 문법은 다소 장황할 수 있지만, 구조를 분명하게 드러내고 큰 시스템을 유지보수하기 좋은 특징이 있습니다. 그래서 지금도 서버 개발과 기업용 시스템에서 중요한 언어로 남아 있습니다.

## 객체지향이란 무엇인가요?

객체지향이라는 말을 처음 들으면 대개 어렵게 느껴집니다. 클래스, 객체, 상속, 캡슐화, 다형성 같은 낯선 단어가 한꺼번에 나오기 때문입니다. 하지만 핵심 아이디어는 생각보다 단순합니다. 프로그램을 기능 덩어리와 데이터 묶음으로 나누어, 서로 역할을 가진 단위로 조직하려는 방식이라고 보면 됩니다.

쉽게 말해, 프로그램을 하나의 긴 절차로만 쓰지 않고 "이 일은 이 객체가 맡는다"라고 역할을 나누는 사고방식입니다. 현실 세계를 그대로 복사하는 것은 아니지만, 적어도 역할과 책임을 묶어 생각하게 도와줍니다.

### 왜 이런 방식이 필요했나

프로그램이 작을 때는 순서대로 쭉 써 내려가는 방식도 어느 정도 괜찮습니다. 하지만 규모가 커지면 어디서 어떤 데이터가 바뀌는지 추적하기 어려워지고, 기능을 추가할 때마다 기존 코드가 쉽게 엉키게 됩니다. 객체지향은 이런 복잡함을 줄이기 위해 등장한 여러 방법 중 하나입니다.

예를 들어 쇼핑몰 프로그램을 만든다고 할 때, 주문, 회원, 상품, 결제 같은 개념을 역할 단위로 나누어 다루면 구조를 파악하기 쉬워집니다. 주문과 관련된 데이터와 동작을 한곳에 모아 두면, 나중에 기능을 고칠 때도 찾기가 수월합니다.

### 객체지향에서 자주 나오는 말들

클래스는 설계도에 가깝고, 객체는 그 설계도로 만든 실제 대상에 가깝다고 이해하면 됩니다. 예를 들어 회원이라는 개념을 프로그램에 넣고 싶다면, 회원이 가져야 할 정보와 행동을 클래스에 적어 둘 수 있습니다. 그리고 실제 사용자 한 명 한 명은 객체로 만들어집니다.

캡슐화는 관련된 데이터와 기능을 하나로 묶고, 바깥에서 아무렇게나 건드리지 못하게 경계를 세우는 생각입니다. 상속은 기존 구조를 바탕으로 새로운 구조를 만드는 방식이고, 다형성은 같은 요청이라도 객체에 따라 다른 방식으로 반응하게 만드는 성질이라고 이해하면 됩니다. 초보자에게는 단어를 완벽히 외우기보다, "역할을 나누고 경계를 세우는 방법"이라는 큰 틀을 먼저 잡는 편이 더 중요합니다.

### 객체지향은 만능인가

여기서 꼭 짚고 넘어가야 할 점이 있습니다. 객체지향은 중요한 사고방식이지만, 모든 문제의 유일한 정답은 아닙니다. 어떤 프로그램은 절차적으로 쓰는 편이 더 단순하고, 어떤 문제는 함수형 스타일이나 데이터 중심 접근이 더 잘 맞기도 합니다.

즉, 객체지향을 배운다는 것은 세상을 객체로만 보라는 뜻이 아니라, 큰 프로그램을 조직하는 대표적인 방법 하나를 배우는 것입니다. 초보자는 특히 객체지향을 신비한 주문처럼 볼 필요가 없습니다. 코드가 커졌을 때 구조를 잡는 한 방법이라고 보면 충분합니다.

### 핵심만 다시 정리하면

객체지향은 프로그램을 역할과 책임이 있는 단위로 나누어 조직하려는 방식입니다. 클래스와 객체, 캡슐화와 상속 같은 개념은 그 구조화를 돕는 도구입니다. 중요한 것은 용어를 외우는 것보다, 왜 큰 프로그램에서 역할 분리가 필요한지 이해하는 것입니다.

## 프레임워크는 무엇이고, 어떤 프레임워크를 선택하는 게 좋을까요?

프레임워크는 개발할 때 자주 반복되는 구조와 규칙을 미리 마련해 둔 작업 틀이라고 생각하면 됩니다. 초보자가 처음 프로젝트를 만들 때는 파일 배치부터 요청 처리 방식, 화면 구성 방식까지 모든 것을 스스로 정해야 할 것 같지만, 프레임워크를 사용하면 자주 쓰는 선택을 상당 부분 대신해 줍니다.

그래서 프레임워크는 생산성을 크게 높여 줍니다. 단순히 편해서가 아니라, 팀이 같은 구조와 규칙 위에서 일할 수 있게 만들어 주기 때문입니다. 예를 들어 웹 프론트엔드에서 상태 관리와 화면 갱신을 어떻게 할지, 서버 개발에서 요청을 어디서 받아 어떤 계층으로 넘길지 같은 문제를 일정한 방식으로 다룰 수 있게 합니다.

### 라이브러리와 무엇이 다른가

초보자가 가장 많이 헷갈리는 부분이 바로 라이브러리와 프레임워크의 차이입니다. 라이브러리는 내가 필요할 때 가져다 쓰는 도구 상자에 가깝습니다. 반면 프레임워크는 전체 구조를 어느 정도 정해 두고, 그 안에서 코드를 넣게 하는 골격에 가깝습니다.

쉽게 비유하면 라이브러리는 필요한 공구를 골라 쓰는 것이고, 프레임워크는 공정 순서와 작업대가 어느 정도 갖춰진 작업장입니다. 그래서 프레임워크는 자유를 조금 줄이는 대신 속도와 일관성을 얻는 경우가 많습니다.

### 어떤 프레임워크를 고르면 좋은가

프레임워크 선택에서 가장 중요한 것은 "지금 만들려는 것과 잘 맞는가"입니다. 웹 화면을 만들고 싶다면 React, Vue, Angular 같은 프론트엔드 프레임워크·라이브러리 생태계가 후보가 될 수 있고, 자바 서버 개발이라면 Spring 계열이 자주 거론됩니다. 파이썬에서는 Django나 FastAPI처럼 목적이 다른 프레임워크가 등장합니다.

초보자는 특히 화려한 기능보다 학습 자료와 생태계를 먼저 보는 편이 좋습니다. 문서가 잘 되어 있고, 예제가 많고, 커뮤니티가 활발한 프레임워크는 막혔을 때 빠져나오기 쉽습니다. 반대로 기능이 좋아 보여도 자료가 적으면 입문 단계에서 금방 지치기 쉽습니다.

### 프레임워크를 고를 때 너무 늦게까지 고민할 필요는 없다

완벽한 프레임워크 선택을 하겠다고 오래 고민하는 것도 흔한 실수입니다. 실제로는 첫 프로젝트에서 모든 선택이 영원히 고정되지 않습니다. 중요한 것은 지금 단계에서 가장 무난하고 자료가 풍부한 선택으로 시작해, 구조화된 개발 경험을 얻는 것입니다.

프레임워크는 공부의 목적 자체가 아니라, 제품을 만드는 과정을 돕는 도구입니다. 따라서 초보자는 특정 프레임워크를 신앙처럼 대하기보다, "이 도구가 내 문제를 어떤 방식으로 쉽게 만들어 주는가"를 중심으로 보는 것이 좋습니다.

## 프론트엔드 개발 언어는 무엇인가요?

프론트엔드 개발을 말할 때 가장 먼저 알아야 할 것은, 엄밀히 말해 한 가지 언어만 있는 것이 아니라는 점입니다. 보통은 HTML, CSS, JavaScript 세 가지를 기본 축으로 이야기합니다. 여기에 TypeScript가 자주 함께 등장합니다.

HTML은 화면의 구조를 잡는 언어입니다. 제목, 문단, 버튼, 입력창, 표, 이미지 같은 요소가 화면에 어떤 의미로 배치되는지를 표현합니다. CSS는 그 구조를 어떻게 보이게 할지 결정합니다. 색, 글꼴, 간격, 배치, 반응형 디자인이 여기에 들어갑니다. JavaScript는 화면에 동작을 부여합니다. 버튼을 눌렀을 때 무슨 일이 일어나야 하는지, 서버에서 데이터를 받아오면 어떻게 보여 줄지, 입력이 바뀌면 화면을 어떻게 갱신할지를 처리합니다.

### 왜 세 가지가 함께 등장하나

초보자는 종종 "프론트엔드 언어는 자바스크립트인가요?"라고 묻습니다. 어느 정도는 맞지만, 정확히는 HTML과 CSS와 JavaScript가 함께 프론트엔드의 기본 뼈대를 이룹니다. 구조, 모양, 동작이 서로 다른 역할을 맡고 있기 때문입니다.

이 구분을 알면 프론트엔드에서 생기는 문제를 보는 눈도 달라집니다. 버튼이 아예 안 보이면 HTML이나 CSS 문제일 수 있고, 눌렀는데 동작이 안 되면 JavaScript 문제일 수 있습니다. 반응형 레이아웃이 깨지면 CSS 쪽을 먼저 의심할 수 있습니다.

### TypeScript는 또 무엇인가

TypeScript는 JavaScript를 더 안전하고 구조적으로 다루기 쉽게 만든 확장 언어라고 생각하면 됩니다. 자바스크립트는 매우 유연해서 빠르게 시작하기 좋지만, 규모가 커지면 데이터의 형태가 헷갈리거나 실수를 늦게 발견하는 문제가 생길 수 있습니다. TypeScript는 변수와 함수의 데이터 형태를 더 분명하게 적게 해 이런 문제를 줄이는 데 도움을 줍니다.

그래서 실무 프론트엔드 프로젝트에서는 TypeScript를 함께 쓰는 경우가 많습니다. 초보자는 처음부터 모든 타입 개념을 깊게 알 필요는 없지만, 자바스크립트 위에 안정성을 더하는 도구라는 정도는 알아두면 좋습니다.

### 프론트엔드 개발은 화면만 예쁘게 만드는 일인가

아닙니다. 프론트엔드 개발은 화면을 그리는 것 이상입니다. 사용자의 행동에 반응하고, 상태를 기억하고, 서버와 데이터를 주고받고, 오류를 친절하게 안내해야 합니다. 그래서 언어를 배운다는 것은 문법만 외우는 것이 아니라, 구조와 상태와 이벤트를 함께 이해하는 일입니다.

### 핵심만 다시 정리하면

프론트엔드의 기본 언어는 HTML, CSS, JavaScript입니다. HTML은 구조, CSS는 모양, JavaScript는 동작을 담당합니다. TypeScript는 그 위에 안정성과 구조화를 더하는 도구라고 이해하면 됩니다.

## 프론트엔드 개발에서 이벤트 처리가 무엇인가요?

프론트엔드에서 이벤트 처리는 사용자의 행동이나 화면에서 일어나는 변화를 감지하고, 그에 맞는 코드를 실행하는 일을 뜻합니다. 버튼 클릭, 마우스 이동, 키보드 입력, 스크롤, 폼 제출, 화면 로딩 같은 것들이 모두 이벤트가 될 수 있습니다.

쉽게 말하면 "무슨 일이 일어났을 때 어떻게 반응할 것인가"를 정하는 것이 이벤트 처리입니다. 프론트엔드가 살아 움직이는 것처럼 느껴지는 이유도 거의 모두 이 이벤트 처리 덕분입니다.

### 왜 중요한가

이벤트 처리가 없다면 웹 화면은 거의 정적인 문서에 가깝습니다. 버튼이 눌려도 아무 일도 일어나지 않고, 입력창에 글자를 쳐도 검사가 되지 않으며, 메뉴를 눌러도 화면 전환이 일어나지 않습니다. 즉, 사용자의 행동과 프로그램의 반응을 연결해 주는 핵심 고리가 이벤트 처리입니다.

예를 들어 회원가입 버튼을 누르면 입력값을 검사하고 서버에 전송해야 합니다. 검색창에 글자를 입력하면 추천어를 보여 줄 수도 있습니다. 장바구니 수량 버튼을 누르면 바로 합계 금액이 바뀌어야 할 수도 있습니다. 이 모든 것이 이벤트 처리입니다.

### 어떻게 이해하면 쉬운가

이벤트를 이해할 때는 두 단계로 나누어 생각하면 쉽습니다. 먼저 "무슨 일이 발생했는가"가 있고, 그다음 "그 일에 대해 어떤 코드를 실행할 것인가"가 있습니다. 예를 들어 클릭 이벤트가 발생하면, 어떤 함수를 실행해 데이터를 바꾸고 화면을 다시 그릴 수 있습니다.

프론트엔드 프레임워크를 쓰면 코드 모양은 달라질 수 있지만 핵심은 같습니다. 사용자의 행동과 상태 변화를 감지하고, 그 결과를 화면에 반영하는 흐름입니다. 그래서 이벤트 처리를 이해하면 프론트엔드의 반절은 이해한 셈이라고 말하기도 합니다.

### 초보자가 자주 막히는 이유

초보자는 종종 "클릭했는데 왜 값이 안 바뀌지?" 같은 문제에서 막힙니다. 이때 실제 원인은 여러 가지일 수 있습니다. 이벤트가 제대로 연결되지 않았을 수도 있고, 연결은 되었지만 상태를 바꾸는 코드가 잘못되었을 수도 있고, 값은 바뀌었는데 화면에 다시 반영되지 않았을 수도 있습니다.

그래서 이벤트 처리는 단순히 함수를 연결하는 기술이 아니라, 입력, 상태 변화, 화면 갱신이 어떻게 이어지는지 보는 훈련이기도 합니다. 이 흐름을 잡으면 프론트엔드 코드가 훨씬 덜 마법처럼 느껴집니다.

### 핵심만 다시 정리하면

이벤트 처리는 사용자의 행동이나 화면의 변화를 감지하고, 거기에 맞는 반응을 실행하는 일입니다. 프론트엔드의 상호작용은 대부분 이벤트 처리 위에서 돌아갑니다. 따라서 프론트엔드를 이해하려면 구조와 스타일뿐 아니라 이벤트 흐름까지 함께 이해해야 합니다.

## 리액트(React)는무엇이고, 왜 많이 사용되나요?

리액트는 웹 화면을 컴포넌트라는 작은 단위로 나누어 만들게 도와주는 프론트엔드 도구입니다. 컴포넌트는 화면의 재사용 가능한 부분이라고 이해하면 쉽습니다. 예를 들어 버튼, 카드, 검색창, 댓글 목록 같은 것을 각각 하나의 컴포넌트처럼 다룰 수 있습니다.

리액트가 많이 사용되는 이유는 단순히 유명해서가 아닙니다. 화면이 복잡해질수록 상태 변화와 재사용을 다루기 쉬운 구조를 제공하기 때문입니다. 특히 현대 웹 서비스처럼 로그인 상태, 목록 필터, 실시간 입력 반영, 화면 조각의 재사용이 많은 상황에서 강점을 보입니다.

리액트를 꼭 당장 써야 한다는 뜻은 아닙니다. 하지만 리액트가 왜 널리 쓰이는지 이해하면 현대 프론트엔드가 어떤 방향으로 발전해 왔는지 감을 잡을 수 있습니다. 과거에는 HTML 조각을 직접 조작하는 코드가 많았다면, 지금은 화면을 상태와 컴포넌트 중심으로 생각하는 경향이 강합니다.

예를 들어 좋아요 버튼을 만들 때, 예전 방식은 버튼의 모양과 문구를 직접 바꾸는 코드를 곳곳에 흩어 놓기 쉬웠습니다. 리액트는 현재 상태가 무엇인지 기준으로 화면을 다시 계산해 보여 주는 방식을 선호합니다. 이런 접근은 처음에는 낯설 수 있지만, 규모가 커질수록 관리가 쉬워집니다.

첫째, 생태계가 큽니다. 문서, 예제, 커뮤니티, 관련 라이브러리가 많아서 학습과 실무 모두 접근성이 좋습니다. 둘째, 컴포넌트 기반 구조가 재사용과 협업에 유리합니다. 팀이 같은 UI 조각을 여러 화면에서 공유하기 좋습니다. 셋째, 웹뿐 아니라 React Native 같은 생태계와도 연결되어 있어서, 개념을 옮겨 가며 쓸 수 있다는 장점이 있습니다.

또한 리액트는 특정 회사만의 도구로 남지 않고 넓은 생태계로 자리 잡았습니다. 그래서 채용 시장에서도 많이 등장하고, 많은 튜토리얼과 예제가 리액트를 기준으로 설명됩니다. 초보자가 자료를 찾기 쉽다는 점은 실제 학습 난이도에 큰 영향을 줍니다.

## 모바일 앱을 개발하는 언어 및 프레임워크는 무엇인가요?

모바일 앱 개발은 크게 두 방향으로 생각할 수 있습니다. 하나는 안드로이드와 아이폰 각각에 맞는 방식으로 만드는 것이고, 다른 하나는 하나의 코드베이스를 최대한 여러 플랫폼에 함께 활용하는 방식입니다. 어떤 쪽을 고르느냐에 따라 언어와 프레임워크 선택도 달라집니다.

안드로이드 쪽에서는 Kotlin과 Java가 자주 언급되고, 아이폰 쪽에서는 Swift가 중심입니다. 이런 방식은 보통 네이티브 앱 개발이라고 부릅니다. 네이티브라는 말은 해당 운영체제의 공식 도구와 구조에 맞춰 개발한다는 뜻입니다. 기기 기능 접근, 성능, 운영체제와의 자연스러운 통합에서 강점이 큽니다.

### 여러 플랫폼을 함께 노리는 방식도 있다

요즘은 React Native와 Flutter 같은 크로스플랫폼 프레임워크도 많이 사용됩니다. 크로스플랫폼은 여러 운영체제에 하나의 코드베이스를 최대한 공유해 대응하려는 접근입니다. React Native는 자바스크립트와 리액트 경험을 활용하기 좋고, Flutter는 Dart 언어와 자체 UI 렌더링 방식으로 일관된 화면 제어에 강점을 보입니다.

초보자에게 중요한 것은 이 도구들이 서로 경쟁하는 이름표가 아니라는 점입니다. 네이티브와 크로스플랫폼은 서로 다른 장단점을 가진 전략입니다. 특정 제품에서는 네이티브가 더 맞고, 다른 제품에서는 크로스플랫폼이 더 현실적일 수 있습니다.
