# 8장. 네트워크 기술

앱과 웹 서비스는 대부분 혼자 일하지 않습니다. 사용자 기기, 서버, 데이터베이스, 외부 서비스가 서로 끊임없이 데이터를 주고받습니다. 그래서 네트워크를 이해하지 못하면 서비스가 왜 느린지, 로그인은 왜 유지되는지, 요청은 어디서 막히는지, 캐시는 왜 필요한지 설명하기 어려워집니다. 8장은 이 통신의 큰 그림을 잡는 장입니다.

초보자는 네트워크를 종종 통신사나 장비 이야기로만 생각합니다. 물론 라우터와 스위치 같은 장비도 중요하지만, 개발자가 먼저 잡아야 할 것은 요청이 이동하는 흐름입니다. 브라우저에서 주소를 입력했을 때 무슨 일이 일어나는지, HTTP는 무엇을 약속하는지, 서버는 어떻게 응답을 준비하는지, 세션과 쿠키는 왜 필요한지가 모두 하나의 이야기로 이어집니다.

이 장을 읽고 나면 네트워크 용어를 따로 외우지 않아도 됩니다. 요청 한 번이 어디를 거쳐 가는지, 그 과정에서 각 기술이 어떤 역할을 맡는지 이해하면 됩니다. 그러면 이후의 인증, 캐시, 서버 배포, 클라우드 이야기도 훨씬 선명해집니다.

## 클라이언트 서버통신은 어떻게 되나요?

클라이언트와 서버의 통신은 아주 단순하게 말하면 요청과 응답의 흐름입니다. 클라이언트는 무엇이 필요하다고 요청하고, 서버는 그 요청을 받아 처리한 뒤 결과를 응답합니다. 여기서 클라이언트는 보통 브라우저나 모바일 앱 같은 사용자 쪽 프로그램이고, 서버는 데이터를 보관하거나 규칙을 처리하는 쪽 시스템입니다.

예를 들어 사용자가 쇼핑몰 앱에서 상품 상세 화면을 열면, 앱은 서버에 특정 상품 정보를 요청합니다. 서버는 데이터베이스나 캐시에서 필요한 정보를 가져와 정리한 뒤 응답을 보냅니다. 앱은 그 응답을 받아 화면에 상품 이름, 가격, 이미지, 재고 상태를 보여 줍니다. 사용자는 버튼만 눌렀을 뿐이지만, 그 뒤에서는 요청과 응답이 오갑니다.

### 왜 서버를 따로 두나요

모든 데이터를 사용자 기기에 넣어 둘 수 없고, 그렇게 해도 안 되기 때문입니다. 가격, 재고, 권한, 주문 상태처럼 계속 바뀌고 보호가 필요한 데이터는 서버에서 관리해야 합니다. 또한 여러 사용자가 같은 서비스를 함께 쓰므로, 누구에게 어떤 정보를 보여 줄지 중앙에서 통제할 필요가 있습니다.

서버는 단순히 데이터만 주는 곳이 아닙니다. 사용자가 로그인했는지 확인하고, 요청이 허용되는지 검증하고, 다른 시스템과 연동하고, 결과를 가공해 돌려줍니다. 즉, 서버는 저장소이면서 규칙 실행기입니다.

### 통신 과정은 왜 느려질 수 있나요

클라이언트와 서버는 물리적으로 떨어져 있으므로, 요청을 보내고 응답을 받는 데 시간이 걸립니다. 네트워크 상태가 나쁘거나 서버가 바쁘거나, 데이터베이스 조회가 오래 걸리거나, 응답 크기가 너무 크면 사용자는 지연을 느끼게 됩니다. 그래서 좋은 서비스는 통신 횟수를 줄이고, 응답을 가볍게 만들고, 캐시를 활용하고, 느린 작업은 비동기로 다루려 합니다.

초보자가 중요한 것은 오류를 볼 때 어느 쪽 문제인지 나눠 생각하는 습관입니다. 요청 자체가 안 나가는지, 서버가 에러를 내는지, 응답은 왔는데 화면에 반영이 안 되는지 구분해야 디버깅이 쉬워집니다.

### 초보자는 어떤 한 문장으로 기억하면 좋을까요

클라이언트는 필요를 말하고, 서버는 판단하고 돌려준다고 기억하면 됩니다. 이 단순한 구조가 웹, 모바일, 게임, IoT, 클라우드 서비스 대부분의 기본 흐름입니다.

이 감각을 잡으면 네트워크는 추상적인 기술이 아니라, 내가 만든 버튼이 실제로 어디와 대화하는지를 보여 주는 생활 언어가 됩니다.

### 핵심만 다시 정리하면

클라이언트 서버 통신은 요청과 응답의 구조로 이루어집니다. 클라이언트는 사용자 쪽 프로그램, 서버는 데이터와 규칙을 관리하는 쪽 시스템입니다. 개발자는 이 흐름을 이해할수록 어디에서 느려지고 어디에서 오류가 나는지 훨씬 정확하게 판단할 수 있습니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 요청-응답, 인증, 캐시, 서버 구조, 네트워크 장비와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 어디에서 응답 속도가 느려질지, 어디에 캐시를 둘지 판단할 때 이 개념이 다시 등장합니다.

## 웹 서버 접속 과정은 어떻게 되나요?

브라우저 주소창에 URL을 입력하고 엔터를 누르는 순간, 생각보다 많은 단계가 연달아 일어납니다. 초보자는 흔히 주소를 치면 바로 페이지가 뜬다고 느끼지만, 실제로는 주소 해석, 서버 찾기, 연결 맺기, 요청 전송, 응답 수신, 화면 해석이 순서대로 진행됩니다. 이 과정을 알면 웹 서비스가 느린 지점을 훨씬 잘 짚을 수 있습니다.

첫 단계는 URL 해석입니다. 브라우저는 사용자가 입력한 주소가 어떤 프로토콜을 쓰는지, 어느 서버를 가리키는지 파악합니다. 그다음 DNS를 통해 도메인 이름을 실제 서버의 IP 주소로 바꾸려 합니다. 사람은 `example.com`을 기억하지만, 네트워크 장비는 IP 주소를 기준으로 통신하기 때문입니다.

### 주소를 찾은 다음에는 무엇이 일어나나요

서버 주소를 알게 되면 브라우저는 네트워크 연결을 준비합니다. 보통 웹에서는 TCP 연결을 맺고, HTTPS라면 이어서 TLS라는 보안 절차를 통해 암호화 통신 준비를 합니다. 여기까지 끝나야 비로소 브라우저가 HTTP 요청을 보낼 수 있습니다. 즉, 요청 본문보다 먼저 길을 열고, 안전한 채널을 만드는 단계가 있습니다.

그다음 브라우저는 `GET /` 같은 요청을 보내고, 서버는 HTML, CSS, JavaScript, 이미지 같은 자원을 응답합니다. 브라우저는 이 응답을 받아 문서를 파싱하고, 필요한 추가 파일들을 다시 요청합니다. 그래서 페이지 하나가 뜰 때 실제로는 수십 개의 요청이 오갈 수도 있습니다.

### 사용자는 왜 기다리게 되나요

느려지는 지점은 여러 곳입니다. DNS 조회가 늦을 수도 있고, TLS 협상이 오래 걸릴 수도 있고, 서버 응답이 느릴 수도 있고, 브라우저가 받아 온 자원을 해석하는 데 시간이 걸릴 수도 있습니다. 즉, 페이지 로딩 시간은 네트워크와 서버와 브라우저 렌더링이 함께 만든 결과입니다.

초보자가 중요한 것은 느림을 무조건 서버 탓으로 보지 않는 것입니다. 어떤 경우는 서버 전에 DNS나 연결 단계가 느릴 수 있고, 어떤 경우는 응답은 빠른데 화면에서 자바스크립트가 무거워 늦게 보일 수 있습니다. 과정을 알고 나면 문제를 훨씬 세밀하게 나눠 볼 수 있습니다.

### 초보자는 이 흐름을 어떻게 기억하면 좋을까요

URL 입력, DNS 조회, 연결 수립, 보안 협상, HTTP 요청과 응답, 브라우저 렌더링이라는 순서만 기억해도 충분합니다. 이 여섯 단계는 웹 성능과 장애 분석의 기본 지도입니다.

이 지도를 머릿속에 넣어 두면 개발자 도구의 Network 탭을 볼 때도 단순한 숫자가 아니라 실제 여정으로 읽히기 시작합니다.

### 핵심만 다시 정리하면

웹 서버 접속은 URL 입력 후 곧바로 페이지가 뜨는 것이 아니라, DNS 조회, TCP 연결, TLS 협상, HTTP 요청과 응답, 브라우저 렌더링을 거치는 다단계 과정입니다. 느려짐은 이 어느 단계에서나 생길 수 있습니다. 이 순서를 이해하면 웹 서비스의 성능과 오류를 훨씬 구조적으로 볼 수 있습니다.

## 웹과 WAS의 역할은 어떻게 되나요?

웹 서버와 WAS를 구분하는 이유는 정적 자원을 빠르게 전달하는 일과, 애플리케이션 로직을 실행하는 일을 분리하기 위해서입니다. 웹 서버는 주로 요청을 받아 정적 파일을 전달하거나, 적절한 애플리케이션 서버로 연결을 넘기는 역할을 합니다. WAS는 Web Application Server의 약자로, 실제 비즈니스 로직을 수행하고 데이터베이스와 연결하며 동적인 응답을 만들어 냅니다.

예를 들어 이미지, CSS 파일, 자바스크립트 파일처럼 그대로 전달하면 되는 자원은 웹 서버가 잘 처리합니다. 반면 로그인 검증, 주문 생성, 재고 계산처럼 규칙과 데이터 처리가 필요한 일은 WAS가 담당합니다. 이렇게 나누면 역할이 명확해지고, 성능과 운영도 더 유리해질 수 있습니다.

### 왜 둘을 굳이 나누나요

정적 파일은 빠르고 단순하게 많이 처리하는 것이 중요합니다. 반면 동적 요청은 애플리케이션 코드 실행, 세션 확인, 데이터베이스 접근 같은 무거운 작업이 따릅니다. 이 둘을 한 덩어리로 두면 서로의 특성이 섞여 최적화가 어려워질 수 있습니다. 그래서 웹 서버가 앞단에서 가벼운 일을 처리하고, 복잡한 일만 WAS로 넘기는 구조가 널리 쓰였습니다.

또한 웹 서버는 리버스 프록시, SSL 종료, 캐시, 압축, 로드밸런싱 같은 기능을 맡기에도 좋습니다. WAS는 애플리케이션 코드 실행에 집중할 수 있으니 책임이 더 선명해집니다.

### 요즘도 이 구분이 그대로 유효한가요

현대에는 Node.js나 Go처럼 하나의 서버 프로세스가 정적 파일 제공과 애플리케이션 로직을 함께 처리하는 경우도 많습니다. 그래서 웹 서버와 WAS의 경계가 예전처럼 절대적인 것은 아닙니다. 그럼에도 앞단 프록시와 뒷단 애플리케이션 실행 계층을 구분하는 사고방식은 여전히 중요합니다.

특히 자바 계열 시스템에서는 WAS라는 표현이 오래 쓰였고, 대규모 서비스에서는 지금도 앞단 웹 서버나 프록시와 뒷단 앱 서버를 분리하는 구조가 흔합니다. 즉, 용어의 형태는 조금 바뀌어도 역할 분리의 원리는 그대로 남아 있습니다.

### 초보자가 가져가야 할 감각

웹 서버는 길목 관리와 정적 자원 처리, WAS는 동적 처리와 비즈니스 로직 수행이라고 기억하면 좋습니다. 완벽히 분리된 제품 이름보다, 어떤 계층이 어떤 책임을 맡는지 이해하는 것이 더 중요합니다.

이 감각이 있으면 배포 구조를 볼 때 nginx, Apache, Tomcat, Node 서버 같은 이름이 나와도 각각이 어디에 놓이는지 훨씬 쉽게 해석할 수 있습니다.

### 핵심만 다시 정리하면

웹 서버는 정적 자원 전달과 요청 분배에 강하고, WAS는 애플리케이션 로직과 동적 응답 생성에 강합니다. 현대에는 둘의 경계가 일부 흐려졌지만, 앞단에서 요청을 정리하고 뒷단에서 비즈니스 로직을 처리하는 역할 분리는 여전히 중요합니다. 초보자는 제품 이름보다 책임 분리를 먼저 이해하는 것이 좋습니다.

### 현업 장면으로 바꾸면 이렇게 보입니다

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 요청이 많아질 때 어떤 장비와 구조가 필요한지 가늠할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

결국 이 개념을 이해한다는 것은 네트워크 용어가 추상 이론이 아니라 흐름 설명 도구로 바뀝니다

### 여기서 많이 생기는 오해

요청, 전송 규칙, 상태 유지, 분산 처리, 장비 역할은 서로 다른 층이라는 점을 나눠 보는 편이 좋습니다. 그러면 비슷한 용어를 만나도 같은 상자에 모두 넣어 버리는 실수를 줄일 수 있습니다.

3. 로그인과 로그아웃, 새로고침, 쿠키 삭제를 직접 해 보며 상태가 어디서 유지되는지 확인해 봅니다.

## 웹 애플리케이션의 캐시

캐시는 자주 쓰는 데이터를 더 가까운 곳에 잠시 보관해 같은 일을 반복하지 않게 하는 장치입니다. 웹 애플리케이션에서 캐시가 중요한 이유는 요청이 올 때마다 매번 서버 계산과 데이터베이스 조회를 처음부터 다 하면 느리고 비싸기 때문입니다. 자주 바뀌지 않는 결과를 적절히 저장해 두면 사용자도 빨라지고 서버 부담도 줄어듭니다.

초보자는 캐시를 그냥 속도 올리는 기능 정도로만 생각하기 쉽지만, 실제로는 어디에 캐시를 두느냐가 중요합니다. 브라우저 안에 둘 수도 있고, CDN 같은 중간 네트워크에 둘 수도 있고, 서버 메모리나 별도 캐시 저장소에 둘 수도 있습니다. 즉, 캐시는 한 종류의 기술이 아니라 여러 위치에서 쓰이는 전략입니다.

### 웹에서 캐시는 어디에 생기나요

브라우저 캐시는 이미지, CSS, 자바스크립트 파일처럼 자주 바뀌지 않는 자원을 사용자의 기기 안에 저장해 둡니다. 같은 페이지를 다시 열 때 네트워크 요청을 줄여 주므로 체감 속도에 큰 영향을 줍니다. CDN 캐시는 사용자와 가까운 지역에서 정적 자원을 전달해 지연을 줄여 줍니다.

서버 쪽에서는 자주 조회되는 데이터나 계산 결과를 메모리에 두어 데이터베이스 부하를 줄일 수 있습니다. 예를 들어 메인 화면 인기 상품 목록이나 국가 코드 목록처럼 자주 읽고 자주 바뀌지 않는 데이터는 캐시에 잘 맞습니다. 즉, 캐시는 브라우저, 네트워크, 서버 여러 층에서 동시에 활용될 수 있습니다.

### 캐시는 왜 어렵다고 하나요

가장 어려운 점은 언제 지울지입니다. 오래된 데이터를 계속 보여 주면 빨라 보이더라도 틀린 정보를 제공하게 됩니다. 이를 캐시 무효화 문제라고 합니다. 가격이 바뀌었는데 옛 가격이 보이거나, 수정한 프로필 사진이 안 바뀌는 상황이 대표적입니다.

그래서 캐시는 무조건 많이 쓰는 것이 정답이 아닙니다. 무엇이 자주 바뀌고 무엇이 거의 안 바뀌는지 구분해야 합니다. 정적 파일은 긴 캐시가 유리하지만, 실시간 재고 정보는 더 신중해야 합니다. 즉, 캐시는 성능과 최신성 사이의 균형 문제입니다.

### 초보자는 어떻게 이해하면 좋을까요

캐시는 한 번 계산한 답을 가까이 적어 두는 메모라고 생각하면 됩니다. 덕분에 매번 처음부터 묻지 않아도 되지만, 메모가 낡았는지 확인하는 규칙이 함께 필요합니다. 이 두 요소를 함께 생각해야 캐시를 제대로 이해할 수 있습니다.

이 관점을 잡으면 브라우저 새로고침, CDN, Redis, 응답 헤더, 만료 시간 같은 개념도 모두 하나의 흐름으로 보이게 됩니다.

### 핵심만 다시 정리하면

캐시는 자주 쓰는 데이터를 가까운 곳에 저장해 속도와 비용을 개선하는 전략입니다. 웹에서는 브라우저, CDN, 서버 등 여러 층에서 캐시가 사용됩니다. 다만 오래된 데이터를 보여 주지 않도록 무효화 규칙을 함께 설계해야 하므로, 캐시는 단순한 가속 기능이 아니라 성능과 최신성의 균형 기술입니다.

### 이 개념이 실전에서 빛나는 순간

이 개념은 초보자에게는 이론처럼 보이지만, 조금만 실제 장면으로 옮겨 보면 매우 실용적인 기준이 됩니다. 브라우저와 서버 사이에서 무슨 일이 벌어지는지 추적할 때 특히 그렇습니다.

이 절을 제대로 소화하면 속도 문제와 인증 문제를 같은 눈으로 추적할 수 있게 됩니다

요청, 전송 규칙, 상태 유지, 분산 처리, 장비 역할은 서로 다른 층이라는 점을 나눠 보는 편이 좋습니다. 초보자에게 필요한 것은 어려운 설명보다 분명한 경계입니다.

1. 브라우저 개발자 도구의 Network 탭을 열고 이 주제와 관련된 요청 하나를 끝까지 따라가 봅니다.

## 프로토콜이란 무엇인가요?

프로토콜은 통신할 때 지켜야 하는 규칙입니다. 사람끼리 대화할 때도 언어와 순서와 예절이 있듯이, 컴퓨터끼리 데이터를 주고받을 때도 형식과 절차가 필요합니다. 어떤 형식으로 보내는지, 누가 먼저 말하는지, 오류가 나면 어떻게 처리하는지, 연결을 어떻게 맺고 끊는지가 정해져 있어야 통신이 가능합니다.

초보자는 프로토콜을 종종 특정 프로그램 이름처럼 오해합니다. 하지만 프로토콜은 앱이 아니라 약속입니다. HTTP, TCP, IP, DNS, SMTP 같은 이름은 각각 다른 목적의 통신 규칙을 뜻합니다. 즉, 프로토콜은 소프트웨어가 아니라 소프트웨어와 장치가 따르는 공통 문법에 가깝습니다.

### 왜 규칙이 이렇게 많이 필요한가요

네트워크 통신은 단순히 데이터를 한 번 보내고 끝나는 일이 아닙니다. 상대를 찾아야 하고, 길을 정해야 하고, 중간에 손실이 났는지 확인해야 하고, 보안도 챙겨야 합니다. 그래서 한 가지 규칙만으로 모든 문제를 해결하기 어렵습니다. 각 층마다 다른 프로토콜이 역할을 나누어 맡습니다.

예를 들어 IP는 데이터가 어느 주소로 가야 하는지와 관련이 있고, TCP는 데이터가 빠지지 않고 순서대로 도착하도록 돕습니다. HTTP는 그 위에서 웹 요청과 응답을 어떤 형식으로 주고받을지 정의합니다. 즉, 프로토콜은 계층적으로 쌓여 동작합니다.

### 개발자는 프로토콜을 어디서 체감하나요

브라우저에서 API를 호출할 때 HTTP를 직접 체감하고, 이메일 시스템을 다룰 때 SMTP를, 데이터베이스 연결에서는 또 다른 전용 프로토콜을 체감합니다. 인증과 보안에서도 TLS 같은 규칙이 중요합니다. 따라서 개발자는 특정 제품을 쓰더라도 그 아래에서 어떤 프로토콜이 움직이는지 알면 문제를 훨씬 잘 해석할 수 있습니다.

예를 들어 요청이 서버에 도달하지 않는다면 HTTP 코드만 볼 일이 아니라 DNS, TCP 연결, TLS 협상 같은 아래 단계도 살펴봐야 할 수 있습니다. 프로토콜을 이해하면 어디에서 규칙이 어긋났는지 더 정확히 볼 수 있습니다.

### 초보자가 기억할 한 문장

프로토콜은 컴퓨터끼리 말이 통하게 해 주는 통신 규칙입니다. 데이터를 보내는 형식과 절차를 맞추는 약속이 없다면, 네트워크는 성립할 수 없습니다.

이 한 문장만 선명해도 TCP, HTTP, HTTPS, WebSocket 같은 단어를 볼 때 모두 서로 다른 규칙의 이름으로 이해할 수 있습니다.

### 핵심만 다시 정리하면

프로토콜은 컴퓨터와 프로그램이 통신할 때 지켜야 하는 규칙입니다. 각 프로토콜은 주소 찾기, 신뢰성 보장, 웹 요청 형식 정의처럼 서로 다른 역할을 맡습니다. 초보자는 프로토콜을 특정 앱이 아니라 통신의 문법으로 이해하는 것이 중요합니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 요청-응답, 인증, 캐시, 서버 구조, 네트워크 장비와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 어디에서 응답 속도가 느려질지, 어디에 캐시를 둘지 판단할 때 이 개념이 다시 등장합니다.

## TCP/IP vs HTTP

TCP/IP와 HTTP는 경쟁하는 두 기술이 아니라, 서로 다른 층에서 협력하는 규칙입니다. 초보자가 자주 혼동하는 이유는 둘 다 네트워크 통신에서 자주 등장하기 때문입니다. 하지만 HTTP는 웹에서 무엇을 요청하고 어떻게 응답할지에 가까운 규칙이고, TCP/IP는 그 데이터가 실제로 어디로 가고 얼마나 신뢰성 있게 전달될지를 다루는 더 아래층 규칙입니다.

IP는 데이터를 어느 주소로 보낼지 결정하는 데 초점을 둡니다. 쉽게 말해 목적지를 찾는 규칙입니다. TCP는 그 데이터가 중간에 빠지지 않고, 순서가 뒤섞이지 않게 전달되도록 돕습니다. 반면 HTTP는 브라우저가 서버에 어떤 문서를 요청하고, 서버가 어떤 상태 코드와 본문으로 응답할지 정합니다.

### 왜 둘을 따로 이해해야 하나요

브라우저에서 페이지를 열 때 사용자는 HTTP 요청을 보지만, 그 요청이 실제로 움직이기 위해서는 보통 TCP/IP 층의 도움이 필요합니다. 주소를 찾아 가고, 연결을 맺고, 데이터를 나눠 보내고, 다시 조립하는 일은 아래층이 담당합니다. 즉, HTTP만 알아서는 통신 전체를 설명할 수 없고, TCP/IP만 알아서는 웹 요청의 의미를 설명할 수 없습니다.

이 차이는 문제를 볼 때 특히 중요합니다. HTTP 500 에러는 서버 애플리케이션 문제일 수 있지만, TCP 연결 실패는 서버에 닿기도 전에 생긴 문제일 수 있습니다. 어느 층에서 문제가 발생했는지 구분해야 해결 방향도 달라집니다.

### 초보자는 어떻게 외우면 좋을까요

TCP/IP는 길을 찾고 안전하게 실어 나르는 운송 체계, HTTP는 그 위에서 어떤 내용을 주문하고 돌려줄지 정하는 업무 규칙이라고 생각하면 됩니다. 하나는 운송, 하나는 의미 있는 대화입니다. 둘이 함께 있어야 웹이 동작합니다.

물론 현실의 네트워크는 더 많은 층과 프로토콜로 이루어져 있지만, 초보자가 처음 잡아야 할 감각은 이것으로 충분합니다. 아래층은 전달을, 위층은 의미를 담당한다는 구분입니다.

### 핵심만 다시 정리하면

TCP/IP는 주소 찾기와 신뢰성 있는 전달을 담당하는 아래층의 통신 규칙이고, HTTP는 웹에서 요청과 응답의 의미를 정의하는 위층의 규칙입니다. 둘은 대체재가 아니라 협력 관계입니다. 이 차이를 이해하면 네트워크 문제를 어느 층에서 봐야 하는지 훨씬 분명해집니다.

## HTTP는 무엇인가요?

HTTP는 웹에서 클라이언트와 서버가 요청과 응답을 주고받는 방법을 정한 프로토콜입니다. 브라우저가 페이지를 달라고 하거나, 앱이 서버에 데이터를 보낼 때 가장 자주 보게 되는 규칙입니다. 초보자는 HTTP를 인터넷 전체와 같은 뜻으로 받아들이기도 하지만, 더 정확히는 웹 통신의 문법이라고 보는 편이 맞습니다.

HTTP 요청에는 보통 무엇을 원하는지, 어떤 방식으로 원하는지, 추가 정보가 무엇인지가 담깁니다. 예를 들어 `GET`은 조회, `POST`는 새 데이터 전송이나 생성에 자주 쓰입니다. 응답에는 결과 본문뿐 아니라 상태 코드와 헤더가 포함됩니다. 상태 코드는 200, 404, 500처럼 결과 상태를 숫자로 알려 주고, 헤더는 캐시, 인증, 데이터 형식 같은 부가 정보를 전달합니다.

### HTTP를 이해하면 왜 좋은가요

많은 웹 개발 문제는 결국 HTTP 레벨에서 드러납니다. 요청 메서드가 맞는지, 응답 상태 코드가 무엇인지, 헤더가 올바른지, 본문 형식이 JSON인지 파일인지에 따라 동작이 달라집니다. 네트워크 탭에서 보이는 정보 대부분이 HTTP 수준의 정보이기 때문에, 이 개념을 이해하면 디버깅이 훨씬 쉬워집니다.

또한 HTTP는 원래 무상태에 가깝게 설계되어 있어, 요청 하나하나가 독립적으로 처리되기 쉽습니다. 이 때문에 로그인 상태 유지나 사용자별 맞춤 동작을 하려면 쿠키, 세션, 토큰 같은 추가 장치가 등장합니다. 즉, HTTP를 이해하면 왜 인증 기술이 따로 필요한지도 함께 보이게 됩니다.

### 요청과 응답을 어떻게 읽어야 하나요

초보자는 본문 데이터만 보고 싶어 하지만, 실무에서는 상태 코드와 헤더가 매우 중요합니다. 200은 성공, 301과 302는 이동, 401은 인증 필요, 403은 금지, 404는 없음, 500은 서버 내부 오류처럼 읽을 수 있습니다. 헤더에는 콘텐츠 타입, 캐시 정책, 인증 정보, 쿠키 등 중요한 정보가 담깁니다.

즉, HTTP는 단지 데이터를 실어 나르는 통로가 아니라, 요청의 의도와 응답의 의미를 풍부하게 표현하는 구조입니다. 이 구조를 읽을 수 있으면 브라우저 개발자 도구와 API 문서가 훨씬 덜 낯설어집니다.

### 초보자가 꼭 기억해야 할 한 가지

HTTP는 웹에서 대화를 하는 규칙이라는 점입니다. 누가 무엇을 원하고, 어떤 형식으로 주고받고, 결과가 성공인지 실패인지 합의하는 규칙입니다. 그 합의가 있기 때문에 브라우저와 서버와 API 도구들이 서로 통할 수 있습니다.

이 감각만 분명해도 HTTP는 더 이상 어려운 약자가 아니라, 웹 개발의 기본 문장 구조로 보이기 시작합니다.

### 핵심만 다시 정리하면

HTTP는 웹에서 요청과 응답의 형식과 의미를 정하는 프로토콜입니다. 메서드, 상태 코드, 헤더, 본문이 함께 동작하며 웹 서비스의 기본 대화를 이룹니다. 개발자는 HTTP를 이해할수록 API 문서와 네트워크 오류를 훨씬 더 정확하게 읽을 수 있습니다.

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 요청이 많아질 때 어떤 장비와 구조가 필요한지 가늠할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

## 웹 서버 접속 과정은 어떻게 되나요? (서버 안쪽에서 보는 흐름)

사용자의 HTTP 요청이 도착하면 먼저 웹 서버나 리버스 프록시가 그 요청을 받습니다. 여기서 SSL 종료를 하거나, 정적 파일 요청이면 바로 응답하거나, 동적 요청이면 적절한 애플리케이션 서버로 전달할 수 있습니다. 애플리케이션 서버는 요청 내용을 해석해 인증을 확인하고, 비즈니스 규칙을 수행하며, 필요한 데이터를 읽거나 씁니다.

### 애플리케이션 서버 뒤에서는 어떤 일이 벌어지나요

애플리케이션 서버는 보통 데이터베이스, 캐시, 메시지 큐, 외부 API 같은 여러 시스템과 통신합니다. 예를 들어 상품 상세 요청이라면 먼저 캐시에 결과가 있는지 보고, 없으면 데이터베이스에서 상품 정보를 읽고, 필요한 경우 재고 시스템이나 추천 시스템의 정보를 합칠 수도 있습니다. 처리 결과가 준비되면 JSON이나 HTML 형태로 응답을 만들고 다시 앞단으로 돌려보냅니다.

앞단 웹 서버는 이 응답을 받아 클라이언트에게 전달합니다. 경우에 따라 응답 헤더를 조정하거나 압축하거나 캐시 정책을 붙일 수도 있습니다. 즉, 서버 내부에서도 요청 하나가 여러 층을 지나며 가공됩니다.

### 왜 이렇게 여러 단계를 거치나요

단순히 복잡해 보이기 위해서가 아닙니다. 요청을 분산하고, 정적 파일 처리와 동적 처리를 나누고, 데이터 접근을 효율화하고, 장애 범위를 줄이기 위해서입니다. 앞단 계층이 없으면 애플리케이션 서버가 불필요한 부담을 모두 떠안게 되고, 캐시 계층이 없으면 데이터베이스로 요청이 몰릴 수 있습니다.

또한 이런 분리는 운영에도 유리합니다. 어떤 층이 느린지 모니터링하기 쉽고, 필요한 계층만 확장하기도 쉬워집니다. 예를 들어 트래픽이 늘었을 때 앱 서버만 늘릴지, 캐시를 강화할지, DB 읽기 구조를 나눌지 판단할 수 있습니다.

### 초보자는 어떤 그림으로 기억하면 좋을까요

클라이언트 요청이 서버 문 앞에 오면, 길목 관리자 역할의 웹 서버가 먼저 받고, 실제 업무 담당자인 애플리케이션 서버가 일을 처리하고, 기록 보관소인 데이터베이스와 캐시가 뒷받침한다고 생각하면 됩니다. 하나의 요청도 내부에서는 여러 담당자를 거친다는 감각이 중요합니다.

이 그림을 머릿속에 넣어 두면 로드밸런서, 캐시, WAS, DB, 메시지 큐 같은 단어가 각각 어디에 붙는지 훨씬 쉽게 이해할 수 있습니다.

### 핵심만 다시 정리하면

서버에 도착한 요청은 보통 웹 서버나 리버스 프록시를 거쳐 애플리케이션 서버로 전달되고, 그 안에서 데이터베이스와 캐시 등 여러 시스템을 거쳐 처리됩니다. 이 다단계 구조는 성능, 확장성, 운영 편의성을 위해 필요합니다. 초보자는 서버를 하나의 검은 상자가 아니라 여러 역할 계층의 협업 구조로 보는 것이 좋습니다.

## 세션과 쿠키는 무엇인가요?

HTTP는 기본적으로 요청 하나하나가 독립적으로 처리되는 성격이 강합니다. 그래서 사용자가 로그인한 상태인지, 장바구니에 무엇을 담았는지, 어떤 언어 설정을 선택했는지 같은 정보를 유지하려면 별도의 장치가 필요합니다. 이때 자주 등장하는 것이 쿠키와 세션입니다.

쿠키는 브라우저에 저장되는 작은 데이터 조각입니다. 서버가 응답할 때 쿠키를 내려주면 브라우저는 그것을 저장해 두었다가 이후 같은 사이트에 요청할 때 함께 보낼 수 있습니다. 세션은 보통 서버 쪽에서 사용자 상태를 관리하는 방식입니다. 서버는 사용자를 구분할 수 있는 세션 식별자를 만들고, 그 식별자를 쿠키에 담아 브라우저에 보내는 식으로 자주 구현합니다.

### 둘은 어떻게 협력하나요

많은 초보자가 세션과 쿠키를 대체재로 생각하지만, 현실에서는 같이 쓰이는 경우가 많습니다. 서버는 로그인한 사용자의 상태를 세션 저장소에 보관하고, 브라우저는 그 세션을 가리키는 식별자를 쿠키로 들고 있습니다. 다음 요청이 오면 서버는 쿠키에 담긴 식별자를 보고 이 사용자가 누구인지 찾아냅니다.

즉, 쿠키는 전달 수단에 가깝고, 세션은 서버 측 상태 관리 방식에 가깝습니다. 물론 쿠키에 직접 일부 설정 값을 담는 경우도 있고, 세션을 전혀 쓰지 않는 구조도 있습니다. 하지만 기본 감각은 브라우저 쪽 저장과 서버 쪽 상태 관리의 조합입니다.

### 왜 둘을 구분해서 이해해야 하나요

보안과 확장성 문제 때문입니다. 중요한 사용자 상태를 브라우저에 그대로 넣는 것은 위험할 수 있습니다. 반면 서버에만 상태를 두면 어느 서버가 그 정보를 갖고 있는지, 서버가 여러 대일 때 어떻게 공유할지 고민해야 합니다. 그래서 쿠키와 세션은 편의성과 보안 사이의 절충을 반영합니다.

또한 쿠키는 크기가 작고 요청마다 함께 전송되므로 너무 많은 정보를 넣는 데 적합하지 않습니다. 세션은 서버 자원을 사용하므로 사용자 수가 많아질수록 관리 전략이 필요합니다. 따라서 이 둘은 단순한 저장 기능이 아니라 로그인과 상태 유지를 설계하는 핵심 요소입니다.

### 초보자는 어떤 한 문장으로 기억하면 좋을까요

쿠키는 브라우저가 들고 다니는 작은 메모, 세션은 서버가 사용자 상태를 보관하는 보관함이라고 기억하면 좋습니다. 둘이 연결되면서 우리는 새로고침을 해도 로그인 상태를 이어 갈 수 있습니다.

이 감각이 잡히면 로그인 유지, 장바구니, 사용자 맞춤 설정 같은 기능이 어떻게 가능한지 훨씬 자연스럽게 이해하게 됩니다.

### 핵심만 다시 정리하면

쿠키는 브라우저에 저장되는 작은 데이터이고, 세션은 보통 서버가 사용자 상태를 관리하는 방식입니다. 실제 서비스에서는 세션 식별자를 쿠키로 전달하는 식으로 둘이 함께 쓰이는 경우가 많습니다. 이 구분을 알면 로그인 유지와 상태 관리 구조를 훨씬 정확하게 이해할 수 있습니다.

## JWT란 무엇인가요?

JWT는 JSON Web Token의 약자로, 사용자 정보나 권한 같은 클레임을 담아 서명된 형태로 전달하는 토큰 방식입니다. 초보자는 JWT를 로그인 그 자체로 오해하기 쉽지만, 더 정확히 말하면 인증과 권한 확인에 활용될 수 있는 전달 형식입니다. 즉, 사용자를 증명하는 정보 조각을 네트워크에서 다루기 쉽게 만든 포맷입니다.

JWT는 보통 점으로 나뉜 세 부분으로 이루어집니다. 헤더, 페이로드, 서명입니다. 페이로드에는 사용자 아이디, 만료 시간, 역할 같은 정보가 들어갈 수 있고, 서명은 이 내용이 임의로 바뀌지 않았는지 검증하는 데 사용됩니다. 여기서 중요한 점은 서명은 위조 방지에 가깝지, 내용 자체를 숨기는 암호화와는 다를 수 있다는 것입니다.

### 왜 JWT가 널리 쓰였나요

서버가 모든 로그인 상태를 별도 세션 저장소에 보관하지 않아도, 토큰 안에 필요한 정보를 담아 비교적 간편하게 검증할 수 있기 때문입니다. 특히 여러 서버가 분산된 환경이나 모바일 앱, 외부 API 연동 환경에서는 토큰 기반 인증이 편리할 때가 많습니다. 클라이언트는 로그인 후 받은 토큰을 보관했다가 이후 요청에 함께 보냅니다.

서버는 토큰 서명을 확인하고, 만료 여부를 보고, 필요한 권한 정보를 읽어 요청을 처리할 수 있습니다. 이렇게 하면 세션 저장소 의존성을 줄일 수 있지만, 대신 토큰 발급과 갱신, 만료 전략을 잘 설계해야 합니다.

### JWT를 쓸 때 자주 생기는 오해

첫째, JWT는 암호화된 비밀 상자가 아닙니다. 기본적으로는 인코딩과 서명이 중심이므로, 민감한 정보를 무턱대고 넣으면 안 됩니다. 둘째, JWT를 쓴다고 해서 자동으로 더 안전해지는 것도 아닙니다. 탈취되면 위험할 수 있으므로 저장 위치, 만료 시간, 재발급 방식, HTTPS 사용 여부가 중요합니다.

셋째, JWT가 모든 로그인 구조의 정답도 아닙니다. 관리가 간단한 세션 기반 구조가 더 적절한 경우도 많습니다. 즉, JWT는 유행어가 아니라 상황에 맞는 선택지입니다.

### 초보자는 어떻게 이해하면 좋을까요

JWT는 사용자에 대한 몇 가지 정보를 담은 신분증 비슷한 토큰이라고 생각하면 됩니다. 서버는 그 신분증이 위조되지 않았는지 확인하고, 유효 기간과 권한 정보를 보고 요청을 처리합니다. 다만 신분증을 들고 다니는 방식인 만큼 잃어버렸을 때의 위험과 갱신 규칙도 함께 생각해야 합니다.

이 감각을 잡으면 인증 구조를 볼 때 세션 기반인지 토큰 기반인지, 그리고 왜 그런 선택을 했는지 조금 더 분명하게 읽을 수 있습니다.

### 핵심만 다시 정리하면

JWT는 사용자 정보와 권한 정보를 담아 서명된 형태로 전달하는 토큰 포맷입니다. 서버는 이를 검증해 인증과 권한 확인에 활용할 수 있습니다. 편리하지만 만능은 아니며, 저장 방식과 만료 전략과 보안 설계가 함께 따라와야 합니다.

## 라우터, 스위치, 로드밸런서는 무엇인가요?

쉽게 말하면 스위치는 같은 건물 안에서 어느 방으로 보낼지 정하는 역할, 라우터는 다른 건물로 가는 길을 찾는 역할, 로드밸런서는 손님을 여러 직원에게 적절히 나눠 주는 역할이라고 생각할 수 있습니다. 이름이 비슷해 보여도 문제를 해결하는 층이 다릅니다.

특히 로드밸런서는 개발자에게 매우 가깝습니다. 서버가 여러 대일 때 요청을 고르게 나누고, 특정 서버가 죽으면 다른 서버로 보내고, 헬스 체크를 통해 장애 대응을 돕는 구조가 자주 등장하기 때문입니다. 대규모 서비스에서 확장성과 가용성을 이야기할 때 거의 빠지지 않는 개념입니다.

같은 네트워크 내부에서 장치끼리 연결하는 일과, 서로 다른 네트워크를 이어 주는 일은 성격이 다르기 때문입니다. 스위치는 주로 가까운 내부 연결을 효율적으로 다루고, 라우터는 더 넓은 범위에서 어느 길로 보내야 할지 판단합니다. 인터넷 자체도 수많은 라우팅 결정의 집합입니다.

## 통신에서 동기와 비동기는 어떻게 다른가요?

통신에서 동기와 비동기의 차이는 응답을 기다리는 방식과 결과를 받는 시점에 있습니다. 동기 통신은 요청을 보내고 바로 그 자리에서 응답을 기다리는 흐름에 가깝습니다. 비동기 통신은 요청을 보내고 나서, 결과가 나중에 다른 경로로 오거나 나중 시점에 확인하도록 설계된 흐름에 가깝습니다.

예를 들어 상품 정보를 조회하는 API는 보통 즉시 결과가 필요하므로 동기 요청이 자연스럽습니다. 반면 대용량 파일 변환, 이메일 발송, 영상 인코딩처럼 시간이 오래 걸리는 작업은 요청을 받은 뒤 바로 완료 응답을 주기 어렵습니다. 이럴 때는 작업 접수만 먼저 알려 주고, 나중에 결과를 조회하게 하거나 이벤트로 알려 주는 비동기 방식이 더 잘 맞습니다.

### 왜 둘을 나눠 생각해야 하나요

모든 통신을 동기로 처리하면 오래 걸리는 작업이 전체 응답 시간을 끌어올립니다. 사용자는 화면이 멈췄다고 느낄 수 있고, 서버도 대기 시간이 길어집니다. 반대로 모든 것을 비동기로 바꾸면 구조가 복잡해지고, 결과를 언제 어떻게 확인할지 추가 설계가 필요합니다. 결국 핵심은 사용자 경험과 시스템 성격에 맞는 리듬을 선택하는 것입니다.

동기 통신은 단순하고 이해하기 쉽습니다. 요청과 응답이 한 쌍으로 묶여 있어 흐름을 추적하기 편합니다. 비동기 통신은 확장성과 처리량에서 이점이 있지만, 메시지 큐, 웹훅, 재시도, 중복 처리 같은 추가 고민이 필요할 수 있습니다.

### 실무에서는 어떤 식으로 쓰이나요

결제 승인 결과 조회, 로그인, 상품 검색처럼 즉시 보여 줘야 하는 기능은 동기 통신이 많습니다. 반면 주문 완료 후 알림 발송, 통계 집계, 추천 모델 업데이트, 대용량 업로드 후 변환 작업은 비동기 처리에 잘 맞습니다. 겉으로는 같은 서비스 안에서도 내부 구현은 동기와 비동기가 섞여 있을 수 있습니다.

초보자가 중요한 것은 비동기가 무조건 더 고급이라는 식의 오해를 버리는 것입니다. 어떤 작업은 동기가 가장 자연스럽고, 어떤 작업은 비동기로 풀어야 시스템이 건강해집니다. 문제의 성격을 보는 눈이 더 중요합니다.

### 초보자는 어떤 한 문장으로 기억하면 좋을까요

지금 바로 답이 필요한가, 아니면 접수만 하고 나중에 결과를 받아도 되는가를 기준으로 생각하면 됩니다. 이 질문이 통신 구조를 나누는 가장 쉬운 출발점입니다.
