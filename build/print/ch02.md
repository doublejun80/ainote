# 2장. 소프트웨어의 종류와 특징

이 장에서는 초보자가 가장 자주 헷갈리는 분류를 정리합니다. 웹과 앱의 차이, 프론트엔드와 백엔드의 차이, 웹 애플리케이션이 무엇인지 같은 질문은 개발 공부 초반에 거의 반드시 나옵니다.

이 부분이 중요한 이유는, 이름이 비슷하다고 해서 역할까지 같은 것은 아니기 때문입니다. 용어를 대충 알아듣는 상태로 넘어가면 뒤에서 배우는 네트워크, 데이터베이스, 아키텍처 내용이 모두 흐려집니다. 반대로 여기서 구분을 잘 잡아 두면 다음 장으로 갈수록 이해가 훨씬 쉬워집니다.

## 이 장에서 특히 주의할 점

이 장은 정의만 외우는 식으로 읽으면 금방 헷갈립니다. 대신 세 가지 기준을 붙잡고 읽는 것이 좋습니다. 첫째, 어디서 실행되는가. 둘째, 누가 직접 만지는가. 셋째, 무엇을 책임지는가. 이 세 가지 기준으로 보면 비슷해 보이는 말들도 꽤 분명하게 갈라집니다.

## 장을 읽고 나면

이 장을 읽고 나면 최소한 다음 정도는 설명할 수 있어야 합니다. 웹과 앱이 왜 다른지, 프론트엔드와 백엔드가 무엇을 나누어 맡는지, 그리고 웹 애플리케이션 개발이 단순히 홈페이지를 만드는 일이 아닌 이유가 무엇인지 말입니다.

## 소프트웨어의 종류

소프트웨어라고 하면 많은 사람이 일단 휴대폰 앱이나 컴퓨터 프로그램부터 떠올립니다. 물론 그것도 소프트웨어가 맞습니다. 하지만 소프트웨어라는 말은 훨씬 넓습니다. 우리가 직접 사용하는 앱뿐 아니라, 그 앱이 돌아가게 만드는 운영체제, 데이터를 저장하는 데이터베이스, 개발자가 쓰는 편집기와 테스트 도구까지 모두 소프트웨어에 들어갑니다.

그래서 이 개념을 이해한다는 것은 이름을 외우는 일이 아니라, "이 소프트웨어는 무슨 역할을 하는가"를 구분하는 일에 가깝습니다. 이 역할 구분이 잡히면 나중에 새로운 기술 이름을 만나도 덜 흔들립니다.

### 가장 먼저 나눌 수 있는 큰 분류

가장 이해하기 쉬운 기준은 두 가지입니다. 하나는 컴퓨터나 기기 전체가 돌아가도록 돕는 소프트웨어이고, 다른 하나는 사용자가 직접 목적을 이루기 위해 쓰는 소프트웨어입니다.

첫 번째 부류를 흔히 시스템 소프트웨어라고 부릅니다. 운영체제, 장치와 연결되는 드라이버, 프로그램 실행을 돕는 여러 기반 소프트웨어가 여기에 들어갑니다. 사용자는 직접 보지 못하는 경우가 많지만, 이것이 없으면 다른 프로그램도 돌아갈 수 없습니다.

두 번째 부류는 응용 소프트웨어라고 생각하면 됩니다. 메신저, 문서 작성 프로그램, 쇼핑 앱, 사진 편집기처럼 사용자가 직접 만지는 대부분의 제품이 여기에 속합니다. 사용자는 보통 이 부류를 가장 먼저 소프트웨어라고 떠올립니다.

### 개발 도구와 플랫폼은 어디에 들어가나

여기서 한 번 더 헷갈리기 쉬운 것이 개발 도구와 플랫폼입니다. 개발 도구는 개발자가 소프트웨어를 만들기 위해 사용하는 프로그램입니다. 코드 편집기, 버전 관리 도구, 빌드 도구, 테스트 도구가 대표적입니다. 사용자가 직접 쓰는 제품은 아니지만, 제품을 만들기 위해 꼭 필요합니다.

플랫폼은 조금 더 넓은 개념입니다. 다른 소프트웨어가 그 위에서 만들어지고 실행될 수 있게 기반을 제공하는 환경이라고 보면 됩니다. 운영체제도 큰 의미에서는 플랫폼이고, 클라우드 플랫폼이나 앱 마켓 생태계, 애플리케이션 서버 같은 것도 플랫폼이라고 부를 수 있습니다. 초보자에게 중요한 것은 플랫폼이라는 말이 자주 "다른 것을 올려서 쓰는 기반"이라는 뜻으로 쓰인다는 점입니다.

### 실무에서는 왜 이 구분이 중요한가

실무에서 하나의 서비스는 보통 한 종류의 소프트웨어만으로 이루어지지 않습니다. 예를 들어 쇼핑 서비스를 운영한다면 고객이 사용하는 모바일 앱은 응용 소프트웨어입니다. 그 앱이 데이터를 불러오는 서버도 소프트웨어입니다. 서버가 돌아가는 운영체제도 소프트웨어이고, 개발자가 오류를 찾기 위해 쓰는 로그 도구와 배포 도구도 소프트웨어입니다.

이처럼 실제 현장에서는 여러 종류의 소프트웨어가 겹겹이 쌓여 움직입니다. 그래서 초보자도 "내가 지금 다루는 것은 사용자용 제품인지, 기반인지, 개발 도구인지" 정도는 구분할 수 있어야 합니다.

### 무엇과 무엇을 자주 헷갈리나

가장 흔한 오해는 앱과 소프트웨어를 같은 말처럼 쓰는 것입니다. 앱은 소프트웨어의 한 종류일 뿐입니다. 또 어떤 사람은 서버를 하드웨어로만 생각합니다. 하지만 실무에서는 서버라는 말이 컴퓨터 장비 자체를 뜻하기도 하고, 그 위에서 동작하는 서버 프로그램을 뜻하기도 합니다. 문맥에 따라 다르다는 점을 기억해야 합니다.

또한 플랫폼이라는 말도 자주 헷갈립니다. 어떤 문장에서는 운영체제를 뜻하고, 어떤 문장에서는 서비스 생태계 전체를 뜻합니다. 처음에는 넓게 "다른 소프트웨어가 올라타는 기반" 정도로 이해하면 충분합니다.

### 핵심만 다시 정리하면

소프트웨어는 앱만 뜻하지 않습니다. 사용자가 직접 쓰는 프로그램도 소프트웨어이고, 그 프로그램이 돌아가게 만드는 기반과 개발 도구도 모두 소프트웨어입니다. 이 역할 구분을 알고 나면 앞으로 만나는 새로운 기술 이름도 훨씬 덜 낯설어집니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 소프트웨어 종류, 화면과 서버의 역할, 제품 분류 감각와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 웹으로 갈지 앱으로 갈지, 어디에 더 많은 복잡성이 숨어 있는지 판단할 때 이 개념이 다시 등장합니다.

그래서 이 절의 설명은 곧 제품의 첫 버전을 어디서 시작할지 훨씬 현실적으로 볼 수 있습니다

### 읽다가 흔들리는 지점

이 주제에서 가장 흔한 오해는 웹, 웹앱, 네이티브 앱, 프론트엔드, 백엔드를 모두 비슷한 수준의 말로 받아들이는 점입니다.

어떤 말은 제품 형태를 가리키고, 어떤 말은 역할 분리를 가리키며, 어떤 말은 실행 환경을 말한다는 점을 먼저 구분해야 합니다. 이 기준만 있어도 뒤 장에서 같은 말을 다시 만나도 훨씬 덜 흔들립니다.

### 손으로 확인해 보면 더 빨리 남습니다

이 개념은 읽는 것만으로는 쉽게 손에 잡히지 않습니다. 아주 작은 확인만 해도 본문이 훨씬 입체적으로 보입니다.

1. 자주 쓰는 서비스 세 개를 떠올리고 이 주제 관점에서 각각 어떤 형태인지 분류해 봅니다.

2. 화면에서 일어나는 일과 서버에서 일어나는 일을 두 칸으로 나눠 적어 보면 경계가 훨씬 분명해집니다.

3. 내가 만들고 싶은 기능 하나를 정해 두고 브라우저, 모바일 앱, 서버 중 어디부터 필요할지 순서를 적어 봅니다.

### 책 전체 흐름 속에서의 자리

이 개념은 여기서 끝나는 개념이 아닙니다. 이 절에서 잡은 감각은 3장의 도구 선택, 4장의 API 개념, 8장의 실제 통신 흐름로 이어집니다.

따라서 다음 절을 읽을 때는 "이 개념이 지금 설명하는 층은 어디인가"를 계속 추적해 보세요. 그 습관이 전체 책을 훨씬 쉽게 만듭니다.

## 웹,웹앱, 네이티브 앱, 하이브리드 앱의 차이

이 질문은 초보자가 거의 반드시 헷갈리는 주제입니다. 이유는 간단합니다. 사용자 입장에서는 비슷한 서비스를 모두 "앱"이라고 부르기 쉽기 때문입니다. 하지만 개발 관점에서는 어디서 실행되는지, 어떻게 배포되는지, 기기의 기능을 얼마나 깊게 쓰는지에 따라 차이가 큽니다.

먼저 가장 쉬운 말부터 정리해 보겠습니다. 웹은 브라우저에서 주소를 입력하거나 링크를 눌러 들어가는 형태의 서비스입니다. 뉴스 사이트, 회사 소개 페이지, 검색 서비스처럼 브라우저 안에서 열리는 것들이 여기에 들어갑니다.

웹앱은 그 웹 중에서도 사용자의 입력과 상태 변화가 많고, 앱처럼 상호작용이 활발한 형태를 말합니다. 예를 들어 메일 서비스, 문서 편집 서비스, 일정 관리 도구처럼 로그인하고 데이터를 바꾸고 저장하는 웹 서비스는 웹앱에 가깝다고 볼 수 있습니다.

네이티브 앱은 특정 운영체제에 맞게 만든 앱입니다. 안드로이드용 앱, 아이폰용 앱처럼 각 플랫폼의 도구와 규칙에 맞춰 만듭니다. 그래서 카메라, 알림, 저장소, 센서 같은 기기 기능을 더 깊게 활용하기 쉽고, 성능 최적화에도 유리한 경우가 많습니다.

하이브리드 앱은 여러 의미로 쓰이지만, 초보자에게는 "웹 기술과 앱 포장을 섞어서 여러 플랫폼에 배포하려는 방식" 정도로 이해하면 충분합니다. 어떤 방식은 웹 화면을 앱 안에 넣는 형태이고, 어떤 방식은 하나의 코드베이스로 여러 운영체제에 대응하는 형태입니다. 세부 구현은 다르지만 공통점은 한 번에 여러 플랫폼을 노리려는 시도라는 점입니다.

### 언제 무엇을 선택하나

정보를 빠르게 보여 주고 링크 공유가 중요하다면 웹이 유리할 수 있습니다. 사용자는 설치 없이 바로 들어올 수 있고, 검색 엔진을 통해 찾기도 쉽습니다.

사용자가 로그인한 뒤 데이터를 계속 바꾸고 저장하며, 브라우저 안에서 거의 프로그램처럼 쓰는 서비스라면 웹앱이라는 개념이 더 잘 어울립니다. 회사의 업무 도구나 협업 도구가 대표적입니다.

카메라, 위치, 푸시 알림, 오프라인 동작, 부드러운 애니메이션이 핵심이고 운영체제와 깊게 붙어야 한다면 네이티브 앱이 강합니다. 반대로 팀 규모가 작고 여러 플랫폼에 빨리 내야 한다면 하이브리드나 크로스플랫폼 전략이 매력적일 수 있습니다.

### 자주 나오는 말: PWA는 무엇인가

여기서 PWA라는 말이 가끔 나옵니다. 이 용어는 Progressive Web App의 줄임말입니다. 한국어로 굳이 풀면 "앱처럼 쓸 수 있게 발전된 웹" 정도로 이해하면 됩니다. 여전히 웹 기술로 만들지만, 설치에 가깝게 보이게 하거나 일부 오프라인 기능과 기기 기능을 활용하도록 다듬은 형태입니다.

그래서 PWA를 두고 "웹과 앱의 중간 같다"고 표현하는 사람이 많습니다. 완전히 네이티브 앱은 아니지만, 단순한 웹페이지보다 앱 같은 사용 경험을 제공할 수 있기 때문입니다. 다만 이 표현은 느낌을 설명하는 말이지, 정확한 공식 분류라고 생각할 필요는 없습니다.

### 왜 이 차이가 실무에서 중요하나

예를 들어 음식 배달 서비스를 만든다고 해 보겠습니다. 손님이 검색으로 바로 들어와 메뉴를 보는 경로는 웹이 강할 수 있습니다. 그런데 자주 주문하는 고객에게 푸시 알림을 보내고, 위치와 결제 정보를 안정적으로 다루고, 앱 아이콘으로 자주 열게 만들고 싶다면 앱 전략이 중요해집니다.

즉, 이 선택은 기술 취향의 문제가 아니라 제품 전략의 문제이기도 합니다. 누구에게 어떻게 도달할 것인지, 어떤 기능이 핵심인지, 팀이 어디에 강한지에 따라 달라집니다.

### 무엇을 특히 헷갈리기 쉬운가

웹앱과 하이브리드 앱을 같은 말처럼 생각하면 곤란합니다. 웹앱은 주로 사용 경험과 서비스 성격을 설명하는 말입니다. 하이브리드 앱은 개발 방식이나 배포 전략 쪽에 더 가깝습니다.

또한 네이티브 앱이 무조건 최고라고 단정하는 것도 위험합니다. 최고 성능이 필요한 제품도 있지만, 빠르게 실험하고 시장 반응을 보는 것이 더 중요한 제품도 있습니다. 좋은 선택은 제품 목표에 따라 달라집니다.

### 핵심만 다시 정리하면

웹은 브라우저에서 열리는 서비스이고, 웹앱은 그중에서도 앱처럼 상호작용이 풍부한 형태입니다. 네이티브 앱은 특정 운영체제에 맞춰 만든 앱이고, 하이브리드 앱은 여러 플랫폼을 함께 노리기 위한 혼합 전략입니다. 무엇이 더 낫다고 외우기보다, 언제 어떤 선택이 맞는지 이해하는 것이 더 중요합니다.

### 실제로 만들 때는 이런 선택으로 이어집니다

## 프론트 엔드와 백엔드

프론트엔드와 백엔드는 개발 입문자가 가장 자주 듣는 구분입니다. 그런데 이 말을 너무 단순하게 이해하면 나중에 금방 막히게 됩니다. 프론트엔드는 그저 예쁘게 꾸미는 부분이고, 백엔드는 그 밖의 어려운 것 전부라고 생각하는 경우가 많은데, 실제로는 그렇게 단순하지 않습니다.

가장 쉬운 설명은 이렇습니다. 프론트엔드는 사용자가 직접 보고 만지는 쪽입니다. 화면, 버튼, 입력창, 메뉴, 그래프, 애니메이션, 사용 흐름 같은 것이 여기에 포함됩니다. 백엔드는 눈에 잘 보이지 않지만 서비스가 제대로 돌아가도록 뒤에서 처리하는 쪽입니다. 데이터 저장, 로그인 확인, 권한 검사, 주문 처리, 외부 시스템과 연동하는 일 등이 여기에 들어갑니다.

### 프론트엔드는 무엇을 맡나

프론트엔드의 핵심 역할은 사용자가 서비스를 이해하고 조작할 수 있게 만드는 것입니다. 화면을 보기 좋게 만드는 것만이 아니라, 어떤 순서로 보여 줄지, 실수했을 때 어떻게 안내할지, 정보가 너무 많을 때 어떻게 정리할지도 프론트엔드의 일입니다.

예를 들어 회원가입 화면을 생각해 보면, 입력칸을 배치하고, 비밀번호 조건을 보여 주고, 잘못 입력했을 때 경고를 띄우고, 가입 완료 후 다음 화면으로 넘어가게 만드는 일까지 모두 프론트엔드에 속합니다. 즉, 프론트엔드는 디자인과 개발이 만나는 지점이자 사용자 경험을 책임지는 영역입니다.

### 백엔드는 무엇을 맡나

백엔드는 사용자가 직접 보지 않는 영역에서 서비스의 규칙과 데이터를 처리합니다. 회원가입 예시를 이어 가면, 백엔드는 이메일이 이미 가입된 것인지 확인하고, 비밀번호를 안전하게 저장하고, 가입 정보를 데이터베이스에 기록하고, 필요한 경우 인증 메일을 보내는 일을 담당합니다.

또한 백엔드는 서비스의 중심 규칙을 지키는 역할을 합니다. 주문 취소가 가능한 시간인지, 할인 쿠폰을 중복 사용하면 안 되는지, 관리자만 볼 수 있는 데이터인지 같은 판단은 보통 백엔드에서 이뤄집니다. 이유는 간단합니다. 사용자의 기기 안에서만 처리하면 조작되기 쉽기 때문입니다.

### 둘은 어떻게 연결되나

프론트엔드와 백엔드는 보통 약속된 형식으로 대화합니다. 이 연결 지점을 API라고 부릅니다. API는 프로그램끼리 대화하는 약속이라고 이해하면 됩니다. 프론트엔드가 "이 사용자 정보를 주세요"라고 요청하면, 백엔드는 약속된 형식으로 응답합니다.

여기서 중요한 것은 둘이 완전히 따로 노는 존재가 아니라는 점입니다. 프론트엔드가 어떤 데이터를 필요로 하는지, 백엔드가 어떤 형식으로 줄 수 있는지 서로 맞아야 서비스가 부드럽게 동작합니다. 그래서 실무에서는 화면 개발자와 서버 개발자가 계속 소통하게 됩니다.

### 왜 초보자가 이 구분을 꼭 알아야 하나

이 구분을 알면 문제가 생겼을 때 어디를 봐야 할지 감이 생깁니다. 버튼이 안 눌리는 문제인지, 눌렀는데 서버가 응답을 안 하는 문제인지, 응답은 왔는데 화면에 표시가 안 되는 문제인지 나누어 생각할 수 있기 때문입니다.

또한 앞으로 배우게 될 많은 주제가 어느 편에 더 가까운지 파악하기 쉬워집니다. 데이터베이스, 인증, 서버 배포는 보통 백엔드와 더 가깝고, 화면 상태 관리나 사용자 상호작용은 프론트엔드와 더 가깝습니다. 물론 둘이 완전히 분리되는 것은 아니지만, 큰 분류를 알고 있으면 학습 지도가 훨씬 선명해집니다.

### 자주 하는 오해

프론트엔드는 쉬운 쪽이고 백엔드는 어려운 쪽이라고 생각하는 경우가 많습니다. 하지만 실제로는 종류가 다른 어려움일 뿐입니다. 프론트엔드는 브라우저 차이, 복잡한 화면 상태, 접근성, 사용자 경험 문제를 다룹니다. 백엔드는 보안, 데이터 일관성, 성능, 장애 대응을 다룹니다. 둘 다 만만하지 않습니다.

또한 프론트엔드는 디자인이고 백엔드는 개발이라고 생각하는 것도 오해입니다. 프론트엔드 역시 분명한 개발 영역이며, 규모가 커질수록 구조와 성능, 테스트가 매우 중요해집니다.

### 핵심만 다시 정리하면

프론트엔드는 사용자가 직접 만나는 화면과 상호작용을 담당하고, 백엔드는 데이터와 규칙과 보이지 않는 처리 과정을 담당합니다. 둘은 API 같은 약속을 통해 연결되며, 어느 한쪽만 잘해서는 좋은 서비스가 되기 어렵습니다.

## 웹 어플리케이션 개발

웹 어플리케이션 개발은 브라우저에서 사용하는 프로그램을 만드는 일이라고 생각하면 됩니다. 여기서 중요한 것은 "브라우저에서 본다"는 사실보다, 브라우저를 통해 실제 업무나 행동이 이뤄진다는 점입니다. 단순히 정보를 읽기만 하는 페이지를 넘어서, 로그인하고, 데이터를 입력하고, 저장하고, 검색하고, 결과를 바꾸는 서비스가 웹 어플리케이션입니다.

그래서 웹 어플리케이션 개발은 단순히 홈페이지를 만드는 일과는 다릅니다. 화면을 만드는 일만으로 끝나지 않고, 서버와 통신하고, 데이터를 저장하고, 사용자의 상태를 관리하고, 보안과 성능까지 고려해야 합니다.

### 웹페이지와 웹 애플리케이션은 무엇이 다른가

회사 소개 페이지처럼 정적인 정보를 보여 주는 페이지는 전통적인 웹페이지에 가깝습니다. 물론 이런 페이지도 잘 만드는 것이 중요하지만, 사용자의 입력과 복잡한 상태 변화는 많지 않습니다.

반면 웹 메일, 온라인 문서 편집기, 예약 시스템, 관리자 화면처럼 사용자가 계속 입력하고 결과가 바뀌는 서비스는 웹 애플리케이션에 가깝습니다. 즉, 핵심 차이는 상호작용의 깊이와 뒤에서 동작하는 로직의 복잡성에 있습니다.

### 실제로는 어떤 것들이 함께 움직이나

웹 애플리케이션 하나가 동작하려면 최소한 몇 가지가 함께 필요합니다. 사용자에게 보이는 화면이 있어야 하고, 화면에서 일어난 행동을 처리하는 코드가 있어야 합니다. 서버는 요청을 받아 데이터를 읽고 쓰며, 데이터베이스는 그 정보를 저장합니다. 여기에 로그인, 권한, 오류 처리, 속도 개선, 배포 같은 문제도 따라옵니다.

예를 들어 병원 예약 서비스를 만든다고 생각해 보겠습니다. 화면에서는 날짜와 시간을 고르게 해야 하고, 서버에서는 이미 누가 예약했는지 확인해야 하며, 데이터베이스에는 예약 결과를 저장해야 합니다. 예약 취소 규칙이 있다면 그것도 처리해야 하고, 관리자 페이지가 있다면 권한에 따라 보이는 정보도 달라져야 합니다. 이것이 바로 웹 애플리케이션 개발이 단순 화면 작업이 아닌 이유입니다.

### 왜 많은 서비스가 웹으로 시작하나

웹은 접근성이 좋습니다. 사용자는 설치 없이 링크만으로 들어올 수 있고, 검색을 통해 유입되기도 쉽습니다. 팀 입장에서도 배포와 수정이 비교적 빠릅니다. 그래서 아이디어를 검증하거나 초기 사용자를 모을 때 웹은 매우 강력한 출발점이 됩니다.

특히 업무용 서비스나 관리 도구, SaaS 제품은 지금도 웹이 핵심 채널인 경우가 많습니다. 회사 내부 시스템, 협업 툴, 대시보드, 예약 시스템, 관리자 화면처럼 브라우저만 있으면 여러 환경에서 쉽게 접속할 수 있는 서비스는 웹이 매우 잘 맞습니다.

### 웹 개발이 생각보다 어려워지는 지점

겉으로 보기에는 브라우저 하나만 잘 다루면 될 것 같지만, 실제로는 문제가 빠르게 늘어납니다. 네트워크가 느릴 때 어떻게 할지, 새로고침하면 상태가 어떻게 되는지, 여러 사용자가 동시에 접근할 때 데이터가 꼬이지 않는지, 민감한 정보가 노출되지 않는지 모두 신경 써야 합니다.

또한 브라우저에서 돌아간다는 말은 여러 환경에서 잘 돌아가야 한다는 뜻이기도 합니다. 화면 크기 차이, 입력 방식 차이, 성능 차이, 접근성 문제까지 생각해야 하므로, 웹 개발은 생각보다 넓은 범위를 요구합니다.

### AI 시대의 웹 애플리케이션 개발

AI는 웹 개발 속도를 크게 높여 주고 있습니다. 화면 초안, 폼 처리 코드, API 연결 코드, 테스트 초안 등을 빨리 만들 수 있기 때문입니다. 그래서 예전보다 훨씬 빠르게 프로토타입을 만들고 실험할 수 있습니다.

하지만 빠르게 만들 수 있다고 해서 웹 애플리케이션 개발이 단순해진 것은 아닙니다. 오히려 구조를 검토하는 능력의 중요성이 더 커졌습니다. AI가 만든 화면이 그럴듯해 보여도 데이터 흐름이 엉키면 서비스는 불편해지고, 보안 검토가 빠지면 위험해집니다. 결국 웹 개발에서도 사람은 여전히 "전체가 제대로 맞물리는가"를 판단해야 합니다.

### 핵심만 다시 정리하면

웹 어플리케이션 개발은 브라우저에서 사용하는 프로그램을 만드는 일입니다. 단순 페이지 제작이 아니라 화면, 서버, 데이터, 보안, 운영이 함께 맞물리는 소프트웨어 개발입니다. 그래서 웹은 시작하기 쉬워 보여도, 제대로 만들려면 생각보다 넓은 이해가 필요합니다.

### 이 개념이 실전에서 빛나는 순간

이 개념은 초보자에게는 이론처럼 보이지만, 조금만 실제 장면으로 옮겨 보면 매우 실용적인 기준이 됩니다. 새로운 서비스 아이디어를 어떤 형태로 시작할지 정할 때 특히 그렇습니다.

이 절을 제대로 소화하면 작은 기능 하나가 여러 층을 함께 건드린다는 사실이 선명해집니다

### 헷갈릴 때 다시 세워야 하는 기준

이 절에서 자주 길을 잃는 이유는 웹, 웹앱, 네이티브 앱, 프론트엔드, 백엔드를 모두 비슷한 수준의 말로 받아들이는 점입니다.
