# 7장. 데이터베이스 기술

서비스를 만들다 보면 결국 데이터를 어디엔가 저장해야 합니다. 회원 정보, 주문 내역, 게시글, 댓글, 결제 기록, 로그 같은 것들이 모두 데이터입니다. 7장은 이 데이터를 어떻게 안전하게 저장하고 꺼내는지 이해하기 위한 장입니다. 데이터베이스는 단순한 저장 창고가 아니라, 서비스의 기억을 관리하는 핵심 시스템입니다.

초보자는 데이터베이스를 단순히 표를 넣어 두는 엑셀 비슷한 것으로 생각하기 쉽습니다. 하지만 실제 데이터베이스는 동시 접근, 보안, 복구, 정합성, 조회 성능까지 함께 다뤄야 합니다. 그래서 앱 코드와 데이터 저장을 어떻게 나눌지, 관계형 데이터베이스와 NoSQL을 어떻게 구분할지 이해하는 것이 중요합니다.

이 장의 목표는 SQL 문법을 암기하는 것이 아닙니다. 데이터베이스가 왜 따로 존재하는지, 왜 그냥 앱에서 직접 파일처럼 다루지 않는지, 어떤 상황에서 다른 저장 방식이 필요한지를 개괄적으로 이해하는 것입니다.

## 데이터베이스(DBMS)의 이해

데이터베이스는 데이터를 체계적으로 저장해 두는 공간이고, DBMS는 그 데이터베이스를 관리하는 소프트웨어입니다. 초보자는 둘을 같은 말처럼 쓰기 쉽지만, 엄밀히 말하면 데이터베이스는 내용물에 가깝고, DBMS는 그것을 저장하고 검색하고 보호하는 관리자입니다. MySQL, PostgreSQL, SQLite, Oracle 같은 이름은 보통 DBMS 제품 이름입니다.

왜 DBMS가 따로 필요할까요. 단순히 파일에 데이터를 적어 둘 수도 있지만, 실제 서비스에서는 여러 사용자가 동시에 데이터를 읽고 쓰고, 오류가 나도 복구해야 하며, 특정 조건으로 빠르게 찾아야 합니다. DBMS는 이런 문제를 해결하기 위해 인덱스, 잠금, 권한 관리, 백업, 복구, 트랜잭션 같은 기능을 제공합니다.

### 데이터베이스를 이루는 기본 감각

관계형 데이터베이스를 기준으로 보면, 데이터는 보통 테이블 형태로 정리됩니다. 테이블은 같은 종류의 데이터를 담는 표이고, 행은 한 건의 기록, 열은 각 항목의 속성입니다. 예를 들어 사용자 테이블에는 이름, 이메일, 가입일 같은 열이 있고, 사용자 한 명 한 명이 행으로 들어갑니다.

하지만 데이터베이스는 단순한 표 보관소가 아닙니다. 여러 테이블 사이의 관계를 관리하고, 조건을 걸어 원하는 데이터를 찾고, 동시에 일어나는 변경이 서로 꼬이지 않게 막아 줍니다. 이때 트랜잭션이라는 개념이 중요합니다. 트랜잭션은 여러 작업이 하나의 묶음처럼 성공하거나 실패해야 할 때 일관성을 지키기 위한 장치입니다.

### 인덱스와 성능은 왜 함께 나오나요

데이터가 적을 때는 그냥 순서대로 찾아도 큰 문제가 없습니다. 하지만 수십만, 수백만 건이 되면 특정 사용자나 주문을 즉시 찾아야 할 때 속도가 급격히 중요해집니다. 이때 인덱스가 도움을 줍니다. 인덱스는 책 뒤의 찾아보기처럼, 원하는 값을 더 빨리 찾게 해 주는 보조 구조입니다.

물론 인덱스도 공짜는 아닙니다. 너무 많이 만들면 저장 공간을 더 쓰고, 데이터를 쓸 때마다 인덱스도 함께 갱신해야 하므로 부담이 생길 수 있습니다. 즉, 데이터베이스는 저장뿐 아니라 조회 패턴과 변경 패턴을 함께 고려하는 설계가 중요합니다.

### 초보자가 꼭 잡아야 할 그림

데이터베이스는 서비스의 기억이고, DBMS는 그 기억을 안전하고 빠르게 다루게 해 주는 관리 시스템입니다. 테이블, 인덱스, 트랜잭션 같은 개념은 모두 데이터를 많이, 오래, 안전하게 다루기 위해 등장한 도구입니다.

이 그림을 잡고 나면 SQL 문법을 배우더라도 그것이 단순한 명령어 암기가 아니라, 데이터를 다루는 목적과 연결된 언어라는 점이 보이게 됩니다.

### 핵심만 다시 정리하면

데이터베이스는 데이터를 저장하는 공간이고, DBMS는 그 공간을 관리하는 소프트웨어입니다. 실제 서비스에서는 동시성, 검색 속도, 복구, 보안 때문에 DBMS가 필수적입니다. 테이블, 인덱스, 트랜잭션 같은 개념은 모두 데이터를 안전하고 효율적으로 다루기 위한 기본 장치입니다.

### 이 내용을 알면 어디서 덜 막히는가

그래서 이 절의 설명은 곧 서비스가 커질수록 데이터 설계가 왜 더 중요해지는지 보입니다

## 왜 앱과 DB를 바로 연동하지 않나요?

초보자는 종종 앱이 데이터베이스에 직접 붙으면 더 빠르고 단순하지 않나요라고 묻습니다. 작은 실습에서는 그렇게 보일 수 있습니다. 하지만 실제 서비스에서는 앱과 데이터베이스 사이에 보통 백엔드나 서버 계층을 둡니다. 이유는 단순히 습관 때문이 아니라, 보안과 규칙과 확장성을 지키기 위해서입니다.

만약 사용자의 앱이 데이터베이스에 직접 접속할 수 있다면, 접속 정보가 앱 안에 들어가야 하고, 사용자는 그 통로를 분석하거나 악용할 수 있습니다. 그러면 데이터베이스 구조가 그대로 노출되고, 권한 제어도 어려워집니다. 특히 공개 서비스에서는 매우 위험합니다.

### 서버 계층은 어떤 역할을 하나요

백엔드는 단순한 중간 전달자가 아닙니다. 누가 어떤 데이터를 볼 수 있는지 확인하고, 입력값을 검증하고, 여러 규칙을 적용하고, 필요한 경우 여러 시스템을 함께 호출해 결과를 조합합니다. 예를 들어 주문 요청 하나에도 재고 확인, 결제 확인, 쿠폰 검증, 배송지 검증, 주문 저장 같은 여러 단계가 들어갑니다. 이런 규칙은 데이터베이스 쿼리 하나로 끝나지 않습니다.

또한 서버 계층은 데이터베이스 변경을 외부에 직접 드러내지 않게 해 줍니다. 앱은 약속된 API만 알면 되므로, 내부 테이블 구조가 조금 바뀌어도 앱 전체를 다 고치지 않아도 될 수 있습니다. 즉, 서버는 보안 장벽이면서 변화 흡수층입니다.

### 성능과 운영 측면에서도 왜 중요한가요

앱 수천 개가 직접 데이터베이스에 붙으면 연결 관리가 복잡해지고, 잘못된 요청이 곧바로 데이터베이스 부담으로 이어집니다. 반면 서버 계층이 있으면 캐시를 두거나, 요청을 조절하거나, 여러 데이터베이스를 조합하거나, 로그와 모니터링을 한곳에서 관리하기 쉽습니다. 장애 대응도 훨씬 수월해집니다.

물론 내부 관리자 도구나 매우 작은 개인 프로젝트에서는 직접 연결이 허용될 수 있습니다. 하지만 사용자 수가 늘고 보안이 중요한 서비스에서는 앱과 DB를 직접 연결하지 않는 이유가 분명해집니다. 좋은 구조는 조금 우회하더라도 시스템을 훨씬 오래 안전하게 버티게 합니다.

### 초보자가 꼭 기억할 점

앱과 DB 사이에 서버를 둔다는 것은 괜히 한 단계를 늘리는 것이 아닙니다. 사용자 요청을 검증하고, 권한을 통제하고, 비즈니스 규칙을 적용하고, 데이터 구조 변경을 완충하는 역할이 있기 때문입니다. 결국 이 중간 계층 덕분에 서비스는 더 안전하고 유연해집니다.

이 관점을 이해하면 프론트엔드, 백엔드, 데이터베이스가 왜 나뉘는지 더 선명하게 보입니다. 단순히 역할 분담이 아니라 위험과 복잡성을 관리하는 구조인 것입니다.

### 핵심만 다시 정리하면

앱과 데이터베이스를 바로 연결하지 않는 이유는 보안, 권한 제어, 규칙 적용, 연결 관리, 구조 변경 흡수 때문입니다. 서버 계층은 단순한 중계가 아니라 서비스 규칙과 안정성을 담당하는 중요한 완충층입니다. 작은 실습에서는 생략될 수 있어도, 실제 서비스에서는 매우 중요한 구조적 선택입니다.

### 실제로 만들 때는 이런 선택으로 이어집니다

이 개념은 정의 하나로 끝나는 주제가 아니라, 실제 선택의 기준이 되는 개념입니다. 특히 앱과 DB 사이에 어떤 계층이 필요한지 판단할 때 이 절의 내용이 곧바로 판단 기준이 됩니다.

이 관점을 잡아 두면 DB를 그냥 창고처럼 보지 않고 규칙이 담긴 시스템으로 보게 됩니다

데이터의 모양, 데이터에 대한 규칙, 데이터를 다루는 언어, 그 시스템을 운영하는 소프트웨어를 분리해 봐야 합니다. 정의를 통째로 외우기보다 경계를 먼저 세우는 편이 훨씬 오래 갑니다.

## NoSQL은 SQL이 아닌가요?

NoSQL이라는 이름만 보면 SQL을 쓰지 않는다는 뜻처럼 느껴집니다. 하지만 실제로는 관계형 데이터베이스와 다른 모델을 강조하는 넓은 범주의 이름으로 이해하는 편이 맞습니다. 즉, SQL을 적으로 두는 개념이 아니라, 꼭 테이블 관계 중심이 아닌 다른 저장 방식도 필요하다는 흐름에서 나온 말입니다.

관계형 데이터베이스는 표 구조와 관계, 정합성, 강한 일관성에 강합니다. 반면 현실의 데이터는 항상 깔끔한 표로만 표현되지 않습니다. 문서 구조가 자주 바뀌거나, 키와 값 중심으로 매우 빠르게 읽고 써야 하거나, 그래프 관계가 복잡한 경우에는 다른 방식이 더 잘 맞을 수 있습니다. 그래서 NoSQL 계열이 등장했습니다.

### NoSQL에는 어떤 종류가 있나요

문서형 데이터베이스는 JSON 비슷한 문서 구조를 그대로 저장하는 데 강합니다. 그래서 속성이 자주 바뀌는 데이터나 계층 구조가 있는 데이터에 편리할 수 있습니다. 키값 저장소는 매우 빠른 조회와 단순한 구조가 강점이라 캐시나 세션 저장에 자주 쓰입니다. 컬럼 기반 저장소나 그래프 데이터베이스도 각각 대규모 분석, 관계 탐색 같은 장면에서 강점을 보입니다.

즉, NoSQL은 하나의 제품이 아니라 다양한 비관계형 저장 방식의 묶음입니다. 초보자는 NoSQL을 무조건 최신이거나 더 좋은 것처럼 볼 필요는 없습니다. 관계형 데이터베이스가 잘 맞는 문제도 여전히 매우 많습니다.

### 그럼 SQL 데이터베이스와 어떤 기준으로 고르나요

데이터가 안정된 구조를 갖고 있고, 여러 데이터 사이의 관계와 정합성이 매우 중요하다면 관계형 데이터베이스가 강합니다. 반대로 데이터 구조가 유연하게 바뀌거나, 단순한 읽기와 쓰기를 엄청나게 많이 처리해야 하거나, 특정 접근 패턴이 아주 뚜렷하다면 NoSQL 계열이 유리할 수 있습니다.

실무에서는 둘 중 하나만 고집하지 않는 경우가 많습니다. 주문과 결제처럼 정확성이 중요한 데이터는 관계형 데이터베이스에 두고, 캐시나 세션은 키값 저장소에 두고, 검색 인덱스는 별도 시스템에 두는 식입니다. 즉, 저장 기술도 역할별 분업이 흔합니다.

### 초보자가 꼭 기억하면 좋은 한 가지

NoSQL은 SQL의 반대편 진영이 아닙니다. 데이터를 어떤 모양으로 저장하고 어떤 패턴으로 읽고 쓸 것인가에 따라 다른 선택지를 제공하는 범주입니다. 결국 핵심은 유행어가 아니라 데이터의 성격과 서비스 요구를 보는 것입니다.

이 감각을 잡으면 나중에 특정 데이터베이스 제품 이름을 보더라도, 그것이 어떤 데이터 문제에 강한지 질문하는 습관이 생깁니다.

### 핵심만 다시 정리하면

NoSQL은 SQL을 부정하는 말이라기보다, 관계형 모델 외의 다양한 저장 방식을 가리키는 넓은 범주입니다. 문서형, 키값, 컬럼형, 그래프형 등 여러 종류가 있으며, 데이터 구조와 접근 패턴에 따라 강점이 다릅니다. 초보자는 관계형과 NoSQL을 승부로 보기보다 문제에 맞는 저장 전략으로 이해하는 것이 좋습니다.

이 개념을 배우는 이유는 단어를 하나 더 외우기 위해서가 아닙니다. 관계형과 비관계형 저장 방식을 비교할 때 무엇을 먼저 볼지 정하는 눈을 만들기 위해서입니다.

결국 이 개념을 이해한다는 것은 조회와 저장의 패턴이 구조 선택에 어떤 영향을 주는지 이해하게 됩니다

### 여기서 많이 생기는 오해

이 개념이 갑자기 어려워지는 순간은 보통 데이터베이스를 단순한 저장 폴더로 생각하거나, SQL과 DBMS를 같은 말처럼 받아들이는 점입니다.

데이터의 모양, 데이터에 대한 규칙, 데이터를 다루는 언어, 그 시스템을 운영하는 소프트웨어를 분리해 봐야 합니다. 그러면 비슷한 용어를 만나도 같은 상자에 모두 넣어 버리는 실수를 줄일 수 있습니다.
