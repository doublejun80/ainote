# 4장. 개발할 때 알아야 하는 필수 지식

3장까지가 어떤 분야와 언어를 배우는지에 대한 큰 지도를 보는 시간이었다면, 4장은 개발 대화에서 끊임없이 튀어나오는 기본 용어를 정리하는 장입니다. 초보자가 가장 힘들어하는 순간은 새로운 개념 그 자체보다, 설명 안에서 또 다른 낯선 단어가 연달아 나오는 순간입니다. 그래서 이 장에서는 정의만 주지 않고, 그 개념이 왜 생겼는지와 실제로 언제 마주치는지를 같이 설명합니다.

예를 들어 API라는 말을 듣는 순간 어떤 사람은 서버를 떠올리고, 어떤 사람은 라이브러리 문서를 떠올립니다. 둘 다 맞을 수 있습니다. 문제는 이런 단어들이 맥락에 따라 뜻이 조금씩 달라진다는 점입니다. 자료 구조, 동기와 비동기, JSON, 세션 같은 말도 마찬가지입니다. 이름은 많이 들었는데 실제로는 어디에 놓여 있는지 감이 안 잡히면, 강의를 들어도 문장이 통째로 흐려집니다.

이 장의 목표는 용어를 외우게 하는 것이 아닙니다. 각각의 단어가 개발에서 어떤 역할을 맡는지, 어떤 판단을 돕는지 이해하게 하는 것입니다. 4장을 읽고 나면 문서나 강의를 볼 때 낯선 말이 나와도 "아, 이건 데이터 모양을 말하는구나", "이건 요청을 주고받는 약속을 말하는구나"처럼 스스로 위치를 잡을 수 있어야 합니다.

## 이 장을 읽을 때의 포인트

첫째, 비슷해 보이는 용어를 억지로 한 덩어리로 외우지 않는 것이 좋습니다. 함수와 클래스는 역할이 다르고, 라이브러리와 프레임워크도 주도권이 다릅니다. 비슷한 말끼리 차이를 또렷하게 구분할수록 실무 문서를 읽기가 쉬워집니다.

둘째, 웹 개발 예시가 많이 나오더라도 웹 전용 지식으로 보지 않는 편이 좋습니다. API, 비동기, 자료 구조, 모듈 같은 개념은 앱, 서버, 데이터 처리, 자동화 스크립트 어디에서나 등장합니다. 즉, 이 장은 특정 기술이 아니라 개발 공통 언어를 배우는 장입니다.

셋째, 모든 용어를 처음부터 완벽하게 외우려 하지 않아도 됩니다. 중요한 것은 지금 당장 손에 잡히는 설명을 만드는 것입니다. 나중에 실제 코드를 보게 되면, 오늘 익힌 개념이 훨씬 선명하게 다시 연결될 것입니다.

## 자료 구조란 무엇인가요?

자료 구조는 데이터를 어떻게 담고, 꺼내고, 정리할지를 정한 방식입니다. 아주 단순하게 말하면 데이터를 담는 그릇의 설계도라고 볼 수 있습니다. 초보자는 종종 변수에 값 넣으면 끝 아닌가요라고 생각하지만, 실제 개발에서는 데이터가 한두 개가 아니라 수십 개, 수천 개, 수백만 개가 되기 때문에 어떤 모양으로 보관하느냐가 성능과 코드 이해도에 큰 차이를 만듭니다.

예를 들어 학생 이름을 순서대로 저장하고 싶다면 배열이나 리스트가 잘 맞습니다. 반대로 이름으로 바로 찾아야 한다면 사전형 자료 구조인 맵이 더 편합니다. 중복 없는 태그 목록이 필요하면 집합이 어울립니다. 같은 데이터라도 무엇을 자주 할 것인지에 따라 적합한 자료 구조가 달라집니다. 그래서 자료 구조는 단순한 문법이 아니라, 문제를 풀기 위한 사고 도구입니다.

### 자료 구조를 왜 따로 배우나요

초보자가 자료 구조를 어려워하는 이유는 아직 데이터가 작기 때문입니다. 실습 초기에는 항목이 몇 개 안 되니 어떤 방식으로 저장해도 결과가 비슷해 보입니다. 하지만 서비스 규모가 커지면 이야기가 달라집니다. 순서가 중요한지, 검색이 빠른지가 중요한지, 중복을 막아야 하는지, 앞뒤에서 자주 넣고 빼는지가 중요한지에 따라 코드 구조가 완전히 달라집니다.

예를 들어 쇼핑몰 장바구니를 생각해 보겠습니다. 화면에는 상품 목록이 순서대로 보여야 하므로 리스트가 자연스럽습니다. 그런데 장바구니 안에 특정 상품이 이미 들어 있는지 빠르게 확인하려면 상품 아이디를 키로 쓰는 맵 구조가 더 유리합니다. 즉, 실제 서비스에서는 하나의 기능 안에서도 여러 자료 구조가 함께 사용됩니다.

자료 구조를 배운다는 것은 이 문제에는 어떤 그릇이 맞을까를 판단하는 눈을 기르는 일입니다. 그래서 면접 준비용 이론으로만 생각하면 금방 지칩니다. 오히려 자료 구조는 코드가 느려지거나 복잡해질 때 어디를 바꿔야 하는지 알려 주는 실용 지식에 가깝습니다.

### 대표적인 자료 구조를 감각적으로 이해해 봅시다

배열과 리스트는 순서대로 늘어놓는 데 강합니다. 그래서 목록 표시, 차트 데이터, 할 일 목록처럼 순서가 중요할 때 자주 쓰입니다. 대신 중간에 항목을 자주 끼워 넣거나 이름으로 곧바로 찾아야 하면 불편할 수 있습니다.

맵은 이름표를 붙여 꺼내는 서랍에 가깝습니다. 사용자 아이디로 사용자 정보를 찾거나, 설정 이름으로 설정 값을 읽을 때 유용합니다. 집합은 중복을 자동으로 막아 주는 목록이라고 이해하면 편합니다. 이미 본 알림, 선택된 태그, 방문한 페이지 같은 정보를 관리할 때 잘 맞습니다.

스택과 큐도 자주 등장합니다. 스택은 나중에 넣은 것을 먼저 꺼내는 구조라서 되돌리기 기능이나 함수 호출 흐름을 설명할 때 자주 나옵니다. 큐는 먼저 들어온 것을 먼저 처리하는 구조라서 대기열, 메시지 처리, 작업 예약과 잘 어울립니다. 현실 세계의 줄 서기와 비슷하다고 보면 됩니다.

### 실무에서는 어떤 식으로 드러날까요

자료 구조 선택은 눈에 띄지 않지만, 사용자 경험에 큰 영향을 줍니다. 검색 자동완성 기능을 만들 때 목록을 전부 훑어야 한다면 느려질 수 있습니다. 반대로 적절한 구조를 쓰면 입력하는 즉시 후보를 빠르게 보여 줄 수 있습니다. 채팅 서비스에서 메시지를 시간순으로 쌓고, 읽은 사용자 집합을 따로 관리하고, 대기 중인 이벤트를 큐로 처리하는 식으로 기능마다 다른 자료 구조가 조합되기도 합니다.

초보자에게 중요한 점은 복잡한 알고리즘부터 외우자가 아닙니다. 먼저 데이터가 어떤 성질을 갖는지 묻는 습관을 들이면 됩니다. 순서가 중요한가요? 중복을 허용하나요? 빠르게 찾는 일이 많은가요? 앞뒤에서 자주 꺼내나요? 이 질문만 익숙해져도 자료 구조 선택의 절반은 이미 시작된 셈입니다.

### 핵심만 다시 정리하면

자료 구조는 데이터를 저장하는 방식이자, 데이터를 다루는 전략입니다. 어떤 자료 구조를 쓰느냐에 따라 코드의 읽기 쉬움, 실행 속도, 기능 확장 방식이 달라집니다. 따라서 자료 구조는 시험용 용어가 아니라, 개발자가 문제를 더 좋은 모양으로 바꾸기 위해 매일 사용하는 기본 도구입니다.

### 이 내용을 알면 어디서 덜 막히는가

이 개념을 이해하면 자료 구조, API, 비동기, 데이터 형식 같은 핵심 개념의 경계와 관련된 질문을 훨씬 현실적으로 바라볼 수 있습니다. 실제로는 데이터를 어떤 모양으로 다룰지, 요청을 어떻게 주고받을지 정할 때 이 개념이 다시 등장합니다.

그래서 이 절의 설명은 곧 문서를 읽을 때 용어 때문에 발이 묶이는 일이 크게 줄어듭니다

### 읽다가 흔들리는 지점

이 주제에서 가장 흔한 오해는 용어가 너무 많아 보여 서로 다른 개념을 같은 상자에 넣어 버리는 점입니다.

정의 하나를 외우기보다 이 말이 코드 구조인지, 통신 방식인지, 데이터 표현인지 먼저 가르는 편이 좋습니다. 이 기준만 있어도 뒤 장에서 같은 말을 다시 만나도 훨씬 덜 흔들립니다.

### 손으로 확인해 보면 더 빨리 남습니다

이 개념은 읽는 것만으로는 쉽게 손에 잡히지 않습니다. 아주 작은 확인만 해도 본문이 훨씬 입체적으로 보입니다.

1. 본문 예시를 바탕으로 이 개념이 요청-응답 흐름의 어느 위치에 있는지 그림으로 그려 봅니다.

2. JSON, API, 비동기처럼 낯선 단어가 나오면 각각이 데이터·규칙·흐름 중 무엇에 해당하는지 분류해 봅니다.

3. 브라우저 화면에서 버튼 하나를 눌렀을 때 어떤 순서로 일이 벌어지는지 말로 풀어 보면 이해가 빨라집니다.

### 책 전체 흐름 속에서의 자리

이 개념은 여기서 끝나는 개념이 아닙니다. 이 절에서 잡은 감각은 7장의 데이터 저장, 8장의 네트워크 흐름, 9장의 구조 설계로 이어집니다.

따라서 다음 절을 읽을 때는 "이 개념이 지금 설명하는 층은 어디인가"를 계속 추적해 보세요. 그 습관이 전체 책을 훨씬 쉽게 만듭니다.

## 함수, 클래스, 객체와 인스턴스, 모듈과 라이브러리, 컴포넌트, 프레임워크

이 절은 초보자가 개발 공부를 하며 가장 자주 헷갈리는 단어들을 한 번에 정리하는 자리입니다. 단어가 많아 보여도 겁먹을 필요는 없습니다. 이 용어들은 모두 코드를 어떻게 나누고, 묶고, 재사용하느냐를 설명하는 말입니다. 서로 경쟁하는 개념이 아니라, 다른 층위에서 코드를 바라보는 이름들입니다.

먼저 함수는 특정 작업을 하나의 이름으로 묶어 둔 것입니다. 예를 들어 가격 계산하기, 로그인 확인하기, 날짜 포맷 바꾸기 같은 반복 작업을 함수로 만들 수 있습니다. 함수의 핵심은 작업을 재사용하고, 긴 코드를 의미 있는 단위로 나누는 데 있습니다. 즉, 함수는 행동의 단위입니다.

클래스는 비슷한 성질과 행동을 가진 대상을 만들기 위한 설계도입니다. 그리고 객체는 그 설계도를 바탕으로 실제로 메모리 안에 만들어진 대상입니다. 인스턴스는 보통 클래스로부터 만들어진 객체를 더 분명하게 말할 때 쓰는 표현입니다. 예를 들어 사용자라는 클래스를 정의해 놓고 철수 사용자, 영희 사용자를 실제로 만들었다면 각각이 객체이자 인스턴스입니다. 초보자는 객체와 인스턴스를 완전히 다른 존재로 외우려다가 더 헷갈리는데, 실제로는 문맥에 따라 거의 같은 뜻으로 쓰이기도 합니다.

### 코드를 묶는 단위는 왜 이렇게 여러 가지일까요

모듈은 관련 있는 코드들을 파일이나 묶음 단위로 정리한 것입니다. 함수가 행동의 단위라면, 모듈은 기능 묶음의 단위에 가깝습니다. 예를 들어 날짜 계산 함수들이 모인 파일, 인증 관련 코드가 모인 파일이 각각 하나의 모듈이 될 수 있습니다. 초보자가 프로젝트가 커졌을 때 가장 먼저 필요를 느끼는 것이 바로 모듈입니다. 파일이 하나로 길어지면 어디에 무엇이 있는지 찾기 어려워지기 때문입니다.

라이브러리는 이미 만들어 둔 기능 모음입니다. 직접 다 만들지 않고 필요한 도구를 가져다 쓰는 개념이라고 보면 됩니다. 날짜 처리 라이브러리, 차트 라이브러리, 이미지 처리 라이브러리처럼 특정 문제를 해결하는 데 도움을 주는 도구 상자에 가깝습니다. 반면 프레임워크는 좀 더 큰 틀입니다. 라이브러리는 내가 필요할 때 가져다 쓰지만, 프레임워크는 미리 정해 둔 구조 안에서 내가 코드를 끼워 넣습니다. 즉, 라이브러리는 내 코드가 도구를 호출하고, 프레임워크는 도구가 내 코드를 호출하는 쪽에 더 가깝습니다.

컴포넌트는 화면이나 기능 조각을 독립적으로 다루기 위한 단위입니다. 특히 웹과 앱 화면 개발에서 많이 쓰입니다. 버튼 하나, 카드 하나, 댓글 입력창 하나를 컴포넌트로 만들면 여러 화면에서 재사용하기 쉬워집니다. 컴포넌트는 대체로 사용자 인터페이스와 관련된 맥락에서 많이 들리지만, 더 넓게 보면 재사용 가능한 부품이라는 뜻을 가집니다.

### 한 번에 구분하는 감각을 만들어 봅시다

이 단어들을 외우기 쉬운 순서로 바꾸면 이렇습니다. 함수는 행동, 클래스는 설계도, 객체는 실체, 모듈은 정리된 묶음, 라이브러리는 가져다 쓰는 도구, 컴포넌트는 재사용 가능한 부품, 프레임워크는 전체 구조와 규칙입니다. 모두 코드 재사용과 구조화를 돕지만, 바라보는 층위가 다릅니다.

| 용어 | 가장 쉬운 감각 | 자주 쓰이는 곳 |

| --- | --- | --- |

| 함수 | 특정 일을 하는 블록 | 계산, 검증, 변환 |

| 클래스 | 비슷한 객체를 만들기 위한 설계도 | 객체지향 코드 |

| 객체/인스턴스 | 실제로 만들어진 대상 | 사용자, 주문, 상품 모델 |

## API vs OpenAPI

API는 프로그램과 프로그램이 대화하는 접점입니다. 쉽게 말해 어떻게 요청하면 무엇을 돌려주는지에 대한 약속입니다. 예를 들어 프론트엔드가 백엔드에 사용자 정보를 요청하거나, 지도 서비스가 외부 위치 데이터를 불러올 때 모두 API를 사용합니다. 그래서 API는 개념 자체가 매우 넓습니다. 운영체제가 제공하는 기능도 API일 수 있고, 라이브러리가 제공하는 함수 묶음도 API일 수 있습니다.

반면 OpenAPI는 API 자체가 아니라, 주로 웹에서 사용하는 HTTP API를 설명하기 위한 명세 형식입니다. 명세 형식이라는 말이 어렵게 들릴 수 있는데, 쉽게 말하면 API를 일정한 규칙으로 적어 두는 문서 포맷입니다. 어떤 주소로 요청을 보내는지, 어떤 값이 필요한지, 어떤 응답이 오는지를 기계도 읽을 수 있는 구조로 표현합니다.

### 둘은 왜 자꾸 같이 나오나요

초보자는 API와 OpenAPI를 같은 말로 오해하기 쉽습니다. 이름이 비슷하고 둘 다 문서 화면에서 자주 등장하기 때문입니다. 하지만 관계를 정확히 말하면, API는 실제 약속이고 OpenAPI는 그 약속을 설명하는 표준화된 설명서입니다. 레스토랑으로 비유하면 API는 주문 가능한 메뉴와 주문 방식 자체이고, OpenAPI는 그 메뉴판을 일정한 형식으로 정리해 둔 문서입니다.

실무에서 OpenAPI가 유용한 이유는 사람이 읽기 쉬운 문서를 만드는 데서 끝나지 않기 때문입니다. OpenAPI 문서가 있으면 테스트 도구, 코드 생성기, 문서 화면, 클라이언트 초안 생성 같은 자동화 작업을 붙이기 쉬워집니다. 즉, API를 팀 안팎에서 덜 헷갈리게 공유할 수 있는 공용 언어 역할을 합니다.

### 실제로는 어떻게 쓰일까요

프론트엔드 개발자는 백엔드가 준 OpenAPI 문서를 보고 어떤 요청을 보내야 하는지 파악할 수 있습니다. QA는 어떤 입력에서 어떤 응답이 나와야 하는지 테스트 기준을 세울 수 있습니다. 백엔드 개발자는 API가 바뀌었을 때 문서와 구현이 어긋나지 않았는지 점검할 수 있습니다. 팀이 커질수록 말로 설명한 API보다 형식화된 API 설명이 훨씬 중요해집니다.

다만 모든 API가 OpenAPI로 작성되는 것은 아닙니다. 라이브러리 API는 보통 코드 문서나 예제로 설명하고, 브라우저 API는 MDN 같은 개발자 문서로 설명됩니다. OpenAPI는 그중에서도 HTTP 기반 웹 API를 체계적으로 다룰 때 특히 힘을 발휘합니다.

### 초보자가 꼭 기억할 차이

API라는 말을 들었을 때는 먼저 무슨 종류의 프로그램 접점인지를 생각하면 됩니다. 운영체제 API인지, 라이브러리 API인지, 웹 API인지에 따라 맥락이 달라집니다. OpenAPI라는 말을 들었을 때는 웹 API를 설명하는 형식화된 문서 체계를 떠올리면 됩니다.

이 차이를 알고 있으면 문서에서 API를 설계한다, OpenAPI 스펙을 갱신한다 같은 말을 볼 때 훨씬 또렷하게 이해할 수 있습니다. 전자는 서비스의 약속 자체를 다듬는 일이고, 후자는 그 약속을 팀이 공유 가능한 형식으로 정리하는 일에 가깝습니다.

### 핵심만 다시 정리하면

API는 프로그램끼리 대화하는 약속이고, OpenAPI는 주로 HTTP API를 일정한 규칙으로 설명하는 명세 형식입니다. 둘은 같은 말이 아니며, OpenAPI는 API를 더 분명하게 공유하고 자동화하기 위한 도구입니다. 이 구분을 알면 문서와 협업 흐름을 읽는 눈이 훨씬 좋아집니다.

## REST API vs RESTful API

REST는 웹에서 자원을 다루는 하나의 설계 스타일입니다. 여기서 자원이라는 말은 사용자, 게시글, 주문처럼 시스템이 관리하는 대상을 뜻합니다. REST 관점에서는 이 자원을 어떤 주소로 표현하고, 어떤 HTTP 동작으로 다룰 것인가를 중요하게 봅니다. 그래서 REST를 제대로 이해하려면 먼저 이것이 특정 프로그램 이름이 아니라 설계 원칙이라는 점부터 잡아야 합니다.

현실에서는 REST API라는 말을 굉장히 넓게 씁니다. 단순히 HTTP로 요청하고 JSON을 돌려주는 API를 통칭하는 경우도 많습니다. 반면 RESTful API는 REST 원칙을 비교적 잘 따르는 API를 강조할 때 쓰는 표현입니다. 즉, 두 말은 완전히 끊어져 있다기보다, 같은 영역 안에서 엄격함의 차이를 드러내는 경우가 많습니다.

### REST에서는 무엇을 중요하게 보나요

REST 스타일에서는 보통 자원을 주소로 표현하고, 동작은 HTTP 메서드로 구분합니다. 예를 들어 사용자 목록은 `/users`, 특정 사용자 한 명은 `/users/42`처럼 표현하고, 조회는 `GET`, 생성은 `POST`, 수정은 `PUT` 또는 `PATCH`, 삭제는 `DELETE`로 구분하는 식입니다. 이렇게 하면 URL은 대상을 말하고, 메서드는 행동을 말하게 됩니다.

또한 상태를 서버에 지나치게 묶어 두지 않고, 요청 하나하나가 스스로 이해될 수 있게 구성하려는 경향이 있습니다. 이를 흔히 무상태성이라고 설명합니다. 어렵게 들리지만 초보자 관점에서는 요청 한 번을 볼 때 필요한 정보가 되도록 그 안에 들어 있어야 한다 정도로 이해해도 충분합니다.

### 현실의 API는 왜 애매하게 불리나요

실무에서 모든 API가 REST 원칙을 완벽히 지키는 것은 아닙니다. 예를 들어 `/getUser`, `/createOrder`처럼 동사가 URL에 들어가기도 하고, 한 번의 요청에 너무 많은 의미가 섞이기도 합니다. 그래도 사람들은 편의상 REST API라고 부릅니다. 그래서 초보자는 REST API라고 적혀 있으면 무조건 정석 REST인가라고 생각하지 않는 편이 좋습니다.

RESTful이라는 표현은 보통 REST스럽다를 강조하는 말입니다. 자원 중심 주소가 분명하고, 메서드 사용이 자연스럽고, 응답 구조가 일관되고, 상태 코드도 의미 있게 쓰인다면 RESTful하다고 평가할 수 있습니다. 하지만 이 역시 절대적인 시험 채점표라기보다 설계 품질을 보는 관점에 가깝습니다.

### 초보자가 실무에서 챙겨야 할 포인트

처음 API를 설계하거나 읽을 때는 세 가지만 보면 됩니다. 첫째, URL이 무엇을 가리키는지 분명한가. 둘째, 메서드가 의도와 맞는가. 셋째, 응답이 일관적이고 예측 가능한가입니다. 이 세 가지가 잘 지켜지면 문서 없이도 API를 추측하기 쉬워집니다.

너무 엄격한 정의 싸움에 오래 머물 필요는 없습니다. 중요한 것은 팀이 읽기 쉽고, 실수하기 어렵고, 확장하기 쉬운 형태로 약속을 만드는 것입니다. REST와 RESTful의 차이를 아는 이유도 결국 그 목표를 더 잘 이루기 위해서입니다.

### 핵심만 다시 정리하면

REST는 웹 자원을 다루는 설계 스타일이고, REST API는 현실에서 넓게 쓰이는 표현입니다. RESTful API는 그 원칙을 비교적 잘 따르는 API를 강조할 때 주로 사용됩니다. 초보자는 이름보다도 자원 중심 주소, 메서드 의미, 응답 일관성이라는 핵심 감각을 먼저 익히는 것이 좋습니다.

## 동기와 비동기라는 개념은 무엇이고, 차이는 무엇인가요?

동기와 비동기는 작업을 기다리는 방식에 대한 개념입니다. 동기는 앞의 일이 끝날 때까지 다음으로 못 넘어가는 흐름에 가깝고, 비동기는 시간이 걸리는 일을 맡겨 두고 그 사이 다른 일을 계속할 수 있는 흐름에 가깝습니다. 초보자는 이 말을 들으면 바로 어려운 프로그래밍 문법부터 떠올리지만, 사실 핵심은 문법이 아니라 작업 흐름을 어떻게 설계하느냐에 있습니다.

가장 쉬운 비유는 식당 주문입니다. 동기 방식이라면 주문한 음식이 완전히 나올 때까지 카운터 앞을 떠나지 못하는 상황과 비슷합니다. 비동기 방식이라면 주문하고 진동벨을 받은 뒤 자리에 가서 다른 일을 할 수 있습니다. 음식이 준비되면 신호를 받고 다시 움직이면 됩니다. 즉, 비동기의 핵심은 기다림을 덜 답답하게 조직하는 것입니다.

### 왜 이 개념이 개발에서 중요한가요

컴퓨터 프로그램은 생각보다 자주 기다립니다. 네트워크 응답을 기다리고, 파일을 읽기를 기다리고, 데이터베이스 결과를 기다립니다. 만약 이런 기다림마다 전체 프로그램이 멈춘다면 화면은 버벅이고, 서버는 비효율적으로 굳어 버립니다. 그래서 어떤 작업은 기다리고, 어떤 작업은 맡겨 두고 다른 일을 하게 만드는 설계가 중요합니다.

예를 들어 웹 화면에서 버튼을 눌렀을 때 서버 응답을 받는 동안 아무 입력도 안 되고 화면이 얼어붙는다면 사용자는 서비스가 고장 났다고 느낄 수 있습니다. 반대로 비동기로 처리하면 로딩 표시를 보여 주고, 다른 화면 동작은 유지하면서, 응답이 오면 결과만 반영할 수 있습니다. 서버 쪽도 마찬가지입니다. 오래 걸리는 작업을 적절히 비동기로 다루면 같은 자원으로 더 많은 요청을 처리하기 쉬워집니다.

### 비동기라고 해서 항상 동시에 실행되는 것은 아닙니다

여기서 많이 생기는 오해가 하나 있습니다. 비동기를 곧바로 병렬 처리와 같은 말로 생각하는 것입니다. 병렬은 실제로 여러 작업이 동시에 실행되는 데 초점을 맞추고, 비동기는 기다리는 동안 다른 흐름을 계속 진행할 수 있게 만드는 데 초점이 있습니다. 둘은 관련이 있지만 완전히 같은 말은 아닙니다.

또한 비동기가 항상 더 좋은 것도 아닙니다. 읽기 쉬운 순차 흐름이 더 중요한 작은 작업은 동기로 처리하는 편이 더 단순할 수 있습니다. 핵심은 시간이 오래 걸리는 외부 작업이나 대기 작업을 다룰 때 적절히 비동기를 활용하는 것입니다. 즉, 비동기는 성능 마법이 아니라 상황에 맞는 설계 선택입니다.

### 초보자는 어떤 장면에서 먼저 체감하나요

웹에서는 `fetch`로 데이터를 불러올 때, 모바일 앱에서는 서버 통신을 보낼 때, 서버에서는 외부 API 호출이나 파일 업로드를 처리할 때 비동기를 자주 만납니다. 처음에는 `async`, `await`, 콜백, 이벤트 루프 같은 용어가 낯설 수 있지만, 그 뒤에 있는 공통 질문은 단순합니다. 이 작업이 끝날 때까지 여기서 멈춰 있어야 하나요, 아니면 다른 일을 해도 되나요?

이 질문만 명확해도 비동기를 훨씬 덜 두려워하게 됩니다. 문법은 언어마다 달라도 문제의 본질은 크게 다르지 않기 때문입니다. 기다림을 어떻게 관리할 것인가, 그리고 사용자 경험과 시스템 효율을 어떻게 지킬 것인가가 중심입니다.

## Ajax라는 것은 무엇인가요?

Ajax는 웹 페이지 전체를 새로고침하지 않고도 서버와 데이터를 주고받을 수 있게 만든 웹 개발 방식입니다. 이름은 오래된 표현이지만, 개념은 지금도 살아 있습니다. 예전 웹은 링크를 누르거나 폼을 제출할 때마다 페이지 전체를 다시 받아 왔습니다. 그러다 보니 화면이 자주 깜빡이고, 작은 데이터 하나를 바꾸는 데도 전체 페이지가 다시 그려졌습니다.

Ajax가 등장하면서 브라우저는 배경에서 서버에 요청을 보내고, 필요한 데이터만 받아와 화면 일부만 바꿀 수 있게 되었습니다. 오늘날 우리가 검색창 자동완성, 댓글 추가, 장바구니 수량 변경, 알림 새로고침 같은 기능을 자연스럽게 쓰는 데에는 이 방식의 영향이 큽니다. 즉, Ajax는 현대 웹의 앱 같은 반응성을 만든 핵심 전환점 중 하나였습니다.

### 이름은 낡았지만 개념은 여전히 중요합니다

Ajax라는 이름에는 원래 XML이 들어 있습니다. 과거에는 서버와 주고받는 데이터 형식으로 XML을 많이 썼기 때문입니다. 하지만 지금은 JSON이 훨씬 널리 쓰이고, 구현도 `XMLHttpRequest`보다 `fetch` 같은 더 현대적인 방식으로 하는 경우가 많습니다. 그래서 초보자는 XML을 꼭 써야 Ajax인가요라고 오해할 필요가 없습니다. 핵심은 데이터 형식이 아니라, 페이지 전체를 다시 열지 않고 비동기 요청으로 필요한 정보만 바꾸는 방식입니다.

즉, 오늘날에는 Ajax를 특정 기술 이름보다 브라우저에서 비동기 요청을 보내 화면 일부를 갱신하는 방식이라는 개념으로 이해하는 편이 가장 자연스럽습니다. 현대 프론트엔드 프레임워크를 쓰더라도 그 밑바탕에는 여전히 이 사고방식이 깔려 있습니다.

### 실제로 어디서 체감할 수 있나요

회원가입 화면에서 이메일 중복 확인을 눌렀을 때, 페이지 이동 없이 결과만 표시된다면 Ajax 계열의 동작입니다. 쇼핑몰에서 수량을 바꿨을 때 총액만 즉시 갱신되는 것도 마찬가지입니다. 채팅 앱이 새 메시지를 불러오는 방식, 관리자 화면이 통계를 주기적으로 다시 가져오는 방식도 넓게 보면 이 흐름 안에 있습니다.

초보자에게 중요한 포인트는 Ajax가 마법 같은 별도 프로그램이 아니라는 점입니다. 결국은 브라우저가 네트워크 요청을 보내고, 응답을 받아 화면 상태를 바꾸는 일입니다. 그래서 Ajax를 이해하면 나중에 `fetch`, 상태 관리, 로딩 처리, 에러 메시지 처리 같은 주제도 훨씬 쉽게 이어집니다.

### 핵심만 다시 정리하면

Ajax는 웹 페이지 전체를 새로고침하지 않고 서버와 비동기 통신해 필요한 부분만 갱신하는 방식입니다. 이름은 오래되었지만 현대 웹앱의 기본 감각을 설명하는 데 여전히 유효합니다. 지금은 XML보다 JSON과 `fetch`가 더 흔하지만, 본질은 배경에서 데이터를 받아 화면 일부를 바꾼다는 데 있습니다.

## XML, Json은 프로그램인가요? 어떻게 생긴건가요?

XML과 JSON은 프로그램이 아니라 데이터를 표현하는 형식입니다. 즉, 무엇을 계산하는 코드가 아니라 데이터를 어떤 모양으로 적을 것인가에 대한 약속입니다. 초보자가 이 둘을 프로그램처럼 느끼는 이유는 문법 모양이 낯설고, 파일로 따로 존재하는 경우가 많기 때문입니다. 하지만 본질은 계산이 아니라 표현입니다.

예를 들어 사용자 정보를 보내야 한다고 해 봅시다. 이름, 나이, 이메일 같은 값을 아무 규칙 없이 적으면 프로그램이 읽기 어렵습니다. 그래서 사람과 프로그램이 모두 이해하기 쉬운 모양으로 정리한 것이 JSON이나 XML입니다. 즉, 둘은 데이터를 안전하고 일관되게 주고받기 위한 포장 방식에 가깝습니다.

### JSON과 XML은 어떻게 다르게 생겼나요

JSON은 키와 값의 짝으로 이루어진 구조가 중심입니다. 그래서 객체나 목록을 표현하기 편하고, 자바스크립트와도 잘 어울려 웹 개발에서 널리 쓰입니다.

```json

{

  "name": "Kim",

  "age": 28,

  "skills": ["JavaScript", "React"]

}

```

XML은 태그를 열고 닫는 구조가 중심입니다. HTML과 비슷한 느낌이라 처음 보면 익숙하기도 하지만, 길고 장황해질 수 있습니다. 대신 구조와 메타데이터를 풍부하게 표현하기에 유리한 경우가 있어 특정 산업, 문서 교환, 오래된 시스템에서는 여전히 사용됩니다.

```xml

<user>

  <name>Kim</name>

  <age>28</age>

  <skills>

    <skill>JavaScript</skill>

    <skill>React</skill>

  </skills>

</user>

```

### 왜 요즘은 JSON을 더 자주 보게 되나요

웹과 앱 개발에서는 JSON이 더 간단하고 읽기 쉬운 편이라 자주 선택됩니다. 프론트엔드와 백엔드가 데이터를 주고받을 때도 JSON이 자연스럽고, 언어마다 파싱 도구도 잘 갖춰져 있습니다. 그래서 초보자가 처음 접하는 API 응답은 대부분 JSON인 경우가 많습니다.

그렇다고 XML이 사라진 것은 아닙니다. 금융, 공공, 문서 표준, 설정 파일, 오래된 엔터프라이즈 시스템에서는 XML이 아직도 중요한 역할을 합니다. 즉, JSON이 현재의 주류라고 해서 XML이 틀린 방식인 것은 아닙니다. 각각 강한 장면이 다릅니다.

### 초보자는 여기서 무엇을 기억하면 좋을까요

가장 먼저 기억할 것은 둘 다 데이터를 담는 형식이라는 점입니다. 계산을 하는 프로그램이 아니라, 데이터를 전달하고 저장하는 언어에 가깝습니다. 그다음으로는 JSON은 보통 더 가볍고 웹 친화적이며, XML은 구조 표현이 더 장황하지만 특정 분야에서 강하다 정도의 감각이면 충분합니다.

나중에 API 응답이나 설정 파일을 볼 때 이 감각이 매우 중요해집니다. 낯선 괄호나 태그를 보고 겁먹는 대신, 아, 이건 프로그램이 아니라 데이터를 적어 둔 형식이구나라고 이해하면 읽는 부담이 크게 줄어듭니다.

### 핵심만 다시 정리하면

XML과 JSON은 프로그램이 아니라 데이터를 표현하는 형식입니다. JSON은 비교적 가볍고 웹에서 널리 쓰이며, XML은 태그 기반 구조 표현에 강해 특정 분야에서 계속 쓰입니다. 둘의 차이를 알면 API 응답, 설정 파일, 데이터 교환 문서를 훨씬 덜 낯설게 읽을 수 있습니다.

## 폴링과 이벤트 방식의 차이는 무엇인가요?

폴링은 무슨 일이 생겼나요를 일정한 간격으로 계속 물어보는 방식입니다. 반면 이벤트 방식은 일이 생기면 알려 주세요에 더 가깝습니다. 두 방식 모두 시스템 사이에 변화를 전달하려는 목적은 같지만, 누가 먼저 움직이느냐와 얼마나 자주 확인하느냐에서 차이가 납니다.

예를 들어 택배 조회를 생각해 보겠습니다. 폴링은 사용자가 10초마다 새로고침해서 배송 상태를 확인하는 것과 비슷합니다. 이벤트 방식은 배송 상태가 바뀔 때마다 택배사가 알림을 보내 주는 것과 비슷합니다. 둘 다 정보를 알 수는 있지만, 사용 경험과 시스템 부담은 크게 달라집니다.

### 폴링은 언제 쓰고 왜 단순한가요

폴링의 장점은 구조가 단순하다는 것입니다. 클라이언트가 일정 주기로 서버에 요청만 보내면 되므로 구현이 비교적 쉽습니다. 그래서 실시간성이 아주 높지 않은 관리자 화면, 배치 작업 상태 확인, 간단한 알림 카운트 갱신 같은 곳에서 여전히 많이 사용됩니다.

하지만 폴링은 변화가 없을 때도 계속 묻는다는 한계가 있습니다. 사용자가 100명, 1만 명으로 늘어나면 쓸모없는 요청도 함께 늘어납니다. 자주 물을수록 실시간 느낌은 좋아지지만 서버 부담이 커지고, 덜 자주 물으면 부담은 줄지만 정보가 늦게 반영됩니다. 결국 타협이 필요합니다.

### 이벤트 방식은 왜 더 실시간처럼 느껴질까요

이벤트 방식은 변화가 발생했을 때만 알려 주기 때문에 불필요한 확인을 줄일 수 있습니다. 브라우저의 버튼 클릭 같은 화면 이벤트도 같은 사고방식이고, 서버가 클라이언트에 새 메시지를 보내는 실시간 알림도 넓게 보면 이벤트 기반 처리입니다. 웹에서는 웹소켓, 서버 센트 이벤트, 웹훅 같은 기술이 이런 흐름과 연결됩니다.

다만 이벤트 방식이 항상 쉬운 것은 아닙니다. 연결 상태를 오래 유지해야 하거나, 누가 어떤 이벤트를 받아야 하는지 관리해야 하거나, 실패 시 재시도 전략이 필요할 수 있습니다. 즉, 폴링보다 더 실시간에 가깝고 효율적일 수 있지만 설계 난이도는 올라갈 수 있습니다.

### 초보자는 어떤 기준으로 이해하면 좋을까요

가장 쉬운 기준은 변화가 자주 일어나고 즉시 반영되어야 하나입니다. 주식 시세, 채팅, 실시간 게임, 주문 접수 알림처럼 즉시성이 중요한 서비스는 이벤트 방식이 잘 맞습니다. 반면 하루에 몇 번만 변하는 통계 화면, 몇 분 간격으로 확인해도 되는 작업 상태 화면은 폴링으로도 충분할 수 있습니다.

실무에서는 둘을 섞어 쓰는 경우도 많습니다. 처음에는 폴링으로 단순하게 시작하고, 사용량이 커지거나 실시간성이 중요해지면 이벤트 방식으로 바꾸기도 합니다. 중요한 것은 어느 기술 이름을 외우느냐가 아니라, 정보 변화를 어떤 리듬으로 전달할지 판단하는 것입니다.

### 핵심만 다시 정리하면

폴링은 일정 주기로 계속 물어보는 방식이고, 이벤트 방식은 일이 생겼을 때 알림을 받는 방식입니다. 폴링은 단순하지만 불필요한 요청이 늘 수 있고, 이벤트 방식은 더 실시간에 가깝지만 설계가 복잡해질 수 있습니다. 따라서 서비스의 변화 빈도와 즉시성 요구를 기준으로 선택하는 것이 좋습니다.
